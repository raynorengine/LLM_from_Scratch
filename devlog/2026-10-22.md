## 결정사항

### Step5 키 설계 — "문맥과 다음 글자를 분리"
- Step4 방식 `key = (문맥) * V + (다음)` 은 n=6에서 `V⁶ = 2.17×10²⁰` 로 **64비트를 11.8배 초과**
- 결정: **`{unsigned long long ctx; int next;}` 두 필드로 분리**
  - 문맥은 n-1글자이므로 n=6에서 `V⁵ = 8.86×10¹⁶` → 64비트에 **208배 여유**
  - CSR 그룹핑은 `(ctx, next)` 2단계 비교로 유지. 나눗셈·나머지 자체가 불필요해짐
  - **한계: n ≤ 6.** n=7은 `V⁶`이라 초과. 강의 요구 범위(2~6)와 일치하므로 수용
- 문맥은 낱개 변수(`prev1`,`prev2`)가 아니라 **길이 n-1 배열(창)** 로 든다
  - 그래야 seq 패딩 / 루프 경계 / 창 밀기 / 정렬 단계 / 입출력 컬럼이 전부 한 형태로 합쳐짐

### CSR 유지
- 사용자 질문 "CSR을 왜 쓰나? 빼면?" 에 대해 실측 검토 후 **유지로 결정**
- 근거는 "없으면 안 돼서"가 **아님**:
  1. Step4에 작동하는 코드가 이미 있음 (빼는 게 추가 작업)
  2. 빈도표 출력이 결정적 순서여야 해서 **정렬은 어차피 필요**
  3. CSR이 강제하는 n ≤ 6 한계가 강의 범위와 일치
- 참고: 실제 워크로드(n당 1,000개 생성)에서는 CSR을 빼도 약 0.25초라 **체감 차이 없음**. "131배 느림"은 10,000개 기준

## 실제 결함 발견 — `isspace()`가 NBSP를 먹었다 (education/08 작성 중)

### 발견 경위
- `education/08`에 "공백은 437,534개로 전체의 23%"를 쓰려다 **"그게 원본 기준인가 분할본 기준인가"** 를 확인
- 재어 보니 원본 437,534 / 분할본 405,715 로 달랐고, 같이 재던 중 **NBSP가 268 -> 237로 31개 줄어든 것**을 발견
- **숫자의 출처를 따지는 습관이 결함을 찾아냈다.** 문서를 안 썼으면 못 찾았을 것

### 결함의 내용
- `step6_prepare.py`의 손실 검사가 `if not ch.isspace()` 로 **공백류를 통째로 제외**하고 있었다
- Python의 `str.isspace()` 는 **NBSP(U+00A0)도 True** 로 본다
- 이 데이터는 NBSP를 **문장 안의 단어 구분 공백**으로 쓴다 (실측 268개, 예: `베일리는[NB] 머릿속에서`)
  - 종결부호 뒤에 NBSP가 오는 경우 21건 + `strip()`이 양 끝 NBSP를 떼낸 것 = **31개가 버려졌다**
- 그런데 검사는 공백류를 보지 않으니 **"손실 없음"으로 보고했다.** 가짜 통과였다
- 더 나쁜 것: 그 부류에 대해 **아무 보장도 못 한다.** NBSP를 전부 날려도, 공백을 끼워 넣어도 조용히 통과

### 고치다가 한 번 더 걸렸다 (중요)
1. **1차 수정**: "공백류는 줄어드는 것만 허용, 늘어나면 실패" 로 바꿨다
   → **여전히 NBSP를 못 잡았다.** "공백류"라는 분류가 NBSP까지 덮고 있었기 때문
   → self-test에 넣은 4a(NBSP 손실 검사)가 FAIL을 내서 알았다. **검사를 먼저 만든 것이 유효했다**
2. **2차 수정(최종)**: 버려도 되는 공백을 `isspace()`가 아니라 **`SKIPPABLE_WS = " \t"` 로 한정**
   - 분할기: 경계에서 `SKIPPABLE_WS`만 건너뛴다 → NBSP 268개 전부 보존
   - `strip()` → `strip(SKIPPABLE_WS)` (strip은 양 끝 NBSP까지 떼낸다)
   - 빈 줄 판정도 같은 기준 (NBSP만 있는 줄은 실측 0개이지만 기준을 맞춤)
   - 검사: `SKIPPABLE_WS`만 감소 허용, 그 밖의 글자(NBSP 포함)는 하나도 변하면 FAIL
