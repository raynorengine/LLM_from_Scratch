## 결정사항

### Step5 키 설계 — "문맥과 다음 글자를 분리"
- Step4 방식 `key = (문맥) * V + (다음)` 은 n=6에서 `V⁶ = 2.17×10²⁰` 로 **64비트를 11.8배 초과**
- 결정: **`{unsigned long long ctx; int next;}` 두 필드로 분리**
  - 문맥은 n-1글자이므로 n=6에서 `V⁵ = 8.86×10¹⁶` → 64비트에 **208배 여유**
  - CSR 그룹핑은 `(ctx, next)` 2단계 비교로 유지. 나눗셈·나머지 자체가 불필요해짐
  - **한계: n ≤ 6.** n=7은 `V⁶`이라 초과. 강의 요구 범위(2~6)와 일치하므로 수용
- 문맥은 낱개 변수(`prev1`,`prev2`)가 아니라 **길이 n-1 배열(창)** 로 든다
  - 그래야 seq 패딩 / 루프 경계 / 창 밀기 / 정렬 단계 / 입출력 컬럼이 전부 한 형태로 합쳐짐

### CSR 유지
- 사용자 질문 "CSR을 왜 쓰나? 빼면?" 에 대해 실측 검토 후 **유지로 결정**
- 근거는 "없으면 안 돼서"가 **아님**:
  1. Step4에 작동하는 코드가 이미 있음 (빼는 게 추가 작업)
  2. 빈도표 출력이 결정적 순서여야 해서 **정렬은 어차피 필요**
  3. CSR이 강제하는 n ≤ 6 한계가 강의 범위와 일치
- 참고: 실제 워크로드(n당 1,000개 생성)에서는 CSR을 빼도 약 0.25초라 **체감 차이 없음**. "131배 느림"은 10,000개 기준

### 정정 — 오전 "n별 전체 n그램 수" 표는 패딩 방식이 달랐다 (docs/07 작성 중 발견)
