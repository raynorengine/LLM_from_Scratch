### 3. PowerShell로 42만 건 집계 → 2분 타임아웃 2회
- `Select-Object -Unique`, `Compare-Object`, 대량 `ForEach-Object` 파이프라인이 42만 건에서 사실상 멈춤
  (`-Unique`는 O(n²), 파이프라인은 항목당 오버헤드)
- 더 큰 문제는 **요청받지도 않은 부가 조사(중복 수, 정렬 여부)로 시간을 낭비했다는 것**
- → `CLAUDE.md`에 **"장시간 작업 사전 승인"** 규칙 신설. 30초 이상 예상되면 미리 알리고 승인받기.
  대량 처리는 .NET 직접 호출(`HashSet`/`Dictionary`/`StreamReader`)이나 Python으로. 데이터 처리는 애초에 PowerShell이 아니라 구현 코드로 작성.

### 4. "150만 vs 190만" 혼란 → 개행 문자
- `docs/01_N-Gram.md`는 155만, 강의는 197만. 불일치처럼 보였으나 **둘 다 맞았다.**
- `1,551,565`(글자) + `420,309`(개행 `\n`) = `1,971,874`(파일 문자수)
- 단어가 42만 개 → 줄바꿈도 42만 개. 그게 더해진 것.
- **확률 계산에는 개행 제외 155만을 쓴다.** 개행을 세면 `다`가 4.91% → 3.87%로 틀어진다.
  → 프로그램이 개행을 **별도 카운터로 출력**하게 만들어서, 4.91%가 안 나올 때 바로 원인을 알 수 있게 함.

### 5. 배열 인덱싱의 숨은 위험 (구현 전에 잡음)
- `count[cp - 0xAC00]` 방식은 **한글이 아닌 문자가 섞이면 배열 범위를 벗어나 메모리가 깨진다.** C에서 조용히 터지는 종류의 버그.
- 구현 전에 데이터를 검사 → 코드포인트 전부 `0xAC00`~`0xD79D`, 비한글 0종. 안전 확인.
- 그래도 코드에 `범위 외 문자` 카운터를 남겨둠 (방어적).

### 6. 빌드 스크립트 `.ps1` → `.bat` 전환
- `build.ps1`의 한글 메시지가 깨짐 → **PowerShell 5.1은 BOM 없는 `.ps1`을 CP949로 읽는다.**

- vcvars64.bat이 내부적으로 `'vswhere.exe' is not recognized` 메시지를 뿜지만 **무해함** (빌드는 정상)

### 7. C에서 한글 출력 깨짐 (함정 2개, 서로 별개)
1. `SetConsoleOutputCP(CP_UTF8)` 없으면 Windows 콘솔 출력이 깨진다
2. `cl /utf-8` 없으면 **소스 코드 안의 한글 문자열 리터럴**이 깨진다
- 둘 다 필요하다. 하나만 하면 여전히 깨진다.
- 추가로 파일은 반드시 `"rb"`(바이너리)로 열 것. 텍스트 모드는 Windows에서 개행을 변환한다.

### 12. 파일명에 step 접두사 도입 (리네임)

  | 이전 | 이후 |
  |---|---|
  | `char_freq.c` | `step1_char_freq.c` |
  | `verify.py` | `step1_verify.py` |
  | `char_freq.exe` / `.obj` | `step1_char_freq.exe` / `.obj` (빌드 산출물) |
  | `char_freq_result.txt` | `step1_char_freq_result.txt` (실행 결과물) |

  4. `verify.py` — `DEFAULT_RESULT = ... "char_freq_result.txt"` → "결과 파일을 찾을 수 없습니다"
- 주석·사용법 문구(총 11군데)는 동작엔 영향 없지만 나중에 헷갈리므로 같이 수정

- `verify.py`의 self-test가 자기 자신을 재호출하는데 `__file__`을 쓰고 있어서 **리네임에 영향 없음**

- **`build.bat`은 접두사를 붙이지 않고 step 공용으로 전환** (사용자 결정)
  - 이유: vswhere로 VS 찾고 vcvars 잡는 로직이 30줄인데, `step1_build.bat`/`step2_build.bat`으로 나누면 그걸 복붙해야 한다
  - 소스명을 **인자로 받도록** 수정:
    ```
    build.bat                        → 기본 step 빌드 (DEFAULT_SRC)
    build.bat run                    → 기본 step 빌드 후 실행
    build.bat step1_char_freq        → 해당 소스 빌드
    build.bat step1_char_freq run    → 빌드 후 실행
    ```
  - `.c` 접미사를 붙여도 자동으로 떼어냄. 없는 소스를 주면 `*.c` 목록을 출력
- **리네임 후 전체 재검증 완료**: 빌드 OK / 실행 결과 동일(`다 4.91%`) / `step1_verify.py` 전수 비교 통과 / self-test 4케이스 FAIL 감지 정상
- **devlog 과거 기록은 수정하지 않았다.** `CLAUDE.md` 규칙(과거 기록 append-only)에 따라, 위 12번 이전 항목들에 나오는 `char_freq.c` 등은 그 시점의 사실로 그대로 둔다
- `education/02_Character-Frequency.md`는 사용자 판단으로 수정하지 않음 (그날 배운 내용의 기록). 단 부록의 실행 명령어는 옛 이름이라 그대로 실행되지 않음 — 이 항목을 참고할 것

## 알아둘 것 (미해결/주의)
- **확률 합계가 99.9998%** — 정확히 100%가 아니다. 2,450개 `double`을 더하며 생기는 부동소수점 누적 오차. 계산이 틀린 건 아니지만 알고 있어야 함. 검증기는 0.01% 허용 오차로 통과 처리.
- **조합 가능한 음절 11,172개 중 사전에 실제 등장하는 것은 2,450개(21.9%)뿐.** 배열의 78%가 끝까지 0.
  - 유니코드는 "쓰이는 글자"가 아니라 "조합 가능한 글자" 전부를 할당해둠 (초성 19 × 중성 21 × 종성 28)
  - 예: `ㅎ+ㅣ+종성` 28글자 중 8개만 쓰임 (`히 3250`, `힘 279`, `힐 157`, `힌 60`, `힝 24`, `힙 3`, `힉 2`, `힛 1`). `힣`은 0.
  - **빈도 0 → 확률 0 → 영원히 생성 불가.** 글자 하나 수준에선 사소하지만, 앞 2글자 이상을 보는 단계로 가면 조합 폭발로 0인 칸이 대부분이 된다. N-gram의 근본 한계이고 이 78%가 그 예고편.
