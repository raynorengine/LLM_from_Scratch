## 강의가 시키는 것
- 토큰을 **글자 1개 → 형태소 1개**로 바꾼다
- 형태소 분석기는 **Kiwi**(`kiwipiepy`)를 쓴다
- 토큰 단위로 n그램을 세고 문장을 생성한 뒤, 다시 사람이 읽을 문장으로 **역변환**한다
- n이 높을 때 생기는 **중복·원문 복사**를 **백오프(backoff)** 로 해결한다
- 이 현상의 이름이 **과적합(overfitting)** 이며, 파트 2(뉴럴 네트워크)로 이어지는 개념이다

## 왜 형태소 분석인가

### 글자 단위의 한계
- Step6(글자 7그램)은 문맥이 **6글자**뿐이다. 한국어 6글자면 한 어절 남짓이라 문장 구조를 담기에 짧다
- 토큰이 형태소면 토큰 1개가 글자 1~3개어치이므로, **같은 n으로 2~3배 긴 문맥**을 본다
- 아래 "어휘 폭발"이 **강의가 드는 진짜 이유**다. 문맥 길이는 그 덤이다

> **주의 — 키 이야기는 여기 넣지 않는다.**
> Step6에서 글자 7그램만 키를 쪼갠 것(V⁷ > 2⁶⁴)은 **우리가 쓴 "여러 글자 번호를 V진법으로 하나의 64비트 정수에 포개는" 최적화의 한계**이지, N-그램이나 글자 단위의 한계가 아니다.
> 강의 참고 코드처럼 **키를 정수 배열로 두면 글자 단위로도 8그램·9그램이 가능하다.** 그러므로 "키가 터져서 형태소로 간다"는 **틀린 인과**다 (2026-10-23 Claude가 실제로 이렇게 썼다가 사용자 지적으로 정정).
> 2026-10-22에 CSR을 들어낸 이유와 같은 종류의 문제다 — *"N그램 원리가 아닌 최적화 부분이라 오히려 개념 이해를 방해한다"*. 최적화는 구현 절에만 적고, 동기 절에 올리지 않는다

### 공백으로만 나누면 안 되는 이유 — 교착어
- 영어는 공백으로 나누면 단어가 된다. 한국어는 **교착어(agglutinative language)** 라 체언·용언 뒤에 조사·어미가 계속 붙는다
- 공백으로 나누면 `학교가`·`학교를`·`학교는`이 **전부 다른 어휘**가 되어 어휘가 폭발한다
- **실측** (`data/novel_sentences.txt`를 공백으로만 분리)

| 항목 | 실측 |
|---|---|
| 어절 총수 | **472,691** |
| 고유 어절 | **94,074종** |
| 그중 1회만 등장 | **59,257종 (63.0%)** |

- **고유 어절의 63%가 딱 한 번 나온다.** n그램은 빈도를 세는 모델인데, 어휘의 3분의 2가 빈도 1이면 셀 통계가 없다
- 같은 말인데 형태만 다른 것들이 어휘를 갉아먹는 모습 (실측, 괄호 안은 빈도)

```
학교:  16종 | 학교에(17) 학교에서(17) 학교(13) 학교를(11) 학교의(11) 학교는(4) 학교가(4) 학교,(2)
사람: 245종 | 사람은(713) 사람이(553) 사람의(380) 사람들은(287) 사람을(256) 사람들이(227) 사람(213)
생각: 368종 | 생각하고(303) 생각했다.(246) 생각이(195) 생각해(175) 생각을(145) 생각한(90) 생각할(81)
우리:  81종 | 우리는(369) 우리들은(289) 우리(261) 우리들의(199) 우리가(157) 우리들이(133) 우리들(69)
```

- `생각`이라는 하나의 의미가 **368종**으로 흩어져 있다. 형태소로 쪼개면 `생각` + `하`·`었`·`다`·`을`… 로 모여 통계가 합쳐진다
- 참고: 붙은 구두점(`생각했다.`)까지 어휘에 섞여 있다. 형태소 분석기는 구두점도 별도 토큰으로 떼어낸다

### 토큰(token)이란?
| 단계 | 토큰의 단위 | 예 | 정하는 방식 |
|---|---|---|---|
| Step1~6 (지금까지) | **글자 1개** | `가` `나` `(공백)` | 코드포인트 그대로 |
| **이번 (Step7~)** | **형태소** | `반갑` `습니다` `학교` | **언어학적 규칙** (Kiwi) |
| 현대 LLM | **서브워드(subword)** | `##학교` `▁the` | **데이터에서 통계적으로 학습** (BPE 등) |
- 세 방식 모두 "텍스트를 정수 ID 열로 바꾼다"는 점은 같다. **무엇을 1개로 볼지**만 다르다
- 강의가 짚은 것: 우리가 Step6에서 글자에 번호를 매긴 것이 **이미 토크나이저의 원리**다. 단위만 바뀐다

## 토큰 구분자 문제

- 토큰 사이를 **공백으로 구분하면 원문의 공백과 구별되지 않는다.** 원문 공백도 복원해야 하므로 정보가 섞인다
- 강의에서 AI가 제안한 근본 해결책: **토큰을 숫자 ID로 저장** — 구분자 자체가 필요 없어진다. 실제 현대 토크나이저의 방식이다
- 강의의 선택: **초보 단계에서 숫자 ID는 읽기 어렵다**는 이유로 가독성을 위해 특수 기호 `<W>`, `<S>` 사용
- **주의 — 강의 본문과 참고 코드가 다르다**
  - 본문: `<W>`(토큰 구분)와 `<S>`(공백) 두 가지를 쓴다고 설명
  - `step08_tokenize.py` 머리 주석: *"후처리에서 kiwi.join()으로 복원하므로 **`<S>` 불필요**, POS 태그 필수"* → 실제로는 `<W>` 하나만 쓴다
  - 공백을 토큰으로 넣는 대신, 역변환 때 `kiwi.join()`이 띄어쓰기를 **다시 만들어낸다**. 공백 정보를 모델이 아니라 복원기가 책임지는 설계다
  - → 강의가 중간에 방식을 바꾼 것으로 보인다. 우리는 어느 쪽을 택할지 결정이 필요하다 (아래 "결정할 것" 참고)
- 참고: Step6도 같은 문제를 겪어 빈도표에서 공백을 `<SP>`로 적었다 (`docs/08`). 꺾쇠 기호를 쓰는 발상은 이미 쓰던 것과 같다

## 전체 파이프라인 (강의)

| 단계 | 도구 | 내용 |
|---|---|---|
| 1 | Python | 데이터 정제 (불필요한 내용 제거) |
| 2 | Python + Kiwi | 형태소 분석으로 토큰화 (**빈칸도 토큰으로 포함** — 본문 기준) |
| 3 | **C** | 토큰 단위 N-Gram 카운팅 및 문장 생성 |
| 4 | Python + Kiwi | 토큰 역변환하여 최종 문장으로 완성 |

- 1단계(정제)는 **우리에겐 이미 끝나 있다**: `data/korean_dictionary/novel_test_data.txt`가 정제본이다 (아래 "데이터" 참고)
- C는 **문자열을 다루지 않는다.** 토큰 → 정수 ID 사상을 1회 만들고 그다음은 전부 정수 연산이다. Step6과 구조가 같다
- 역변환이 **별도 단계인 이유**: `kiwi.join()`이 조사 선택(`은/는`, `이/가`)과 띄어쓰기를 문법에 맞게 복원해 준다. C로 할 수 없는 일이다

## Kiwi 사용의 핵심 (참고 코드에서 확인)

```python
from kiwipiepy import Kiwi
kiwi = Kiwi()
result = kiwi.tokenize("반갑습니다")        # 토큰 객체들. t.form(표면형), t.tag(품사)
kiwi.join([("반갑","VA"), ("습니다","EF")])  # → 문장으로 복원
```

- 토큰 저장 형식은 **`form/tag`** — 태그가 **필수**다. `kiwi.join()`이 품사를 알아야 조사·어미를 바르게 붙인다
- `step08_postprocess.py`는 `tok.rfind("/")` 로 파싱한다. **form 안에 `/`가 들어있을 수 있어서** 마지막 `/` 기준으로 쪼갠다 (앞에서 자르면 깨진다)

### 참고 코드가 실제로 처리한 함정 3가지
1. **종성 자모가 따로 떨어져 나온다**
   - Kiwi 출력에 U+1100~U+11FF(조합용 자모)가 단독 토큰으로 섞여 나온다
   - `step08_tokenize.py`는 `JONGSEONG_MAP`으로 **앞 글자에 종성을 합성**한다 (`ㄹ`탈락·`ㅎ`탈락·`ㅂ`불규칙까지 분기)
   - 이걸 안 하면 어휘에 자모 쪼가리가 끼어 통계가 망가진다
2. **따옴표·괄호는 버린다**
   - `SKIP_TOKENS`에 `" ' 『 』 ( ) “ ” ‘ ’ 「 」` 를 넣어 제외
   - 짝이 안 맞는 따옴표가 생성 문장에 섞이면 복원이 지저분해지기 때문. Step6에서 `“`가 닫는 따옴표로도 쓰인 걸 확인한 그 문제다 (`docs/08`)
   - **단, 이건 글자 손실이다.** 우리 규칙상 버리는 글자는 전수 집계해 보고해야 한다
3. **문장이 줄 경계를 넘어간다**
   - `sent_buffer`를 루프 **밖**에 두고, `.` `!` `?` 를 만날 때만 문장을 끊는다. 빈 줄(문단 경계)에서도 끊는다
   - 줄 단위로 끊으면 한 문장이 중간에서 잘린다

## 백오프(backoff) — 이번 챕터의 새 개념

### 문제
- n이 높아질수록 원본을 그대로 재현하는 비율이 올라가고 **같은 문장이 중복 생성**된다
- 원인은 **데이터 부족**이다. 긴 문맥일수록 그 문맥을 본 횟수가 적어, 다음 토큰 후보가 1개밖에 없는 경우가 생긴다
- 후보가 1개면 선택의 여지가 없다 = **원문 복사**

### 해결
문맥의 후보가 부족하면 **n을 한 단계씩 낮춘다** (강의 다이어그램 그대로)

```
5-그램   돈을 많이 가지고 있 → ?     후보가 매우 적음!
   ↓
4-그램      많이 가지고 있 → ?     후보 부족!
   ↓
3-그램         가지고 있 → ?     후보 충분 ✓
```

- 강의 참고 코드(`step08_sentence.c`)의 설정
  - `MIN_BACKOFF 2` — 바이그램까지만 내려간다
  - `BACKOFF_THRESHOLD 1` — **후보가 1개뿐이면 백오프**. 즉 "원문 복사밖에 못 하는 상황"을 탈출 조건으로 삼았다
  - `MAX_NGRAM 10` — n=2~10 테이블을 **동시에 메모리에 올린다**
  - 생성 10개, 프롬프트 `돈을` 고정
- 강의 보고: *"백오프를 적용하자 중복 문장이 사라지고 모두 다른 문장이 생성되었다"*
- [보충] 이것은 Katz back-off의 가장 단순한 형태다. 정식 백오프는 낮은 n의 확률에 **할인 계수**를 곱해 확률 합을 1로 유지한다. 강의 방식은 할인 없이 "후보가 적으면 그냥 내려간다"라서 **엄밀한 확률분포가 아니다** (Stupid Backoff에 가깝다)

### 특정 단어로 시작하는 문장 생성 (프롬프트)
- 앞 단어를 `돈을`로 **고정**하고 이어서 생성하는 테스트
- 강의 결과: 5그램에서 `돈을 2배로 걸고 하기로 했다` 생성. 원본에는 `돈을 2배로 걸지 않겠어`가 있었다
- → `걸`까지는 원본을 따라가다가 **그 이후를 확률적으로 다르게 이어붙여** 새 문장을 만들었다
- 구현 관점: 생성 시작 시 BOS 패딩 대신 **주어진 토큰들을 history에 미리 채우고** 시작하면 된다. Step6까지는 없던 기능이다

## 과적합(overfitting)

강의의 시험 공부 비유:

| | 기출 외우기 | 원리 이해 |
|---|---|---|
| 같은 문제 | 100점 | 90점 |
| 새 문제 | **0점** | **85점** |
| 이름 | **과적합(overfitting)** | **일반화(generalization)** |

- N-그램에서: n이 높을수록 원본 재현율↑, 새 문장 다양성↓
- 훈련 데이터에만 지나치게 맞춰져 새 데이터에 대한 성능이 떨어지는 현상
- **N-그램만의 문제가 아니다.** 뉴럴 네트워크를 포함한 모든 머신러닝의 핵심 개념이며 파트 2에서 다시 나온다
- 우리는 이미 이 현상을 **수치로 봤다**: Step6에서 원본 문장 통째 일치가 3그램 0% → 5그램 6.7% → 7그램 **20.0%** 로 올랐다 (`docs/08`). 강의가 말로 설명한 것을 Step6이 이미 측정한 셈이다

| 10그램 | 원본에 없는 자연스러운 문장 — `아버지가 서류에 기록을 하자, 아가씨는 전화를 걸고 얼마 후에 미소를 짓으며 안내를 하였습니다.` |
| 프롬프트 `돈을` (5그램) | `돈을 2배로 걸고 하기로 했다` (원본: `돈을 2배로 걸지 않겠어`) |
| 백오프 적용 후 | 중복 문장이 사라지고 모두 다른 문장 |

- 강의 평가는 **정성적**이다. 생성 개수·seed·수치 지표가 2-9에 없다
- 생성 예시는 난수 결과이므로 우리 실행에서 같은 문장이 나오지 않는다
- **형태소 토큰 수·어휘 수·n그램 규모는 강의에 수치가 없고 우리도 아직 측정하지 못했다** (Kiwi 미설치)

## 구현에서 Step6과 달라지는 것 (Claude 보충)

| | Step6 (글자) | Step7~ (형태소) |
|---|---|---|
| 어휘 V | 1,598 (실측) | **미측정** — 수만 종 예상 |
| 키(해시테이블 이름표) | 번호들을 V진법으로 포갠 64비트 정수 | **정수 배열 그대로** (`int key[N]`) |
| 테이블 수 | n마다 1개 (프로그램 분리) | 백오프 때문에 **n=2..N 동시 보유** |
| 입력 | UTF-8 바이트 스트림 | 토큰 문자열 → ID 사상 (해시) |
| 출력 | 글자 그대로 = 읽을 수 있음 | 토큰 열 → **Python 역변환 필요** |

- **키 = 해시테이블에서 항목을 구별하는 이름표**이고, 여기서 이름표는 n그램 그 자체(앞 토큰들 + 다음 토큰)다
  - Step4~6은 그 번호들을 **V진법으로 포개 64비트 정수 하나**로 만들었다 (빠르고 작아서 쓴 최적화)
  - Step7은 **포개지 않고 배열 그대로 둔다** (`int key[N]`). 강의 참고 코드와 같다
  - 포개기를 버리는 이유: V가 수만이라 어차피 곧 넘치고, 무엇보다 **포개기는 N-그램 원리가 아니라 최적화**라서 설명이 길어지는 만큼 개념을 가린다 (CSR을 들어낸 것과 같은 판단)
  - 해시는 여전히 쓴다. `hash_key(key, len)`로 "어느 칸부터 찾을지"만 정하고, 같은 n그램인지는 `key_eq`로 배열을 직접 비교한다
- **메모리**: n=2~10 테이블 9개를 동시에 들면 Step6(최대 67MB)보다 크게 늘어난다. 실측 전에는 추정하지 않는다
- **검증 설계** (CLAUDE.md 검증 규칙): `step7_verify.py`가 원본에서 **Kiwi로 다시 토큰화해** C의 빈도표와 전수 비교한다
  - Kiwi는 결정론적이므로 독립 재계산이 성립한다
  - 단, **토큰화 자체는 Kiwi 하나뿐이라 교차검증이 안 된다.** 토큰화 단계는 "글자 손실 전수 검사"(Step6 `step6_prepare.py`와 같은 방식)로 대신한다
  - 백오프는 "후보 수 ≤ 임계값이면 반드시 한 단계 내려갔는가"를 생성 로그로 검사한다

## 결정할 것 (구현 전 사용자 승인 필요)
1. **`kiwipiepy` 설치** — 이 프로젝트 최초의 외부 의존성 (Python은 "표준 라이브러리 우선" 원칙)
2. **토큰 저장 형식** — `form/tag` + `<W>` (강의·가독성) vs 숫자 ID (근본 해결·현대 방식)
3. **공백 처리** — 토큰으로 포함(본문) vs `kiwi.join()`에 맡김(참고 코드)
4. **입력** — `novel_test_data.txt` vs `novel_sentences.txt`
5. **n 범위** — 강의와 같이 2~10 vs 축소
6. **Step 분할** — 토큰 n그램과 백오프를 한 Step에 넣을지, 나눠서 효과를 측정할지
7. **따옴표 제거(`SKIP_TOKENS`)를 따라갈지** — 따라가면 글자 손실이 생기므로 전수 보고가 필요하다

## AI 사용 팁 (강의 2-9)
- **여러 AI를 교차 활용**: GPT에게 코드 검토를 시킨 뒤 그 결과를 Claude에게 전달해 개선. 서로 다른 관점을 조합한다
- **컨텍스트의 영향**: AI가 데이터 정제 코드를 **C로 쓰려고 해서** Python으로 지시해야 했다. *"C 프로젝트"* 라는 맥락이 강하면 모든 작업을 C로 하려는 경향이 생긴다
  - → 우리 `CLAUDE.md`에 *"데이터 처리 로직은 PowerShell이 아니라 Python"* 규칙이 있는 것과 같은 종류의 문제다
- **레퍼런스 폴더 활용**: 교과서·대본·참고 코드를 폴더에 모아두면 AI가 참조해 더 안정적으로 작업한다 (우리 `reference/`가 이것)
- **에포트(effort) 설정**: 앞부분은 medium으로 충분했지만 복잡해지면서 **max**로 올렸다
- **디버깅도 AI와 함께**: 문제를 알려주면 원인 분석과 수정까지 수행한다. 여러 차례 반복했다
- **전면적 재검토 요청**: 마지막에 **진행 과정을 요약한 문서를 주고** 전면 재검토를 시키면 누락·오류를 찾아낸다
  - → 우리 `PROGRESS.md`·`devlog/`가 그 요약 문서 역할을 한다

## 파트 1 마무리 (강의)
- 클로드 섀넌(1948)의 아이디어 → 글자 빈도 → 바이그램 → 트라이그램 → N-그램 비교 → 문장 생성 → 형태소 분석
- N-그램은 빈도를 세는 단순한 방식이지만, **n을 높이고 토큰 단위로 전환하면** 꽤 자연스러운 문장을 만든다
- **파트 2**: 빈도를 세는 방식 대신 **뉴럴 네트워크**가 데이터에서 패턴을 학습하는 방식으로 전환

### 더 해볼 것 (강의 제안)

- **나만의 언어 모델** — 직접 고른 데이터셋으로. 파트 2에서는 더 전문적인 평가 기준 사용
