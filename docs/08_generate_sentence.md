# 문장 생성 (글자 단위 N-그램)

> 출처: `raw/챕터2-8 문장생성.docx` (본문, 내장 이미지 없음) + Claude 보충.
> 실측값은 `data/korean_dictionary/novel_test_data.txt`와 그것을 문장 분할한 `data/novel_sentences.txt` 기준 Python 독립 계산 (2026-10-22).
> **강의의 결과(생성 예시·데이터 규모)는 "강의가 보고한 것"이다. Step6의 목표값이 아니다.** 구현을 강의 결과에 맞추지 않고, 실측이 다르면 다르다고 적는다 (사용자 지시 2026-10-22)

## 강의가 시키는 것
- 글자 단위 N-그램으로 **단어가 아니라 문장**을 생성한다
- 입력: `data/korean_dictionary/novel_test_data.txt` — *"여러 무료소설들을 자르고 정제한 데이터 셋"*
- n을 바꿔 가며 문장 품질을 비교한다 (강의 예시는 3 / 5 / 7)
- 다음 강의 예고: 글자 → **단어(토큰) 단위**. 한국어는 조사가 붙는 교착어라 형태소 분석기로 분리

## 단어 생성(Step1~5)에서 무엇이 바뀌나 — 3가지
1. **공백도 글자다**
   - 단어 생성엔 빈칸이 필요 없었지만, 문장은 단어 사이 빈칸이 있어야 문장 꼴이 된다
   - 공백과 구두점(`.` `,` `?` `!` `"` `…`)을 **하나의 글자로 취급해 N-그램 통계에 포함**시킨다
   - 구현상 의미: 공백도 그냥 글자 번호 하나다. 세기·뽑기 코드에 특별 처리가 **없다**
2. **BOS/EOS가 단어 경계 → 문장 경계**
   - Step1~5: 단어의 시작·끝. Step6: 문장의 시작·끝
   - 마침표·물음표도 글자이므로, 모델이 "구두점 다음에 EOS"를 통계로 배워 문장이 자연스럽게 끝난다
   - BOS가 **n-1개** 필요한 이유: 문맥이 앞 n-1글자인데 문장 첫 글자를 뽑을 땐 앞 글자가 0개다. 채울 것이 없으면 생성을 시작할 데가 없다
   - EOS가 필요한 이유: 종료 시점을 모델이 정해야 한다. 없으면 길이 상한으로 강제 절단밖에 없다
   - BOS/EOS는 실제 글자가 아니라 글자 번호 뒤에 붙는 특수 번호 2개 (BOS=1596, EOS=1597 → V=1,598)
   - 비대칭 하나: **BOS는 문맥에만 나오고 다음 글자 후보로는 안 나온다**(빈도 0). EOS는 후보에 포함되고 뽑히면 종료
3. **글자 → 숫자 ID를 넓은 범위에서 매긴다**
   - Step1~5: `words.txt`를 전수 스캔해 얻은 **2,450종 고정표**. 한글 완성형 음절만 나와 `used[11172]` 배열로 충분
   - Step6: 공백·숫자·영문·전각 따옴표가 섞여 나옴 → 코드포인트 전 범위를 받는 `used[65536]`(64KB)로 교체
   - 실측 코드포인트 범위 **U+0020 ~ U+FF63** (전부 U+FFFF 이하이므로 2바이트 배열 하나로 덮인다)
   - UTF-8 바이트 길이별 글자 종류: **1바이트 80종 / 2바이트 1종(NBSP) / 3바이트 1,515종** → 디코더가 1~3바이트를 모두 처리해야 한다 (Step5는 3바이트 전용이었다)
   - 강의 [보충]: 이 방식은 이후 형태소 분석 강의에서 **토큰을 숫자 ID로 저장하는 방식과 같은 원리**다
   - 번호를 **등장 순서가 아니라 코드포인트 오름차순**으로 매긴다 (강의 보충은 등장 순서라고 쓴다)
     - 이유: 후보를 번호 순서로 훑어 누적해 뽑으므로, 번호가 실행마다 달라지면 같은 seed에서도 결과가 달라진다. 모델 확률은 어느 쪽이든 같지만 재현성이 깨진다

## 강의 주장 (Step6에서 확인할 대상, 미확인)
| n | 강의 평가 | 강의 생성 예시 |
|---|---|---|
| 3 | 얼핏 문장 같지만 의미는 없다. 글자가 랜덤하게 이어지지만 **공백 위치 정도는 자연스럽다** | `그 외쳤다 읽고 위하여도 치마가 앉아 있던 것도` |
| 5 | 훨씬 파악이 되고 자연스러워지기 시작. **단어 조각이 보인다** | `데이비드는 당황했다, 내가 곧 일을 알게 되었다` |
| 7 | **원본 소설의 문체가 느껨지는 수준** | `첨에는 가야를 원망두 했으나 지금 와서 점점 낯살이 많아` |

- 예시 문장은 강의 실행의 난수 결과라 우리 실행에서 같은 문장이 나오지 않는다

## 문장 분할 — `.?!`로 쪼갠다 (전처리로 분리)
원본은 한 줄에 여러 문장이 뭉쳐 있다 (평균 54.49글자 / 최대 4,104글자). 그대로 쓰면 모델이 "마침표 뒤에도 계속"을 배워 EOS가 잘 안 나온다. 그래서 `step6_prepare.py`가 종결부호로 쪼갠 `data/novel_sentences.txt`를 만든다.

**분할을 C가 아니라 전처리로 둔 이유** — C와 `step6_verify.py`가 각자 분할 규칙을 구현하면 **같은 분할 버그를 함께 가지게 되어** 교차검증이 성립하지 않는다 (`CLAUDE.md` 검증 규칙 2번). 한 번만 쪼개고 양쪽이 같은 파일을 읽는다.

**실측으로 찾은 함정 4개** (전부 글자 손실로 드러났다)

| 함정 | 실측 | 처리 |
|---|---|---|
| 닫는 따옴표가 구분자로 먹혀 결과물에 안 담김 | 첫 시도에서 **12,942자** (`"` 11,741 · `”` 671 · `'` 379 · `)` 135 · `’` 16) | 종결부호 뒤의 닫는 따옴표·괄호는 앞 문장에 붙인다 |
| 소수점·번호를 문장 끝으로 오인 | `.` 뒤 숫자 4,945건 | 숫자`.`숫자는 끊지 않는다 |
| `...` `…` 가 빈 조각을 만든다 | 연속 마침표 1,028건, `…` 1,733개 | 연속 종결부호는 한 덩어리로 소비 |
| **이 데이터는 `“`를 닫는 따옴표로도 쓴다** | `“` 2,310 vs `”` 680 (비대칭), `.“`로 끝나는 줄 13,419건 → 외톨이 `“` 1,553개 | 글자 없는 조각은 버리지 않고 앞 문장에 붙인다 (버리면 **1,972자**) |
| **`isspace()`가 NBSP를 공백으로 봐서 버렸다** | NBSP 268개 중 **31개**가 경계에서 사라짐. 검사가 공백류를 제외해 **"손실 0"으로 보고** | 버려도 되는 공백을 `SKIPPABLE_WS = " 	"` 로 한정. NBSP는 데이터 글자로 보존 |

**분할 결과 (전수 검사 통과)**

```
원본 35,034줄  ->  66,961문장
평균 28.04글자 | 중앙 24 | 최대 358 | 3글자 이하 348개(0.52%)
모든 글자 비교: 원본 1,909,086 -> 분할 1,877,291
  차이는 U+0020 31,795자 제거뿐 (문장 사이 공백, 의도됨)
  NBSP 268개를 포함한 나머지 모든 글자는 개수가 완전히 같다
글자 종류 1,596종 (분할해도 변하지 않는다)
```

- 손실 검사는 **모든 글자를 종류별로 전수 집계**해 비교하고, 글자를 두 부류로 나눠 다른 기준을 쓴다
  - `SKIPPABLE_WS`(ASCII 스페이스·탭): 줄어드는 것만 허용, 몇 개 줄었는지 보고. **늘어나면 실패**
  - 그 밖의 모든 글자(**NBSP 포함**): 하나라도 변하면 실패
- 상위 몇 개만 보면 NBSP 268개나 `｣` 6개에서 난 손실을 못 잡는다
- 검사를 통과하지 못하면 파일을 쓰지 않고 종료 코드 1로 끝낸다
- 출력은 LF 고정. CRLF면 C가 `"rb"`로 읽을 때 `\r`이 글자로 섞여 글자 종류가 늘어난다 (아래 7그램 키 여유가 27종뿐이라 늘어나면 안 된다)

## 실측 규모 (분할 기준, BOS n-1개 + EOS 1개 패딩)
V = 1,598 (글자 1,596 + BOS + EOS)

| n | 전체 n그램 | 서로 다른 n그램(=패턴수) | 서로 다른 문맥 | 해시 칸 | 적재율 |
|---|---|---|---|---|---|
| 3 | 1,944,252 | **171,051** | 38,032 | 2¹⁹ | 32.6% |
| 5 | 1,944,252 | **821,221** | 473,641 | 2²¹ | 39.2% |
| 7 | 1,944,252 | **1,319,934** | 1,092,883 | 2²² | 31.5% |
- 전체 n그램 수가 n과 무관하게 1,944,252로 같다: 길이 L 문장 → n그램 L+1개
  - 검산: 글자 1,877,291 + 문장 66,961 = 1,944,252. 패딩 개수를 틀리면 이 값이 깨지므로 검증 항목으로 쓴다
- 서로 다른 n그램은 n이 커질수록 늘지만 증가 폭은 줄어든다 (3→5 +380%, 5→7 +61%)
- 해시 칸은 n마다 다르게 잡았다. Step4의 거부선(적재율 70%)에 여유를 두는 가장 작은 2의 거듭제곱
  - n=7을 2²¹로 하면 62.9%로 거부선에 너무 가깝다

## 자료구조와 키 — 7그램이 가능해진다 (Claude 보충)
- **해시테이블 + 후보 전수 순차 조회** (Step4·Step5와 동일). CSR은 쓰지 않는다 (사용자 지시 2026-10-22)
- **n=3, 5는 단일 키**: 앞 글자들과 다음 글자를 V진법 n자리 수 하나로 만든다
  - V³ ≈ 4.08×10⁹, V⁵ ≈ 1.04×10¹⁶ 로 64비트에 여유롭게 들어간다
- **n=7은 키를 쪼갠다**: 문맥(64비트) + 다음 글자(int) 두 칸으로 저장
  - 단일 키면 V⁷ ≈ 2.66×10²² 로 2⁶⁴ = 1.8447×10¹⁹ 을 약 1,400배 넘는다
  - 문맥만이면 V⁶ = 1.6652×10¹⁹ < 2⁶⁴ → **들어간다 (여유 1.108배)**
- Step5(단어, V=2,452)는 n ≤ 6이 한계였다. V⁶ = 2.17×10²⁰ 으로 넘쳤기 때문
  - **문장 데이터는 글자 종류가 줄어서(2,450 → 1,596) 7그램이 가능해졌다.** 강의가 7그램을 예시로 든 것과 맞아떨어진다
- **주의: 글자 종류가 늘면 7그램 키가 조용히 터진다**
  - V⁶ < 2⁶⁴ ⟺ **V ≤ 1,625**, 즉 글자 종류 **1,623종이 상한** (현재 1,596종에서 27종 여유)
  - 넘치면 서로 다른 7그램이 같은 키로 합쳐지고 **오류도 나지 않는다** (Step4 `[7]` 주석과 같은 함정)
  - → 구현에 V 상한 검사를 넣었다. 곱하기 **전에** 나눗셈으로 확인한다 (먼저 곱하면 이미 넘쳐서 검사가 무의미하다)
  - n=8은 문맥이 V⁷ ≈ 2.66×10²² 이라 이 데이터로도 불가능하다
- 해시 값은 넘쳐도 되고 키는 안 된다: `ht_slot`의 `문맥 × V + 다음`은 "어느 칸부터 찾을지"만 정하므로 넘쳐서 겹치면 충돌일 뿐이다. 같은 n그램인지는 문맥과 다음 글자를 직접 비교해 판단한다

## 공백을 빈도표에 어떻게 쓰나 (Step6에서 새로 생긴 문제)
빈도표는 탭 구분인데 공백이 하나의 글자라서 그대로 쓰면 빈 칸처럼 보여 사람도 검증기도 열을 구분할 수 없다. 표시 이름을 쓴다.

| 글자 | 표시 이름 |
|---|---|
| 스페이스 (437,534회) | `<SP>` |
| NBSP U+00A0 (268회) | `<NBSP>` |
| 제어문자 | `<U+XXXX>` (이 데이터엔 없지만 방어) |
| BOS / EOS | `BOS` / `EOS` (Step5와 동일) |
| 그 외 전부 | 글자 그대로 (`가`, `.`, `"`, `A`) |
- 데이터에 `<`와 `>`가 **없음을 전수 확인**했으므로 꺾쇠 이름이 실제 글자와 충돌하지 않는다
- 검증 모드(`--map` / `--hist`)의 표준입력도 같은 표기를 쓴다. 공백을 그대로 보내면 `scanf("%s")`가 구분자로 읽어 버려 문맥을 받을 수 없다
- 단, **결과 파일의 문장은 글자 그대로** 쓴다 (`<SP>`가 아니라 진짜 공백). 사람이 문장을 읽는 용도다

## 평가 — 강의가 지적한 "원본 매칭의 어려움"
- 강의: *"단어 생성과 달리 데이터양이 많아지기 때문에 생성된 결과가 원본 텍스트에 있는 문장인지 확인하기가 단순하지 않다"*
- 단어 생성에서 쓴 **사전 일치율**을 문장에 그대로 쓸 수 없다
  - 단어는 3.69글자라 같은 길이의 단어가 많아 길이별 비교가 뜻이 있었다. 문장은 평균 28글자에 최대 358글자라 길이별로 나누면 칸마다 표본이 몇 개뿐이라 비율이 의미를 잃는다
  - 그래서 Step6은 **전체 일치율만** 센다: 생성 문장이 `novel_sentences.txt`에 통째로 있는 비율 (`*` 표시)
- 이 지표는 **암기**를 재는 용도다. n이 커질수록 원본 문장을 그대로 재현하는 쪽으로 가는지 본다
- "그럴듯한 새 문장인지"는 숫자로 못 잰다 → 결과 파일의 문장을 직접 읽어 판단한다 (강의 평가도 정성적이다)
- 실측 (seed 1792649450, 15개 생성)

| n | 원본 문장 그대로 | 관찰 |
|---|---|---|
| 3 | 0 / 15 = 0.0% | 어절은 끊기지만 의미가 없다 |
| 5 | 1 / 15 = 6.7% | 구절 단위로 읽히기 시작. 짧은 대화문 하나가 원본 그대로 (`"괜찮습니다.`) |
| 7 | **3 / 15 = 20.0%** | 짧은 대화문이 원본 그대로 나온다 (`"기운을 내요."`, `“그럼 가봐.`, `"좋습니다.`) |
- 7그램에서 암기가 드러나는 이유: 문맥이 6글자라 **6글자 이하 문장은 문맥이 BOS 패딩으로 거의 다 덮여** 원본을 그대로 복원할 수밖에 없다
  - Step5에서 본 *"길이 n-2 이하 생성 단어는 반드시 사전 단어"*(education/06 5.2)와 같은 현상이다

## [보충] N-그램의 "학습"은 딥러닝의 훈련과 다르다
- AI가 코드 주석에 "N-그램 학습"이라고 쓰는 경우가 있지만, 딥러닝의 훈련(training)과는 다르다
- N-그램은 **빈도를 세는(counting) 것**이므로 학습보다 **통계 수집**에 가깝다
- 경사하강법·가중치 갱신이 없다. 데이터를 한 번 훑으면 끝이고, 같은 데이터면 결과가 항상 같다 (난수는 생성 단계에만 쓰인다)
- 실측 세기 시간: n=3 10.9ms / n=5 41.6ms / n=7 76.1ms (188만 글자)

## AI 사용 팁 (강의 2-8)
- **계획과 검증까지 요청**: *"글자 단위 N-그램으로 문장을 생성해 보고 싶다. 계획을 세워줘"* → 구현 계획뿐 아니라 검증 방법까지 포함된 계획서가 나온다
- **데이터 정제도 AI에게**: *"데이터를 청소해야 하지 않을까"* → 불필요한 내용을 식별해 정제 코드를 작성. 미덥지 않으면 *"더 할 거 없냐"*, *"모두 제거해줘"* 로 반복 요청해 품질을 높인다
- **매번 결과가 다름**: LLM은 비결정적이라 같은 지시에도 코드 구조·접근이 달라진다. 강의는 이를 단점이 아니라 *"자신의 생각을 반영시킬 여지"* 로 본다
