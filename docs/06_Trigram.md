# 트라이그램 (Trigram)

> 출처: `raw/챕터2-6 트라이그램(Trigram).docx` + Claude 보충. 실측값은 `data/korean_dictionary/words.txt` 기준 Python 독립 계산 (2026-10-21, 생성 실험은 10만 개, seed 12345)

## 바이그램 → 트라이그램
- 트라이그램: n=3. 앞 **2글자**를 보고 다음 글자를 예측 → P(c | a, b)
- 계산: P(c | a, b) = count(a, b, c) / count(a, b, ·)
  - count(a, b, ·) = 문맥 (a, b) 뒤에 무언가가 온 모든 횟수
- 바이그램보다 긴 패턴을 반영 → 생성 결과가 더 자연스러움 (강의)
- 비유: 바이그램 = 두 글자 끝말잇기 → 트라이그램 = **앞 두 글자를 보고** 다음 글자 고르기

## 슬라이딩 윈도우 + BOS 패딩
- 3글자 창을 한 칸씩 이동
- 문맥이 2글자여야 하므로 시작에 **BOS 2개**를 붙인다 (강의: "'사' 한 글자 단어는 어쩔 수 없이 앞에 패딩 문자로 BOS 2개")
  - 나비 → `[BOS] [BOS] 나 비 [EOS]` → 3그램: (BOS,BOS,나) (BOS,나,비) (나,비,EOS)
  - 길이 L 단어 → 3그램 **L+1개** (바이그램 BOS/EOS 포함과 같은 개수)
  - EOS는 1개면 충분 — EOS가 뽑히는 순간 생성이 끝나므로 그 뒤 문맥이 필요 없음
- 강의 표: (BOS, BOS) 다음 → 사 4,614 / 가 4,448 / 자 4,105
  - 실측 일치. 바이그램의 BOS 행과 **같은 값**이다 (BOS 2개 = "단어 첫 글자"라는 같은 정보)
- 생성: 문맥 (BOS, BOS)에서 출발 → 다음 글자 c를 뽑음 → 문맥을 (b, c)로 한 칸 밀기 → EOS가 나오면 종료

## 실측 규모
| 항목 | 바이그램 | 트라이그램 |
|---|---|---|
| n그램 총 개수 (BOS/EOS 포함) | 1,971,874 | 1,971,874 |
| 서로 다른 n그램 | 171,425 | **654,039** |
| 서로 다른 문맥 | 2,451 | 169,589 |
- 강의 "약 65만 개 트라이그램" → 실측 654,039 (BOS 2개 + EOS 1개 패딩 기준). 일치
  - 패딩 없이 단어 안에서만 세면: 총 712,304 / 서로 다른 430,931 → 강의는 패딩을 넣은 기준
- 평균 단어 길이: 강의 3.6글자 / 실측 1,551,565 ÷ 420,309 = **3.69글자** (강의는 버림 표기로 보임)

## 자료구조 (Claude 보충 — 강의 문서에는 없음)
- 2차원 배열의 확장인 3차원 배열은 불가능
  - 2,452³ ≈ 147억 칸 × 4B ≈ **59GB**. 그중 65만 칸만 사용 (0.004%)
  - 바이그램에서 배운 "없는 조합에 메모리를 쓰지 않는다"가 여기서는 선택이 아니라 필수
- 키를 정수 하나로: `key = (a × V + b) × V + c` (V = 2,452)
  - 최댓값 ≈ 1.47 × 10¹⁰ > 2³² (약 43억) → **32비트 정수에 안 들어감. 64비트(`unsigned long long`) 키 필요**
  - 바이그램 키(최대 약 600만)는 32비트로 충분했음 — Step3 코드를 그대로 복사하면 여기서 조용히 넘침
- 해시테이블 크기: 65만 키 → 2²⁰(약 105만) 칸이면 적재율 62% (선형 탐사엔 높은 편) / 2²¹(약 210만) 칸이면 31%
- 문맥별 후보 조회
  - 바이그램 ②(해시만)처럼 후보 2,452개를 전부 조회하는 방식은 문맥마다 2,452번이라 더 불리해짐
  - CSR처럼 키를 정렬하면 같은 문맥 (a, b)의 후보들이 연속 구간에 모임 → 문맥 → 구간을 찾는 방법이 필요 (문맥 16.9만 개)
  - 구체적인 설계는 Step4 브리핑에서 정한다

## 체계적 비교: 사전 일치율
- 강의: 눈으로 보고 판단하기 어려움 → **1,000개 생성 후 사전에 있는 단어의 비율**로 비교
- 정의: 생성된 단어 중 `words.txt`에 정확히 있는 단어의 비율. 길이별로도 본다
- Claude 보충: 일치율은 트라이그램 전용 지표가 아니라 **어떤 생성 모델에도 쓸 수 있다.** Step3 질의응답에서 이미 비공식적으로 쟀다 (result_03: 19/50)
- 강의 vs 실측 (실측 10만 개씩)
  | | 강의 바이그램 | 실측 바이그램 | 강의 트라이그램 | 실측 트라이그램 |
  |---|---|---|---|---|
  | 전체 | 40% | 41.6% | 61.7% | **57.5%** |
  | 1글자 | — | 98.7% | — | 100% |
  | 2글자 | 79% | 80.1% | 98% | 97.1% |
  | 3글자 | 17% | 16.3% | 65% | 63.1% |
  | 4글자 | — | 9.2% | — | 50.2% |
  | 5글자 | 0% | 0.3% | 27% | **17.4%** |
  | 6글자 | — | 0% | — | 10.5% |
  - 바이그램은 강의와 거의 일치. 트라이그램 전체·5글자는 강의보다 낮음
  - 강의는 1,000개라 5글자 표본이 약 100개뿐 (실측 비율 10.9% 기준) → 표본 변동이 클 수 있음. 패딩 방식 차이 가능성도 있음 (강의 상세 미공개)
- 생성 길이 분포의 변화 (실측)
  | 길이 | 사전 | 바이그램 생성 | 트라이그램 생성 |
  |---|---|---|---|
  | 1글자 | 0.32% | 21.3% | **0.31%** |
  - 바이그램의 "한 글자 단어 과다" 문제가 사라짐. 문맥 (BOS, 사)가 "첫 글자 '사'"를 알기 때문
  - P(EOS | 사) = 25.8% (바이그램) → P(EOS | BOS, 사) = 1 / 4,614 = **0.02%** (트라이그램)

## 좋은 언어 모델이란 (강의)
- 사전에 있는 단어만 만드는 것이 좋은 것은 아니다
- **사전에 없지만 있을 법한 그럴듯한 단어**를 만들어야 진정한 언어 모델
- 즉 일치율은 높을수록 무조건 좋은 지표가 아니다 → 아래 과적합과 연결

## n을 너무 높이면: 과적합 (설명만, 구현 안 함)
- 평균 단어 길이 3.69글자 → n이 단어 길이 이상이면 **문맥이 단어 전체를 포함**
  - 사전 단어를 그대로 재현할 수밖에 없음 → 새 단어를 만드는 능력이 사라짐
- 강의 그림: 6-그램(문맥 = 앞 5글자)으로 "자동판매기" 생성
  | 단계 | 문맥 | 선택지 |
  |---|---|---|
  | 1글자 | (BOS×5) | 많음 (가, 나, 다 …) |
  | 2글자 | …자 | 꽤 있음 (자동차, 자연, 자유 …) |
  | 3글자 | …자동 | 줄어듦 (자동차, 자동문, 자동판매기 …) |
  | 4글자 | …자동판 | 거의 없음 |
  | 5글자 | …자동판매 | 1~2개 |
  | 6글자 | 자동판매기 | 거의 확정 |
- 실측 (words.txt에서 그 접두사로 시작하는 단어)
  | 접두사 | 단어 수 | 다음 글자 종류 |
  |---|---|---|
  | 자 | 4,105 | 431 (기 373, 연 278, 동 267 …) |
  | 자동 | 267 | 118 (차 34, 조 10, 제 9 …) |
  | 자동판 | **1** | 1 (매) |
  | 자동판매 | 1 | 1 (기) |
  | 자동판매기 | 1 | 1 (EOS) |
  - 강의 그림보다 더 빨리 좁혀짐: **3글자 "자동판"에서 이미 확정** (단어 1개뿐)
- 실측: 다음 글자 선택지가 **1개뿐인 문맥**의 비율 (BOS/EOS 패딩 포함)
  | n | 서로 다른 문맥 | 선택지 1개인 문맥 |
  |---|---|---|
  | 2 | 2,451 | 17.9% |
  | 3 | 169,589 | 49.7% |
  | 4 | 547,576 | 79.8% |
  | 5 | 684,407 | 84.3% |
  | 6 | 720,877 | 85.2% |
  - 트라이그램에서 이미 문맥 절반이 "외운 길" 하나뿐. n=4부터 80%를 넘음
- 강의: "n을 100까지 늘리면?" → 100글자 단어가 없으므로 사실상 **사전 통째로 외우기**. 일치율 100%에 가깝지만 새 단어를 못 만듦
- LLM에서도 같은 문제: 모델을 과하게 맞추면 **과적합** = 학습 데이터를 그대로 외움
- 강의 제안: "n을 2~6까지 비교해 봐라" → 이 저장소에서는 Step4를 트라이그램 전용으로 두고, n 비교는 위 실측 표로 설명만 한다 (2026-10-21 결정, 독립 Step 원칙)

## AI 사용 팁 (강의)
- **다음 단계를 물어보기**: "그다음엔 뭘 하면 좋을까" → AI가 트라이그램 확장, 사전 검증, 자모 분리 분석 등을 제안
  - 이 저장소에선 자모 분리를 Step4에서 제외: n이 아니라 토큰 단위를 바꾸는 것이라 두 변수가 동시에 바뀜 → 토크나이저 단계의 주제
- **명시적으로 지시해야 하는 경우**: AI가 사전 데이터를 갖고 있었는데도 생성 단어 검증을 스스로 하지 않음. "당장 적용해줘"라고 지시한 뒤에야 추가
- **간결한 지시의 효과**: "세 글자 해줘"만으로 트라이그램 구현 + 기존 파일 번호 규칙에 맞춘 파일명까지 자동
- **체계적 평가 제안**: 바이그램과 트라이그램 차이가 불분명하다고 하자 AI가 1,000개 생성 후 사전 일치율 비교를 제안. 정량 평가 방법을 AI에게 묻는 것도 효과적
