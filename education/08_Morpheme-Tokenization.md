## 들어가기 전에 — 왜 형태소로 가는가

Step1~6까지 토큰은 **글자 1개**였다. 이제 **형태소 1개**로 바꾼다.

이유는 하나다. **한국어는 교착어(agglutinative language)** 라서 명사·동사 뒤에 조사와 어미가 끝없이 붙는다. 공백으로만 나누면 `학교가`·`학교를`·`학교는`이 전부 **다른 어휘**가 된다.

실측으로 확인한 것:

| 항목 | 실측 |
|---|---|
| 고유 어절 (공백 분리) | **94,074종** |
| 그중 **딱 한 번만** 등장 | **59,257종 (63.0%)** |

N-그램은 **빈도를 세는 모델**이다. 그런데 어휘의 3분의 2가 빈도 1이면 **셀 통계가 없다.**

한 단어만 떼어 보면 더 분명하다 (`생각`으로 시작하는 고유 어절, 괄호는 빈도):

```
368종 | 생각하고(303) 생각했다.(246) 생각이(195) 생각해(175) 생각을(145) 생각한(90) …
       1회만 등장하는 것이 213종(58%): 생각해냈습니다. 생각하자마자 생각했죠?" 생각뿐이었다. …
```

하나의 의미가 **368갈래로 흩어져 있다.** 형태소로 쪼개면 `생각`이라는 조각을 공유하게 되어 통계가 모인다.

> **주의 — "키가 터져서 형태소로 간다"는 말은 틀렸다.**
> Step6에서 글자 7그램만 키를 쪼갠 것(V⁷ > 2⁶⁴)은 *"여러 글자 번호를 V진법으로 64비트 정수 하나에 포개는"* **최적화의 한계**였다. 키를 정수 배열로 두면 글자 단위로도 8·9그램이 가능하다.
> 최적화는 구현 사정이지 동기가 아니다. (2026-10-23에 실제로 이 혼동이 있었고, CSR을 들어낸 것과 같은 종류의 문제였다)

# 1단계 — 데이터 전처리

## 1.1 왜 전처리가 필요한가

원본은 **한 줄에 여러 문장이 뭉쳐 있다** (평균 54.5글자, 최대 4,104글자).

그대로 쓰면 BOS/EOS가 "문장의 시작·끝"이 아니라 **"줄의 시작·끝"** 이 된다. 모델은 문장을 끝내는 법(EOS)을 배우지 못하고 "줄이 끝나는 법"을 배운다.

**이건 우리만의 문제가 아니다.** 강의 참고 구현 둘 다 문장을 쪼갠다:

```python
# reference_python 노트북
for para in re.split(r"\n\s*\n", text):            # 빈 줄 = 문단 경계
    for s in re.findall(r"[^.!?]+[.!?]*", para):   # 종결부호에서 자르기

# reference_C 의 step08_tokenize.py
if form in (".", "!", "?"):                        # 종결부호에서 문장 끊기
    out.write("<W>".join(sent_buffer) + "\n")
```

차이는 **언제 쪼개느냐**뿐이다. 강의는 토큰화할 때, 우리는 미리.

## 1.2 어디까지 버릴 것인가 — 참고 구현이 서로 다르다

이 결정이 Phase 1의 핵심이었다. 확인해 보니 **강의의 두 참고 구현이 서로 다른 선택을 했다.**

| | 숫자 | 문장 속 영문 | 따옴표 |
|---|---|---|---|
| `reference_C/clean_data.py` | **유지** | **유지** (줄 전체가 영문인 줄만 삭제) | 정제에선 유지 → 토큰화에서 `SKIP_TOKENS`로 버림 |
| `reference_python` 노트북 | 제거 | 제거 | 제거 |

노트북 쪽 필터는 이것이다:
```python
not_allowed = re.compile(r"[^가-힣 ,.!?]")    # 한글·공백·,.!? 외 전부 제거
```

### 숫자·영문을 버리면 무슨 일이 생기나 (실측)

```
원본: 거기에는 2미터가 넘는 리자놀의 큰 몸집이
결과: 거기에는  미터가 넘는 리자놀의 큰 몸집이      ← 수량이 사라짐

원본: 로봇은 SF에서는 가장 잘 알려진
결과: 로봇은  에서는 가장 잘 알려진                 ← 비문이 됨
```

숫자 **7,311개**, 영문 **6,734개**가 사라진다. 전체의 2.51%라는 비율로는 보이지 않는 손실이다.

### 우리가 택한 것

**숫자·영문은 살리고, 따옴표는 버린다.**

```python
ALLOWED_RE = re.compile(r"[가-힣0-9A-Za-z ,.!?]")
```

- **숫자·영문을 살리는 이유**: 자연스러운 문장을 만드는 것이 목적인데 뜻이 깨지고 비문이 된다
- **따옴표를 버리는 이유**: 참고 구현 **양쪽 다** 결국 n그램에는 따옴표를 넣지 않는다(노트북은 정제에서, C는 토큰화에서). 버리는 *시점*만 다르고 최종 결과는 같은데, **정제 때 버리면 문장 분할의 따옴표 함정까지 함께 사라진다**

> **판단 기준에 대한 교훈**: 처음에 *"우리는 C 프로젝트니까 C reference를 따라야 한다"* 고 근거를 들었는데, 이건 틀린 기준이다. 참고 구현이 둘 다 Python이었어도 답은 같아야 한다. **기준은 참고 구현의 언어가 아니라 내용** — 숫자·영문이 문장에 필요한가 — 이어야 한다.

### 따옴표 함정이란 (Step6에서 겪은 것)

따옴표를 남기면 분할이 지옥이 된다. Step6 당시 실측:

| 함정 | 실측 |
|---|---|
| 닫는 따옴표가 구분자에 먹혀 사라짐 | **12,942자 손실** |
| 소수점·번호를 문장 끝으로 오인 | `.` 뒤 숫자 4,945건 |
| `...` `…` 가 빈 조각을 만듦 | 연속 마침표 1,028건 |
| 이 데이터는 `“`를 **닫는** 따옴표로도 씀 | 외톨이 `“` 1,553개 |
| `isspace()`가 NBSP를 공백으로 봐서 버림 | NBSP 31개 조용히 소실 |

따옴표를 먼저 버리면 **이 다섯이 통째로 사라진다.** 강의가 왜 그렇게 했는지 여기서 이해된다.

## 1.3 강의 정규식에 손실 버그가 있다

강의 노트북의 분할 정규식:
```python
re.findall(r"[^.!?]+[.!?]*", para)
```

`[^.!?]+` 가 **최소 한 글자를 요구**한다. 그래서 **문단이 종결부호로 시작하면 그 부호들이 통째로 사라진다.**

정제 후 `"...그래` → `...그래` 처럼 점으로 시작하는 문단이 실제로 생길 수 있다. 그래서 우리는 정규식 대신 **직접 훑는 스캐너**로 구현했다:

```python
while i < len(text):
    ch = text[i]
    buf.append(ch)
    if ch in TERMINATORS:
        i += 1
        while i < len(text) and text[i] in TERMINATORS:   # 연속 종결부호를 함께 삼킨다
            buf.append(text[i]); i += 1
        sentences.append("".join(buf)); buf = []
        continue
    i += 1
if buf:                      # 종결부호 없이 끝난 꼬리도 버리지 않는다
    sentences.append("".join(buf))
```

연속 종결부호를 함께 삼키는 이유는, 하나씩 끊으면 `.` 만 든 빈 문장이 줄줄이 생기기 때문이다.

## 1.4 검사를 세 갈래로 나눈 이유

**정제는 일부러 글자를 버리는 작업이다.** 그래서 버그로 글자가 사라져도 "원래 버리려던 것"과 구분되지 않는다. 그래서 검사를 셋으로 나눴다.

| 갈래 | 대상 | 기준 |
|---|---|---|
| (1) | 허용 글자 중 공백이 아닌 것 (한글·숫자·영문·`,.!?`) | **개수가 완전히 같아야 한다** |
| (2) | 허용하지 않은 글자 | 결과에 **0개여야 한다** |
| (3) | 공백 | 검사하지 않고 **개수만 보고** |

**(3)만 예외인 이유**: 공백은 양쪽으로 변한다. 문단 안의 줄바꿈이 공백으로 바뀌어 **늘기도 하고**, 문장 경계에서 떼어내 **줄기도 한다**. "줄어들기만 한다" 같은 규칙을 쓸 수 없다.

> Step6에서 `isspace()`로 공백류를 통째로 검사에서 뺐다가 **NBSP 31개가 조용히 사라진 적**이 있다. 그래서 여기서는 **ASCII 공백 하나만** 예외로 두고 나머지는 전부 (2)에 걸리게 했다. **검사에서 제외하는 범위는 직접 열거해서 최소로 잡는다.**

검사를 통과하지 못하면 **파일을 쓰지 않고 종료 코드 1로 끝낸다.** 망가진 데이터를 저장하면 다음 단계가 그걸 정상으로 믿고 진행해 원인을 찾기 어려워진다.

# 2단계 — 형태소 토큰화

## 2.1 토큰이 실제로 어떻게 생겼나

```
원문 : 바로 그때 랄프는 너무 놀라 기절할 뻔했습니다.
토큰 : 바로/MAG 그때/NNG 랄프/NNP 는/JX 너무/MAG 놀라/VV 어/EC
       기절/NNG 하/XSV ᆯ/ETM 뻔/NNB 하/XSA 었/EP 습니다/EF ./SF
```

문장 하나가 **15개 토큰**이 된다. `기절할` 한 어절이 `기절`+`하`+`ㄹ` 세 조각이다.

### 품사 태그 (Kiwi 공식 태그표)

| 태그 | 뜻 | 예 |
|---|---|---|
| **SN** | **숫자(0-9)** | `27/SN` `124/SN` |
| **SL** | **알파벳(A-Z a-z)** | `C/SL` |
| SF | 종결 부호(`.` `!` `?`) | `./SF` |
| SP | 구분 부호(`,` `/` `:` `;`) | `,/SP` |
| NNG / NNP / NNB | 일반명사 / 고유명사 / **의존명사** | `세기/NNG` `랄프/NNP` `미터/NNB` |
| NP | 대명사 | `거기/NP` |
| JKS / JKO / JKG / JKB / JX | 주격 / 목적격 / 관형격 / 부사격 / 보조사 | `이/JKS` `를/JKO` `는/JX` |
| VV / VA / VX | 동사 / 형용사 / 보조용언 | `넘/VV` `크/VA` `있/VX` |
| EP / EF / EC / ETM | 선어말 / 종결 / 연결 / 관형형 어미 | `었/EP` `습니다/EF` |
| XSV / XSA | 동사 / 형용사 파생 접미사 | `하/XSV` |
| MAG | 일반 부사 | `바로/MAG` |

Phase 1에서 살린 숫자·영문이 `SN`·`SL`로 제대로 태깅된다.

다만 **고유명사는 틀린다**: `리자놀` → `리자/NNP` + `놀/NNG`, `죽다` → `죽다/NNP`(고유명사로 오인). SF 소설 고유명사가 Kiwi 사전에 없어서다.

## 2.2 토큰 구분자 문제 — `<W>` 와 `<S>`

토큰 사이를 **공백으로 구분하면 원문의 공백과 구별되지 않는다.** 그래서 전용 기호를 쓴다.

- `<W>` : 형태소 구분자
- `<S>` : 공백 토큰

```
27/SN<W>세기/NNG<W>의/JKG<W><S><W>발명/NNG<W>왕/NNG
                            ↑ 여기만 원문에 공백이 있었다
```

### `<S>`를 어디에 넣는지 어떻게 아나

Kiwi는 **공백을 토큰으로 주지 않는다.** 대신 토큰마다 원문에서의 **시작 위치(start)와 길이(len)** 를 알려준다. 앞 토큰이 끝난 자리와 다음 토큰이 시작하는 자리가 **벌어져 있으면** 그 사이에 공백이 있었다는 뜻이다.

```
27/SN    start=0 len=2     → 0~1번 글자
세기/NNG  start=2 len=2     → 2~3번 글자      ← 0+2 == 2, 붙어 있음 = 공백 없음
```

문자열 검색(`" " in ...`)으로 찾으면 토큰 경계와 어긋난다. **위치 정보를 쓰는 것이 정확하다.**

## 2.3 가장 중요한 발견 — 토큰은 원문의 조각이 아니다

Kiwi는 **기본형(lemma)으로 정규화해서** 준다. 원문 조각과 비교해 보면:

```
form='크'     원문조각='큰'        form='넘어지'  원문조각='넘어져'
form='보이'   원문조각='보였'      form='었'      원문조각='였'
```

한 문장 28토큰 중 **6개가 원문과 다르다.** form을 그대로 이어붙이면:

```
...넘어지어 있는 것이 보이었습니다.      ← 이어붙인 것
...넘어져 있는 것이 보였습니다.          ← 원문
```

**Step6과 근본적으로 다른 지점이다.** 글자 토큰은 이어붙이면 그냥 원문이었다.

## 2.4 `kiwi.join()` 은 원문을 복원하지 못한다

되돌리는 함수가 `kiwi.join()`인데, 표본 1,000문장에서 **66.3%만** 원문과 일치했다.

### 왜 `27세기`가 `27 세기`가 되나

**`join()`에는 원문의 공백 정보가 전달되지 않는다.** 우리가 넘기는 건 `(형태, 품사)` 쌍뿐이라, join은 **품사만 보고 띄어쓰기 규칙을 새로 적용**한다:

```
join([27/SN, 세기/NNG])  →  '27 세기'      숫자 + 일반명사  → 띄움
join([2/SN,  미터/NNB])  →  '2미터'        숫자 + 의존명사  → 붙임
join([발명/NNG, 왕/NNG]) →  '발명 왕'      명사 + 명사      → 띄움
join([아리스/NNP, 는/JX])→  '아리스는'     명사 + 조사      → 붙임
```

`2미터`는 멀쩡한데 `27세기`만 벌어지는 이유가 이것이다. **NNG냐 NNB냐의 차이**다.

중요한 건 **공백 정보가 토큰화 시점에는 살아 있었다**는 점이다(start/len이 알려준다). 잃어버리는 곳은 join이다.

## 2.5 복원 방식 3가지 비교 (표본 1,000문장, 토큰 16,924개)

| 방식 | 복원 정확도 | 복원 방법 |
|---|---|---|
| **(1) `<W>`만** | **66.3%** | `kiwi.join()`에 전부 맡김 |
| **(2) `<W>`+`<S>`** | **84.4%** | `<S>`로 어절 띄움 + 어절마다 join + **어절 안의 공백 제거** |
| **(3) `<S>`+실무방식** | **100.0%** | 원문 조각을 그냥 이어붙임 — 다만 **쓸 수 없다** (2.7 참고) |

### (2)에서 "어절 안의 공백 제거"가 핵심이다

`<S>`로 어절을 띄우는 것만으로는 **68.8%** 밖에 안 됐다. join이 **한 어절 안에도** 공백을 넣기 때문이다:

```
join([27/SN, 세기/NNG, 의/JKG])  →  '27 세기의'
```

`27세기의`는 한 어절이라 `<S>`로 끊을 자리가 없는데 join이 안쪽을 벌린다.

**해결의 근거**: 한 어절 안에는 **원래 공백이 없다**(그게 어절의 정의). 따라서 어절 내부에 나타난 공백은 **100% join이 만든 것**이므로 지워도 된다. 이 한 줄이 68.8% → **84.4%**를 만든다.

### 남은 15.6%는 고칠 수 없다

```
대었습니다 → 댔습니다     되어 → 돼       보아요 → 봐요
떨구었 → 떨궜             이게 → 이것이   ← 이건 거꾸로 풀어쓴 것
```

전부 **축약형 차이**다. 띄어쓰기가 아니라 Kiwi가 표준형으로 정규화하는 것이라 `(형태, 품사)`만으로는 복구할 방법이 없다. `join(lm_search=False)`도 시험했으나 **84.4%로 동일**했다.

### 역할 분담이 이렇게 정리된다

| 담당 | 하는 일 |
|---|---|
| **`<S>`** | 어절 경계 = 띄어쓰기 |
| **`join`** | 어절 **안**의 활용형 복원 (`넘어지`+`어` → `넘어져`) |
| **공백 제거** | join이 어절 안에 넣은 공백 삭제 |

## 2.6 형태소 분석기는 원문 복원용 도구가 아니다

`넘어져`를 `넘어지 + 어`로 바꾸는 것이 형태소 분석의 **본업**이다. 이것을 **정규화(lemmatization)** 라고 하며, **정보를 일부러 버려서 '같은 말'을 하나로 모으는 작업**이다.

**즉 정규화는 본질적으로 비가역이다.**

실무에서 형태소 분석기를 쓰는 곳은 **원문을 되돌릴 필요가 없는 작업**이다 — 검색 색인, 키워드 추출, 통계 분석. 문장 생성에는 쓰지 않는다.

우리가 84%에서 막히는 이유는 **도구를 용도 밖으로 쓰고 있기 때문**이다.

## 2.7 더 근본적인 사실 — 형태소 분석은 분할(partition)이 아니다

실무 토크나이저는 원문을 **겹치지 않게 나눠 가진다.** 그래서 이어붙이면 원문이 된다.

그런데 Kiwi는 **한 글자를 두 토큰이 공유한다**:

```
`큰`     → 크/VA(start=0,len=1) + ᆫ/ETM(start=0,len=1)      같은 글자를 둘이 가리킴
`넘어져` → 넘어지/VV(start=6,len=3) + 어/EC(start=8,len=1)   1글자 겹침
```

표본 1,000문장 실측: 겹치는 토큰 **1,372개(8.1%)**, 겹침이 있는 문장 **764개(76.4%)**.

축약·활용 때문에 "어디서 자른다"가 **글자 경계와 맞아떨어지지 않는다.**

### 그래서 (3)의 100%는 쓸 수 없는 100%다

겹친 부분을 건너뛰게 만들면 복원은 100%가 된다. 대신 **토큰의 8.1%가 빈 토큰**이 된다:

```
구해/VV<W>  /EC  <W>냈/VX<W>  /EP  <W>습니다/EF
              ↑ 빈 토큰        ↑ 빈 토큰
```

**빈 토큰은 n그램에 넣을 수 없다.** 복원만 되고 토크나이저로는 못 쓴다.

> **교훈: 숫자가 100%라고 해서 쓸 수 있다는 뜻이 아니다.** 처음 구현했을 때 23.6%가 나왔고, 원인을 추적해서야 "겹침"이라는 구조적 사실을 알았다. 지표가 이상하면 구현을 의심하되, 고친 뒤에는 **그 지표가 무엇을 대가로 얻어졌는지**까지 봐야 한다.

## 2.8 실무는 어떻게 하나 — 애초에 가역이게 설계한다

HuggingFace 문서(강의 참고자료 [3])의 SentencePiece 설명:

> "treats the input text as a raw byte or character stream and **includes the space character, represented as `▁`, in the vocabulary**."
> "At decoding, SentencePiece **concatenates all tokens and replaces `▁` with a space**."

공백을 어휘에 넣고 전용 기호로 표시한다 — **강의의 `<S>`와 같은 발상이다.** 그리고 토큰이 항상 원문의 부분문자열이라 **이어붙이면 원문**이 된다. 복원 규칙이라 할 것이 없고 치환 하나뿐이다.

GPT-2의 byte-level BPE는 256개 바이트를 전부 어휘에 넣어 `<unk>` 자체가 없다.

**단, `<S>`라는 발상만 같고 바탕이 다르다.** SentencePiece는 **분할 위에** `▁`를 얹어서 100%가 공짜지만, 우리는 **분할이 아닌 것 위에** `<S>`를 얹는 거라 100%를 받으려면 토큰을 망가뜨려야 한다.

## 2.9 그렇다면 실무 방식이 공짜인가 — 아니다

원문 조각을 그대로 토큰으로 쓰면 `넘어지`/`넘어져`/`넘어졌`가 서로 다른 토큰이 된다. 표본에서 어휘가 **2,227종 → 2,724종 (1.22배)** 로 늘었다.

형태소 분석을 한 목적이 "어휘를 줄여 빈도를 모으는 것"이었음을 생각하면, **가역성과 어휘 효율은 맞바꿈 관계**다.

현대 서브워드 토크나이저는 이 둘을 동시에 잡으려고 나온 것이다. **언어학적 규칙을 버리고**, 데이터에서 통계적으로 자주 쓰이는 조각을 찾아 어휘를 줄이면서도, 조각이 원문의 부분문자열이라 가역성을 유지한다.

### 이 실습의 위치

```
글자 단위 (Step1~6)    가역 O  / 어휘 작음  / 문맥 짧음
형태소 단위 (Step7)    가역 X  / 어휘 줄임  / 문맥 길어짐    ← 지금 여기
서브워드 (현대 LLM)    가역 O  / 어휘 줄임  / 문맥 길어짐
```

**형태소 단위를 직접 해 봐야 "왜 현대 LLM이 언어학적 분석을 버리고 통계적 서브워드로 갔는지"가 체감된다.** 지금 84.4%에서 막힌 것이 바로 그 이유다.

## 2.10 전체 토큰화 — 실제로 돌려 보니

여기까지가 5문장 미리보기였다. 이제 64,376문장 전부에 적용한다. 결정한 것은 둘이다.

- **`<S>` 포함 버전 하나만 만든다.** 공백을 버리면 복원이 66.3%로 떨어지는 것을 이미 봤다
- **자모 합성은 하지 않는다.** `큰` → `크/VA` + `ᆫ/ETM` 을 그대로 둔다
  - reference_C가 자모를 앞 토큰에 합치는 것은 그쪽이 `form`을 **그냥 이어붙여** 복원하기 때문이다. 우리는 `kiwi.join()`으로 복원하므로 합칠 필요가 없다

### 합격 기준을 따로 만들어야 했다

복원 일치율은 84% 언저리로 나온다. **이 수치로는 "버그인지 Kiwi의 정규화 탓인지" 구분할 수 없다.** 85%가 나오든 83%가 나오든 정상처럼 보인다.

그래서 **100%여야만 하는 것**을 따로 정했다.

> **`<S>` 개수 == 원문의 공백 개수**

공백은 이 단계가 **보존하기로 한 정보**다. 개수가 어긋나면 그건 변명의 여지 없는 결함이다. 이걸 "하드 검사"로 두고, 하나라도 틀리면 **파일을 쓰지 않고 종료**하게 했다.

이 검사가 실제로 두 번 울렸다.

### 1차 — `<S>`가 100칸 부족했다

Kiwi는 **띄어 쓴 고유명사를 토큰 하나로 묶는다.**

```
`강철 동굴/NNP`  (start=2, len=5)     ← 토큰 안에 공백이 들어 있다
실측 98개 / 33종 : 도망친 로봇, 존 록스턴, 쥘 베른, 알파 센타우리 ...
```

토큰 안에 있는 공백은 토큰 **사이**의 틈이 아니므로 `<S>`가 만들어지지 않는다. 그리고 복원할 때 "어절 안의 공백은 join이 만든 것"이라며 지우므로, **`강철 동굴` → `강철동굴`** 로 깨진다. (실제로 깨지는 것을 확인했다)

해결: 공백이 든 토큰을 쪼개고 사이에 `<S>`를 넣는다.
```
강철 동굴/NNP  →  강철/NNP<W><S><W>동굴/NNP
```
복원 결과는 같다 — `join([('강철','NNP'),('동굴','NNP')])` 가 `'강철 동굴'` 을 돌려준다.

### 2차 — 고치니 이번엔 3칸이 넘쳤다

반대 방향의 문제였다. Kiwi는 고유명사를 표준형으로 바꾸면서 **없던 공백을 만들기도 한다.**

```
원문 `오토맨`      → form `오토 맨`        (0칸 → 1칸)
원문 `아이러브 유`  → form `아이 러브 유`   (1칸 → 2칸)
```

`form` 기준으로 쪼개니 원문에 없던 공백이 생긴 것이다. 그래서 **공백이 끼는 토큰은 `form`을 버리고 원문 조각을 쓴다.** 표준형을 잃지만 98개뿐이고, **원문에 없는 공백을 지어내는 것보다 낫다.**

> **여기서 배울 것**: 2.3에서 "토큰은 원문의 조각이 아니다"라고 했는데, 그 성질이 **공백에서도 똑같이 나타난다.** 정규화는 글자만 바꾸는 게 아니라 띄어쓰기도 바꾼다.

### 결과 — 어휘 폭발이 해소됐다

이 단계의 목적은 하나였다. **어휘를 줄여 빈도를 모으는 것.** 숫자로 확인된다.

| | 공백 분리 어절 | **형태소** |
|---|---|---|
| 어휘 | 94,074종 | **16,917종** |
| 1회만 등장 | 63.0% | **30.5%** |

**어휘 5.6배 감소**, 빈도 1짜리는 63% → 30.5%로 떨어졌다. "셀 통계가 없다"던 상태에서 벗어났다.

| 항목 | 값 |
|---|---|
| 문장 / 토큰 | 64,376 / 1,460,593 |
| 그중 `<S>` | 408,173 (**27.9%**) |
| 평균 토큰/문장 | 22.69 |
| 복원 일치 (2.5의 (2)안) | **85.9%** (표본 84.4%와 근접) |

품사 분포 상위: `NNG` 17.7% / `VV` 8.2% / `EC` 8.1% / `SF` 6.1% / `EF` 5.6%

### 다음 단계에 영향을 주는 숫자

**공백이 전체 토큰의 27.9%다.** n그램이 보는 문맥의 1/4 이상이 공백이라는 뜻이다. n=5라면 평균적으로 **내용 있는 토큰은 3~4개**뿐이다. 공백을 토큰으로 넣기로 한 대가이며, 다음 단계에서 n을 정할 때 고려해야 한다.

### 검증에 대한 교훈 하나

프로그램이 스스로 낸 통계와, **토큰 파일만 보고 밖에서 다시 센 값**이 달랐다 — 토큰 100개, 어휘 2종. 원인은 통계를 "Kiwi가 준 원본 토큰"에서 세는 바람에 위에서 쪼갠 결과가 반영되지 않은 것이었다.

**프로그램 안에서만 검증했다면 영영 몰랐을 종류의 결함이다.** 검증은 반드시 *결과물*을 보고, *다른 경로로* 다시 계산해야 한다.

## 복습용 핵심 정리

1. **형태소로 가는 이유는 교착어의 어휘 폭발** 하나다. 고유 어절 94,074종 중 63%가 빈도 1이라 셀 통계가 없다. 키·V진법 같은 **최적화는 동기가 아니다**
2. **전처리에서 무엇을 버릴지는 내용으로 판단한다.** 참고 구현이 어떤 언어로 쓰였는지는 기준이 아니다. 숫자·영문을 버리면 `2미터` → `미터`, `로봇은 SF에서는` → `로봇은 에서는`이 된다
3. **정제는 일부러 버리는 작업이라 버그가 숨는다.** 검사를 (허용 글자 = 완전 일치) / (금지 글자 = 0개) / (공백 = 보고만) 세 갈래로 나눈다. **검사 제외 범위는 직접 열거해서 최소로**
4. **`kiwi.join()`은 품사만 보고 띄어쓰기를 새로 만든다.** 원문 공백은 토큰화 시점(start/len)에는 살아 있고 join에서 잃는다. `<S>`가 그것을 붙잡아 둔다
5. **Kiwi 토큰은 기본형이고, 구간이 서로 겹친다.** 그래서 형태소 분석은 원문의 분할이 아니고, 이어붙여 복원할 수 없다. 정규화는 본질적으로 비가역이다
6. **가역성 ↔ 어휘 효율은 맞바꿈.** 서브워드 토크나이저는 언어학을 버리고 통계로 둘 다 잡은 것이다
7. **100%라는 숫자를 그대로 믿지 않는다.** 그 수치가 무엇을 대가로 얻어졌는지 본다 (빈 토큰 8.1%)
8. **합격 기준은 "100%여야만 하는 것"으로 정한다.** 복원 일치율처럼 애매한 지표는 버그를 가린다.
   여기서는 `<S>` 개수 == 원문 공백 개수가 그 역할을 했고, 실제로 결함 2개를 잡았다
9. **형태소 전환의 성과**: 어휘 94,074종 → 16,917종 (**5.6배**), 빈도 1 비율 63.0% → **30.5%**.
   대가는 공백이 토큰의 **27.9%** 를 차지한다는 것
