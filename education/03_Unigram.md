# 유니그램 — 빈도표로 글자를 "생성"하기

## 복습용 핵심 정리

> **한 줄 요약**: 유니그램은 "빈도표 + 확률대로 뽑기"다. 확률은 정확히 재현되지만, 앞 글자를 보지 않으므로 말이 되지 않는다. 구현의 핵심은 **누적 빈도 → 난수 → 이진 탐색** 세 단계이고, 진짜 함정은 수학이 아니라 C 구현의 디테일(`rand()` 범위, 모듈로 편향, `>` 한 글자)에 있다.

### 개념
- 유니그램 모델 = 빈도표. 생성 = 확률대로 뽑기의 반복
- **구간 길이 = 빈도, 확률 = 구간 길이 ÷ 전체 길이**. 균등 난수를 누적 빈도로 나눈 구간에 대응 → 역변환 샘플링
- 탐욕적 디코딩은 반복, 확률적 샘플링은 다양하지만 의미 없음 → 원인은 **맥락 없음**

### C 핵심 로직
- `srand(seed)`: 수열의 출발점. **한 번만**. 같은 seed = 같은 결과
- `rand()`: LCG 공식으로 만든 정해진 수열. 15비트(최대 32,767)
- `rand30`: `rand()` 두 개 → 30비트. **호출 순서는 별도 문장으로 고정**
- `rand_below`: 모듈로 편향 → 끝자락 재추첨
- `sample_index`: **"누적 > r인 첫 위치"** 를 찾는 이진 탐색(`upper_bound`). 2,450종 → 12회. **`>` 한 글자가 전부**

## 1. 유니그램 = 빈도표 + 뽑기

### 모델은 빈도표 그 자체다
- Step1에서 만든 `step1_char_freq_result.txt`(2,450종 빈도표)가 **유니그램 모델의 전부**다. 따로 "학습"하는 단계가 없다. 세는 것이 학습이다.
- Step2는 이 표를 **불러와서** 글자를 생성한다.
  ```
  Step1: 데이터 → 세기 → 빈도표 저장        (= 학습 + 모델 저장)
  Step2: 빈도표 불러오기 → 확률대로 뽑기    (= 모델 로드 + 추론)
  ```
- 이 구조는 LLM까지 그대로 간다. 학습해서 가중치 파일을 저장하고, 추론할 때 불러와 다음 토큰을 뽑는다. 달라지는 것은 "확률표를 무엇으로 만드느냐"뿐이다.

## 2. 확률적 샘플링의 원리 — 다트 던지기

### 확률을 "칸 수"로 바꾸기

#### 먼저, 강의 그림은 가상의 예시다
강의 그림 "다(50%) | 하(30%) | 는(20%)"는 실제 데이터가 아니다. **글자가 3개뿐이고 빈도 합이 100인 가상의 데이터**로 원리만 보여 준 것이다.
```
가상 데이터:  다 50번, 하 30번, 는 20번  (합 100)

칸 번호  0 ─────────── 49 │ 50 ──── 79 │ 80 ── 99
         [      다 50칸     ][  하 30칸  ][ 는 20칸 ]

난수 r을 0~99 중 하나 고르게 뽑는다 → r=63이면 '하'의 칸 → '하'
```
실제 국어사전에서 '다'는 약 155만 자 중 76,241번이므로 **4.91%** 다.

#### 용어 정리 — 서로 다른 네 가지
| 용어 | 뜻 | 가상 예시 '하' | 실제 데이터 '다' |
|---|---|---|---|
| **빈도 = 구간 길이** | 그 글자가 맡는 **칸의 개수** | 30칸 | 76,241칸 |
| **누적 빈도** | 그 글자까지 빈도를 더한 값 = **구간이 끝나는 경계** | 80 | 76,241 |
| **난수 범위 = 구간** | 그 글자가 뽑히게 되는 **r 값들** | 50 ~ 79 | 0 ~ 76,240 |
| **확률** | 구간 길이 ÷ 전체 길이 | 30 ÷ 100 = 30% | 76,241 ÷ 1,551,565 = **4.91%** |

- **구간 길이는 확률이 아니라 빈도다.** 확률은 구간 길이를 전체 길이로 나눈 **비율**이다
- 누적 빈도는 구간의 **경계**를 표시하는 값이다. 구간 길이와 다르다 ('하'의 누적은 80이지만 길이는 30)
- 난수 범위는 구간 그 자체다. 경계(누적 빈도)를 알면 범위가 정해진다: **앞 글자의 누적 ~ 내 누적 - 1**

#### 실제 데이터
155만 칸짜리 줄을 2,450종 글자가 **빈도만큼** 나눠 갖는다.
```
글자   빈도(구간 길이)  누적 빈도(경계)  난수 범위(구간)
다    76,241          76,241          0       ~  76,240
하    48,158          124,399         76,241  ~ 124,398
이    25,670          150,069         124,399 ~ 150,068
...
(마지막)               1,551,565       ... ~ 1,551,564
```
- r을 0 ~ 1,551,564 중 **아무 칸이나 똑같은 확률로** 뽑는다(균등 난수)
- 그러면 r이 '다'의 구간에 떨어질 확률 = '다'의 칸 수 ÷ 전체 칸 수 = 76,241 / 1,551,565 = **4.91%**
- 즉 **칸을 빈도만큼 나눠 주기만 하면, 균등 난수가 저절로 확률대로 글자를 고른다**
- 확률(소수)을 따로 계산하지 않는다. **정수 빈도를 누적하기만 하면 된다.** 부동소수점 오차도 없다

> **비유**: 다트판을 글자별로 **빈도만큼 넓이**를 나눠 칠한다. 다트(난수)는 아무 데나 고르게 꽂힌다. 넓은 칸일수록 많이 맞는다. 이진 탐색은 다트가 꽂힌 칸이 누구 것인지 확인하는 일이다.

### 내가 헷갈렸던 것: "찾는다"는 게 무슨 뜻인가

> **Q.** 누적 빈도 테이블에서, 먼저 난수를 만들고, 그 값을 이진 탐색으로 찾아가서 글자를 찾는다고 이해하면 되나?

**A.** 순서는 맞다. 하지만 **특정 글자를 찾는 게 아니라 난수가 떨어진 "구간"을 찾는 것**이다.
1. (한 번) 누적 빈도표 준비: 각 글자는 값 하나가 아니라 **구간 하나**를 맡는다
2. (매번) 난수 r 생성: 예) r = 100,000
3. (매번) 이진 탐색: 100,000은 76,241 ~ 124,398 구간 → **'하'**

- "어떤 글자를 찾을지"는 미리 정해져 있지 않다. 난수가 나와야 결정된다.
- **확률은 탐색이 아니라 "구간 길이(빈도) ÷ 전체 길이"에서 나온다.** 이진 탐색은 속도만 담당한다. 선형 탐색으로 바꿔도 같은 r이면 같은 글자가 나온다.

## 3. C 핵심 로직 해부 — `step2_unigram.c`

> 이번 실습에서 가장 많이 질문한 부분. 코드 한 줄 한 줄이 왜 그렇게 생겼는지.

### 3.1 전체 흐름은 한 줄이다
글자 하나를 뽑는 코드:
```c
g_table[ sample_index( rand_below(g_total) ) ].ch
//        ③ 구간 찾기    ② 균등 난수 r       ① 누적 빈도 (로딩 때 계산)
```
그리고 이 줄이 반복되기 전에 **한 번** `srand(seed)`가 실행된다.

### 3.2 Q. "어떤 랜덤 방식을 쓴 거야? 함수 네 개가 다 랜덤 샘플링 아닌가?"

**아니다. 실제로 난수를 만드는 곳은 두 함수뿐이다.**

| 함수 | 랜덤인가 | 하는 일 |
|---|---|---|
| `rand30` | **예** | 난수 원료: `rand()` 두 개 → 30비트 |
| `rand_below` | **예** | 0 ~ 1,551,564 중 하나를 **고르게** |
| `sample_index` | 아니오 | r이 어느 구간인지 **찾기만** 한다 (같은 r → 항상 같은 글자) |
| `argmax_index` | 아니오 | 탐욕적 디코딩용 최다 빈도 글자 (샘플링과 무관) |

- **난수 생성기**: MSVC 표준 `rand()` (선형 합동 생성기, LCG)
- **샘플링 방식**: 누적 빈도 + 이진 탐색 = **역변환 샘플링**(inverse transform sampling, 룰렛 휠 선택이라고도 함)
  - 핵심: **균등** 난수를 빈도만큼 길이가 다른 구간에 대응시키면 → **확률 분포를 따르는** 샘플이 된다

### 3.3 `srand(seed)` — 난수 수열의 출발점

> **Q.** `srand()`에 대해 설명했나? 확률적 샘플링에서 여기가 핵심 로직 아닌가?

**A.** `srand()`는 핵심 계산은 아니지만, **"무엇이 나올지"를 처음부터 결정하는 출발점**이다.

#### `rand()`의 정체: 진짜 난수가 아니라 정해진 수열
```
state = state × 214013 + 2531011   (32비트에서 넘치면 버림)
반환값 = (state >> 16) & 0x7FFF     (15비트 → 그래서 RAND_MAX가 32,767)
```
- `rand()`는 내부에 숫자 `state` 하나를 갖고, 부를 때마다 이 공식으로 다음 값을 계산할 뿐이다 → **의사(가짜) 난수**
- `srand(seed)`는 이 `state`의 **시작값**을 정한다. 출발점이 같으면 그 뒤 수열 전체가 같다

#### 실제 추적: seed 42 → "결르에동칼"
결과 파일 `_01`(seed 42)의 1번 줄과 정확히 일치한다.

| 글자 | `rand()` 두 번 | rand30 | r = x % 1,551,565 | 결과 |
|---|---|---|---|---|
| 1 | 175, 400 | (175<<15)\|400 = 5,734,800 | 1,080,105 | **결** |
| 2 | 17869, 30056 | 585,561,448 | 621,443 | **르** |
| 3 | 16083, 12879 | 527,020,623 | 1,040,088 | **에** |
| 4 | 8016, 7644 | 262,675,932 | 461,447 | **동** |
| 5 | 15809, 1769 | 518,031,081 | 1,359,936 | **칼** |

글자 하나에 `rand()` 두 번 → 10글자 × 30줄이면 수열에서 숫자 600개를 차례로 꺼내 쓴다.

#### `srand()`를 다룰 때 주의할 점
1. **안 부르면** C 표준상 seed 1로 시작한다 → 매번 같은 결과
2. **반복문 안에서 부르면** 매번 같은 출발점으로 돌아간다 → 모든 글자가 같은 r → "결결결결결" (탐욕적 디코딩처럼 반복)
3. **seed = 현재 시각(`time(NULL)`)** 은 1초 단위 → 같은 1초 안에 두 번 실행하면 같은 결과

#### 정리: 역할 분담
| 순서 | 코드 | 역할 |
|---|---|---|
| 0 | `srand(seed)` | 수열의 **출발점** (한 번) |
| 1 | `rand30` | 수열에서 다음 숫자 꺼내기 |
| 2 | `rand_below` | 범위를 0 ~ total-1로 고르게 |
| 3 | `sample_index` | 구간 → 글자 |

**`srand()`는 "무엇이 나올지"를, 1~3은 "어떤 확률로 나올지"를 정한다.** seed를 바꿔도 분포 검정은 똑같이 통과한다.

### 3.4 `rand30` — 왜 `rand()`를 두 번 부르나
```c
static unsigned long long rand30(void)
{
    unsigned long long hi = (unsigned long long)(rand() & 0x7FFF);
    unsigned long long lo = (unsigned long long)(rand() & 0x7FFF);
    return (hi << 15) | lo;
}
```
- **문제**: MSVC `rand()`는 0 ~ 32,767까지만 나온다. 전체 빈도 합은 1,551,565다.
  - `rand() % 1551565`를 쓰면 r이 32,767을 못 넘는다
  - '다'의 구간이 0 ~ 76,240이므로 **'다'만 뽑힌다**
  - → **확률적 샘플링인데 탐욕적 디코딩과 같은 결과**가 나온다 (강의에서 말한 "난수 범위 문제"의 실체)
- **해결**: 15비트 두 개를 이어 붙여 30비트(0 ~ 1,073,741,823)를 만든다
- **디테일 1**: `(rand() << 15) | rand()` 한 줄로 쓰지 않은 이유 → C는 두 `rand()` 중 **어느 쪽을 먼저 호출할지 보장하지 않는다**. 컴파일러마다 순서가 달라지면 같은 seed에서 다른 결과가 나온다
- **디테일 2**: `& 0x7FFF` → RAND_MAX가 더 큰 컴파일러(gcc 등)에서도 정확히 15비트씩만 쓰게 한다

### 3.5 `rand_below` — 모듈로 편향 제거
```c
limit = 2^30 - (2^30 % n);
do { x = rand30(); } while (x >= limit);   /* 끝자락은 버리고 다시 */
return x % n;
```
- 2^30은 1,551,565로 나눠떨어지지 않는다 → `x % n`을 하면 **앞쪽 값이 아주 조금 더 자주** 나온다 (모듈로 편향)
- n의 배수가 끝나는 지점(`limit`) 이상이 나오면 버리고 다시 뽑는다 (재추첨, rejection sampling)
- 버려질 확률은 0.1% 정도라 속도 영향은 없다

### 3.6 `sample_index` — 이진 탐색

> **Q.** `sample_index()`의 while문 로직이 이진 탐색이야?

**A. 맞다.** 다만 교과서 기본형과 모양이 다르다.
```c
static int sample_index(long long r)
{
    int lo = 0, hi = g_kinds - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (g_cum[mid] > r) hi = mid;      /* mid가 답일 수도 있다 → 남긴다 */
        else                lo = mid + 1;  /* mid와 왼쪽은 절대 답이 아니다 */
    }
    return lo;
}
```

| | 교과서 기본형 | `sample_index` |
|---|---|---|
| 찾는 것 | 값이 **같은** 위치 | 누적이 r보다 **큰 첫** 위치 |
| 종료 | 같으면 즉시 반환 | 범위가 1칸이 될 때까지 |
| 반복 조건 | `lo <= hi` | `lo < hi` |
| 표준 라이브러리 | — | C++ `std::upper_bound`, Python `bisect.bisect_right` |

- 핵심 불변식: **"답은 항상 [lo, hi] 안에 있다"**. 이 조건을 유지하며 범위를 절반씩 줄인다
- `cum[mid] > r`이면 mid가 답일 수 있으므로 버리지 않는다(`hi = mid`). `mid - 1`로 하면 답을 놓친다

#### 실제 추적 (r = 100,000, 2,450종)
```
 1회: 0~2449 중 mid=1224 ('붐' 누적 1,543,146 > r) → 왼쪽 절반
 2회: 0~1224 중 mid=612  ('런' 누적 1,479,898 > r) → 왼쪽 절반
 ...  범위 2450 → 1225 → 613 → 307 → ... 절반씩
10회: 0~4    중 mid=2    ('이' 누적 150,069 > r)   → 왼쪽
11회: 0~2    중 mid=1    ('하' 누적 124,399 > r)   → 왼쪽 (mid 유지)
12회: 0~1    중 mid=0    ('다' 누적  76,241 <= r)  → 오른쪽
결과: '하'   (76,241 ≤ 100,000 < 124,399), 12회 비교
```
2^12 = 4,096 ≥ 2,450 → 2,450종에서 항상 12번이면 찾는다.


### 3.7 `argmax_index` — 탐욕적 디코딩
- 빈도가 가장 큰 글자를 찾는 단순한 반복문이다. 난수를 쓰지 않으므로 몇 번을 돌려도 "다다다다다다다다다다"가 나온다
- 동률이면 빈도표에서 앞에 있는 글자를 고른다(빈도표는 빈도 내림차순 → 코드포인트 오름차순)

## 4. 역변환 샘플링 — 많이 쓰는가? 최선인가? 옛날에도 이랬나?

### 실제로 많이 쓰는가 → 그렇다, 표준적인 방법이다
- NumPy `random.choice(p=...)`: 누적합(`cumsum`) + `searchsorted`(이진 탐색). **우리 코드와 같은 구조**
- C++ `std::discrete_distribution`: 일반적으로 누적 확률 + 이진 탐색
- PyTorch `torch.multinomial`(LLM의 다음 토큰 샘플링): 기본 원리 동일
- 예외: 일부 대규모 LLM 추론 엔진은 GPU 병렬에 유리한 다른 기법(Gumbel-max 계열)을 쓰기도 한다

### N-gram에서 최선인가 → 상황에 따라 다르다
실제 데이터로 계산한 난수 1개당 비교 횟수:

| 방식 | 비교 횟수 | 준비 | 특징 |
|---|---|---|---|
| 선형 탐색 (최악) | 2,450 | 없음 | 가장 단순 |
| 선형 탐색 (빈도 내림차순) | **평균 163** | 정렬 | 자주 나오는 글자가 앞이라 의외로 빠름 |
| **이진 탐색 (현재 코드)** | **항상 12** | 누적 배열 | 단순함·속도 균형 |
| Alias method | 1 | 표 2개 (복잡) | 같은 분포에서 수없이 뽑을 때 이론상 최고 |

- **유니그램만 보면** alias method가 최고다(분포 하나를 계속 뽑음)
- **바이그램 이상**은 앞 글자마다 분포가 따로 있고 대부분 뒤 글자 후보가 적다(평균 73개) → 빈도순 선형 탐색이 오히려 빠르기도 하다
- **temperature, top-k처럼 매번 분포를 바꾸면** 미리 만든 구조를 재사용할 수 없다 → 매번 누적합 + 탐색이 자연스럽다
- **현실적 결론**: 우리 규모에서는 어느 방식이든 마이크로초 단위다. N-gram의 진짜 병목은 탐색 속도가 아니라 **빈도표 크기(메모리)** 다 (9장)

### 옛날 N-gram도 이렇게 했나
(세부는 원전 확인 권장)
- 원리 자체는 1940년대 몬테카를로 시절부터 있었다
- **샤넌(1948)** 이 글자 빈도표로 영어 근사문을 처음 생성했다. 고차 근사에는 **책을 아무 데나 펼쳐 같은 글자를 찾고 그다음 글자를 적는** 물리적 샘플링을 썼다. 책이 곧 빈도표이자 난수 생성기였다
- 1980~2000년대 N-gram 전성기(음성인식, 번역)에는 주로 **문장의 그럴듯함 점수를 매기는 용도**였다. 생성은 교육용 시연에 가까웠다
