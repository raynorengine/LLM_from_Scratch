## 1. 세는 단위 정하기 — 음절 / 단어 / 자모

"글자"라는 말이 생각보다 애매하다. 글자 `'감'` 하나를 두고 세 가지로 볼 수 있다.

| 단위 | `'감'`의 분해 | 종류 수 |
|---|---|---|
| **음절** (완성형 글자) | `감` 1개 | 11,172 (실사용 2,450) |
| 자모 (초·중·종성) | `ㄱ`, `ㅏ`, `ㅁ` 3개 | 약 67 |
| 단어 | `감` 1개 | 42만 |

### 음절과 단어는 뭐가 다른가

이게 처음에 가장 헷갈렸던 지점이다. `words.txt`는 **1줄 = 1단어**이고, 그 단어가 음절 여러 개로 되어 있다.

```
가가대소하다          ← 1단어
가 가 대 소 하 다     ← 6음절
```

| | 개수 |
|---|---|
| 단어 | 420,309 |
| 음절 | 1,551,565 |

**같은 파일을 42만 번 셀 수도, 155만 번 셀 수도 있다.** 단어당 평균 3.69음절.

### 왜 음절인가 — 결정적인 이유

질문이 "각 **글자**"였으니 음절이 맞지만, 더 중요한 이유가 있다.

**단어 단위로 세면 전부 1이다.** 사전에는 각 표제어가 한 번씩만 실려 있다.

```
가가대소하다 → 1번
힝힝하다     → 1번
... 42만 개 전부 1번
```

빈도를 세는 의미가 없다. 반면 음절로 세면 같은 글자가 여러 단어에 걸쳐 반복되니 **차이가 생긴다**:

```
가가대소하다 → 가 2, 대 1, 소 1, 하 1, 다 1
힝힝하다     → 힝 2, 하 1, 다 1
             ─────────────────────
합계           하 2, 다 2, 가 2, 힝 2, 대 1, 소 1
```

42만 단어를 다 돌면 음절별 빈도 차이가 쌓인다. 그게 우리가 보려던 것이다.

### 자모는 왜 안 쓰나

 `'감'`을 `ㄱ+ㅏ+ㅁ`으로 쪼개는 방식인데:

- 종류가 67개뿐이라 표가 작다 (장점)
- 하지만 유니코드에서 `'감'`은 **애초에 한 글자로 저장**돼 있어서 쪼개려면 별도 작업이 필요하다
- 생성할 때 불가능한 조합이 나올 수 있다

음절은 문자열을 그냥 한 칸씩 읽으면 끝난다. 그게 실무적 이유다.

## 3. 유니그램 ≠ 음절 (확실히 구분할 것)

*"유니그램을 하려면 음절 단위로 해야 하는 건가?"* — 아니다. **별개의 두 선택이다.**

**유니그램(1-gram)은 "앞을 안 보고 하나씩 센다"는 뜻**이다. 세는 단위는 정해주지 않는다. "그램(gram)"이 뭔지는 내가 정한다.

| 그램을 뭐로 정하나 | 유니그램이 세는 것 |
|---|---|
| 음절 | `가`, `감`, `다` 각각의 빈도 |
| 단어 | `가가대소하다` 각각의 빈도 |
| 자모 | `ㄱ`, `ㅏ`, `ㅁ` 각각의 빈도 |

전부 똑같이 유니그램이다. "앞을 안 본다"는 성질이 같으니까.

> **정리**: "유니그램이니까 음절"이 아니라, **"사전 데이터니까 음절"** 이다.
> 소설 같은 문장 데이터라면 단어 단위 유니그램도 의미가 있다 (같은 단어가 여러 번 나오므로).

## 4. 횟수 → 확률 — 여기부터가 언어모델

빠뜨리기 쉬운데, 이게 질문의 핵심이다.

**`'다'`가 76,241번 나왔다는 숫자는 그 자체로 의미가 없다.** 데이터를 2배로 늘리면 15만이 된다. **데이터 크기에 의존하는 값은 비교에 쓸 수 없다.**

그래서 전체 글자수로 나눠 **정규화**한다.

```
P(c) = count(c) / 전체_글자수

P(다) = 76,241 / 1,551,565 = 4.91%
```

이렇게 하면 세 가지가 생긴다.

1. 모든 확률의 합이 **1** → 이게 "확률분포"다
2. 데이터 크기와 무관하게 **다른 코퍼스와 비교 가능**
3. **곧바로 샘플링에 쓸 수 있다**

### 가장 중요한 깨달음

> **"빈도를 세는 작업"과 "언어모델을 만드는 작업"이 같은 일이다.**

확률표가 곧 모델이다. 신경망처럼 "학습"하는 별도 과정이 없다. 세는 게 학습이다.

나중에 트랜스포머를 배울 때, 그건 **이 표를 행렬 연산으로 대체하는 이야기**가 된다. 하는 일(다음 토큰의 확률분포 내놓기)은 똑같다.

## 5. 한글과 유니코드 — 배열 하나로 끝내는 이유

### 11,172이라는 숫자의 정체

```
초성 19 × 중성 21 × 종성 28 = 11,172
```

유니코드는 한글의 **조합 가능한 모든 음절**을 `'가'`(U+AC00)부터 `'힣'`(U+D7A3)까지 **번호를 연속으로** 할당해놨다.

### 그래서 해시테이블이 필요 없다

번호가 연속이므로 이렇게 할 수 있다:

```c
인덱스 = 코드포인트 - 0xAC00     /* 0 ~ 11,171 */
count[인덱스]++;
```

`long long count[11172]` 배열 **하나가 전부**다.

| | 배열 | 해시테이블 |
|---|---|---|
| 해시 함수 | 불필요 | 필요 |
| 충돌 처리 | 불필요 | 필요 |
| 동적 확장 | 불필요 | 필요 |
| 메모리 | 89KB 고정 | 등장한 것만 |
| 조회 속도 | 산술 1회 | 해시 계산 + 탐색 |

> **주의 — 내가 실제로 헷갈렸던 부분**
> Claude가 브리핑에서 "배열 vs 해시테이블" 두 선택지를 나란히 설명한 뒤 배열로 구현했는데, 설명이 해시테이블을 쓴 것처럼 읽혔다. 내가 *"해시테이블을 어디에 썼어?"* 라고 물어서야 "안 썼다, 배열이다"가 나왔다.
>
> **교훈: AI의 설명과 실제 코드가 다를 수 있다.** 설명을 들었다고 코드를 이해한 게 아니다. 자료구조·알고리즘 같은 핵심은 **"그래서 코드 어디에 있어?"** 로 확인해야 한다.

## 6. C에서 한글 다루기 — 파이썬이 숨겨줬던 것

### UTF-8은 글자마다 길이가 다르다

파이썬에서는 `for c in word`면 한 글자씩 나온다. **C는 안 그렇다.**

```
'다'  →  ED 8B A4   (3바이트)
```

C의 `char`는 1바이트라서 그냥 읽으면 `'다'` 하나가 **세 조각으로 쪼개진다.**

### 해결 — 선두 바이트가 길이를 알려준다

UTF-8은 첫 바이트의 비트 패턴에 길이 정보를 심어놨다.

| 선두 바이트 | 길이 | 내용 |
|---|---|---|
| `0xxxxxxx` | 1바이트 | ASCII (개행 포함) |
| `110xxxxx` | 2바이트 | |
| **`1110xxxx`** | **3바이트** | **한글이 여기** |
| `11110xxx` | 4바이트 | 이모지 등 |
| `10xxxxxx` | — | **이어지는 바이트.** 선두가 될 수 없다 |

그래서 절차는: **선두 바이트로 길이 판단 → 그만큼 묶어서 → 코드포인트로 변환.**

```c
cp = 선두바이트의_유효비트;
for (i = 1; i < len; i++)
    cp = (cp << 6) | (p[i] & 0x3F);   /* 이어지는 바이트는 6비트씩 */
```

### 한글 출력이 깨지는 함정 — 서로 다른 두 문제

C에서 한글을 출력하려 할 때 **두 군데서 깨진다. 하나만 고치면 여전히 깨진다.**

| 문제 | 증상 | 해결 |
|---|---|---|
| 콘솔 코드페이지 | 실행 결과가 깨짐 | `SetConsoleOutputCP(CP_UTF8)` |
| 컴파일러 소스 해석 | **소스에 쓴 한글 문자열**이 깨짐 | `cl /utf-8` 옵션 |

### 그리고 파일은 반드시 바이너리 모드로

```c
fopen(path, "rb")   /* "r"이 아니라 "rb" */
```

Windows에서 텍스트 모드로 열면 **개행을 자동 변환**한다. 개행 수를 정확히 세야 하는 지금 상황에서는 치명적이다.

## 7. 데이터를 먼저 의심하기

이번에 가장 실용적으로 배운 부분이다. **코드를 짜기 전에 데이터를 확인해야 한다.**

### 사례 1 — "150만 vs 190만" 숫자 불일치

`docs/01_N-Gram.md`는 155만, 강의는 197만이라고 했다. 불일치처럼 보였지만 **둘 다 맞았다.**

```
1,551,565 (글자)  +  420,309 (개행 \n)  =  1,971,874 (파일 문자수)
```

단어가 42만 개 → **줄바꿈도 42만 개**. 그게 더해진 것이다.

| | 값 | 용도 |
|---|---|---|
| 글자 수 (개행 제외) | 1,551,565 | **확률 계산에 쓰는 값** |
| 파일 문자 수 (개행 포함) | 1,971,874 | 파일 크기 감각 |

**개행을 글자로 세면 `다`의 확률이 4.91% → 3.87%로 틀어진다.** 그래서 프로그램이 개행을 **별도 카운터로 출력**하게 만들었다. 4.91%가 안 나오면 범인을 바로 알 수 있도록.

> **교훈**: 숫자가 안 맞을 때 "데이터가 잘못됐나?"보다 **"두 숫자가 각각 무엇을 세고 있나?"** 를 먼저 물어야 한다. 대개 정의가 다른 것이다.

### 사례 2 — 배열 인덱싱의 조용한 지뢰

`count[cp - 0xAC00]` 방식은 **한글이 아닌 문자가 섞이면 배열 범위를 벗어나 메모리를 깨뜨린다.** C에서 조용히 터지는 종류의 버그다. 숫자 하나, 영문 하나만 섞여도 그렇다.

그래서 **구현 전에 데이터를 검사**했다:

```
코드포인트 범위 : 0xAC00 ~ 0xD79D   (전부 한글 음절 안)
비한글 문자     : 0종
```

안전 확인 후 진행했고, 그래도 코드에 `범위 외 문자` 카운터를 남겨뒀다 (방어적 프로그래밍).

> **교훈**: "데이터가 깨끗할 것이다"는 가정이 아니라 **확인 대상**이다. 특히 C처럼 안전망이 없는 언어에서는 확인이 곧 생존이다.

## 8. 검증 — 가짜 검증을 피하는 방법

### 가짜 검증이란

결과를 이미 알고 있으니, 그 값을 코드에 박아놓고 통과한 척하는 것.

```python
# 절대 금지
print("전체 글자수 1,551,565 정확합니다")

# 이것도 금지 — 기대값 상수와 자기 자신을 비교
expected = 1551565
print("통과" if expected == 1551565 else "실패")
```

이런 프로그램은 **무엇을 넣어도 통과한다.** 검증이 아니라 장식이다.

### 진짜 검증의 5원칙

| 원칙 | 왜 |
|---|---|
| **1. 독립 재계산** | 원본 데이터에서 처음부터 다시 계산. 검증 대상의 출력을 받아쓰지 않는다 |
| **2. 다른 구현으로 교차검증** | C를 검증하려면 Python으로. 같은 로직을 복사하면 **같은 버그를 함께 가진다** |
| **3. 전수 비교** | 상위 10개가 아니라 2,450종 전부 |
| **4. 실패할 수 있어야 한다** | 틀린 입력에 FAIL이 나오는지 **직접 확인** |
| **5. 종료 코드** | 성공 0 / 실패 1 → 자동 확인 가능 |

### 4번이 핵심 — 검증기를 검증한다

`verify.py --self-test`는 결과 파일을 **일부러 망가뜨려서** 돌린다.

| 변조 케이스 | 결과 |
|---|---|
| 1위 글자 빈도를 +1 | 종료코드 1 → FAIL 감지 ✅ |
| 헤더 `total_chars`를 9999999로 | 종료코드 1 → FAIL 감지 ✅ |
| 마지막 행 삭제 | 종료코드 1 → FAIL 감지 ✅ |
| 1위와 6위 행 교체 (정렬 깨기) | 종료코드 1 → FAIL 감지 ✅ |
| **변조 없는 원본** | 종료코드 0 → 통과 ✅ |

변조된 것은 전부 잡고, 정상인 것만 통과했다. **이제 이 검증기가 가짜가 아님을 알 수 있다.**

> **교훈**: "검증 통과했습니다"는 그 자체로 아무 보장이 아니다. **그 검증기가 실패할 능력이 있는지**를 물어야 한다. AI에게 검증을 맡길 때 특히 그렇다.

## 9. 결과 읽기 — `'다'`가 1등인 이유

```
다(4.91%) > 하(3.10%) > 이 > 기 > 리 > 지 > 사 > 자 > 대 > 수(0.88%)
```

### 우연이 아니다

사전 표제어를 보면 답이 나온다.

```
가가대소하다, 힝힝거리다, 힝힝대다, 힝힝하다, ...
```

**국어사전의 모든 동사·형용사 표제어가 기본형, 즉 `'-다'`로 끝난다.** 그래서 `'다'`는 동사·형용사 개수만큼 거의 확정적으로 등장한다. 2위 `'하'`도 같은 이유다 — `'~하다'` 꼴이 엄청나게 많으니까.

### 교훈 1: 이건 "한국어의 글자 빈도"가 아니다

**"국립국어원 표준국어대사전 표제어의 글자 빈도"** 다.

실제 사람이 쓴 문장을 세면 `'이'`, `'는'`, `'을'` 같은 **조사 글자**가 올라온다. 사전에는 조사가 거의 안 실리니까.

> **어떤 데이터로 표를 만들었는지가 모델의 성격을 결정한다.**

이건 최신 LLM까지 그대로 적용되는 원리다. 학습 데이터가 모델의 편향을 만든다. 같은 코드로 소설 코퍼스를 돌리면 완전히 다른 표가 나온다.

### 교훈 2: 긴 단어가 자동으로 더 큰 가중치를 받는다

글자 단위로 세면 `'가'`(1자)보다 `'가가대소하다'`(6자)가 **6배 기여**한다. 의도한 것인지 아닌지는 목적에 따라 다르다. 단어마다 동등한 가중을 주려면 단어별로 정규화해야 한다.

---

## 10. 배열의 78%가 비어 있다 — 데이터 희소성의 예고편

`'힣'`이 결과에 없는 걸 발견하고 확인해봤다. **0번 등장**이었다.

| | 개수 | 비율 |
|---|---|---|
| 조합 가능한 음절 | 11,172 | 100% |
| **사전에 실제 등장** | **2,450** | **21.9%** |
| 한 번도 안 나옴 | 8,722 | 78.1% |

유니코드는 "쓰이는 글자"가 아니라 **"만들 수 있는 글자"** 를 전부 할당해둔 것이다.

### `ㅎ+ㅣ+종성` 28글자 중 8개만 쓰인다

```
히  3,250     힊  0     힍  0     힑~힗  0
힘    279     힋  0     힎  0     힚     0
힐    157     힜  0     힏  0     힞~힣  0
힌     60
힝     24
힙      3
힉      2
힛      1
```

`힣`은 그 20개 중 하나다. 특별한 게 아니라 **그냥 안 쓰는 글자**다.

### 왜 이게 중요한가

**빈도 0 → 확률 0 → 영원히 생성 불가.**

글자 하나 수준에서는 사소하다. 하지만 **"앞 2글자를 보고 다음을 예측"하는 단계로 가면 조합의 수가 폭발하면서 0인 칸이 대부분이 된다.**

```
글자 1개  : 11,172 칸          → 2,450 사용 (21.9%)
글자 2개  : 11,172² = 1.2억 칸  → 극히 일부만 사용
글자 3개  : 11,172³ = 1.4조 칸  → ...
```

이게 **데이터 희소성(data sparsity)** 문제이고, N-gram의 근본 한계다. **지금 이 78%가 그 예고편이다.**

---

## 11. 왜 이걸로는 문장을 못 만드나 — 다음 단계의 동기

빈도표가 완성되면 자연스럽게 "이걸로 글자를 뽑아보자"가 된다. 두 가지 방법이 있다.

| 방법 | 결과 |
|---|---|
| 항상 최고 확률 글자 선택 (**탐욕적**) | `"다다다다다..."` |
| 확률 분포대로 랜덤 선택 (**확률적 샘플링**) | `"다는하다"` |

**둘 다 실패한다.** 유니그램은 **앞 글자를 전혀 안 보기** 때문이다. 글자를 독립적으로 뽑으니 `'다'` 다음에 `'다'`가 나오는 걸 막을 방법이 없다.

> **유니그램의 가치는 결과물이 아니라, 왜 컨텍스트가 필요한지를 실패로 증명하는 것이다.**

그래서 "앞 글자를 하나만 보면 어떨까?"가 다음 질문이 되고, 그게 **바이그램**이다.

## 12. AI와 작업하는 법 — 오늘 실제로 배운 것

기술 내용보다 이게 더 오래 남을 것 같아서 따로 정리한다.

### 내가 AI에게 걸었던 제동들

| 상황 | 내가 한 말 | 왜 유효했나 |
|---|---|---|
| 설명이 너무 멀리 나감 | "너무 앞서가진 말자" | AI는 설명을 아끼지 않는다. **범위 설정은 내 일** |
| 파일명이 내용과 안 맞음 | "이 프로그램은 빈도 계산인데 왜 `unigram.c`야?" | 이름이 틀리면 나중에 내가 헷갈린다 |
| 설명과 코드가 다름 | "해시테이블을 어디에 썼어?" | **설명을 들은 게 코드를 이해한 게 아니다** |
| 검증이 못 미더움 | "가짜 검증 프로그램 짜지 마" | AI는 "통과했습니다"를 쉽게 말한다 |
| 작업이 계속 멈춤 | "오래 걸릴 것 같으면 미리 말하고 승인받아" | 2분 타임아웃을 두 번 먹고 나서 규칙화 |
| 기록이 부실함 | "시행착오는 안 적어도 되는 건가?" | 결과만 남으면 **왜 그렇게 됐는지가 사라진다** |

### 패턴: AI는 "그럴듯한 완결"을 선호한다

여섯 건 모두 공통점이 있다. AI는 **매끄럽게 끝난 것처럼 보이는 상태**를 만들려 한다. 그래서:

- 설명을 끝까지 다 해버리고 (내가 소화 못 할 양)
- 이름을 대충 붙이고 (돌아가니까)
- "검증 통과"라고 말하고 (실제로 실패할 수 있는지는 확인 안 하고)
- 결과만 기록한다 (과정은 지나간 일이니까)

**내가 할 일은 그 매끄러움을 의심하는 것이다.** 특히:

1. **"그래서 코드 어디에?"** — 설명과 구현의 일치 확인
2. **"이 검증은 실패할 수 있어?"** — 검증의 진위 확인
3. **"왜 그렇게 했어?"** — 결정의 근거 확인
4. **"지금 내가 이해했어?"** — 진도보다 소화가 먼저

### 기록 체계도 같은 원리

오늘 `PROGRESS.md`와 `devlog/`의 역할을 분리했다.

| | `PROGRESS.md` | `devlog/` |
|---|---|---|
| 질문 | **"지금 어디까지 됐나"** | **"왜 그렇게 됐나"** |
| 방식 | 덮어쓰기 | append (보존) |
| 갱신 | 하루 한 번 | 그때그때 |

이유는 **손실의 비대칭성**이다. `PROGRESS.md`가 낡는 건 devlog에서 복구할 수 있지만, devlog를 놓친 시행착오는 **영구 소실**이다. 그래서 복구 불가한 쪽만 즉시 쓴다.

그리고 **education/(이 문서)은 또 다른 층**이다. devlog는 "무슨 일이 있었나"의 기록이고, 이 문서는 **"그래서 내가 뭘 배웠나"** 의 정리다. 대화는 흘러가지만 이건 남는다.

## 13. 복습용 핵심 정리

### 개념

- **유니그램 = "앞을 안 보고 하나씩 센다".** 세는 단위(음절/단어/자모)는 별개로 고르는 것
- **사전 데이터에서는 음절이 유일한 선택** — 단어 단위로 세면 전부 1이라 정보가 없다
- **빈도 → 확률 정규화가 모델의 시작.** 횟수는 데이터 크기에 의존해서 비교 불가
- **빈도표가 곧 모델이다.** 별도의 "학습" 과정이 없다. 세는 게 학습
- **데이터가 모델의 성격을 결정한다.** `'다'` 1등은 한국어의 성질이 아니라 사전 표제어의 성질

### 한글/유니코드

- 한글 음절은 `U+AC00`~`U+D7A3`에 **연속** 할당 → `cp - 0xAC00`이 곧 배열 인덱스
- `초성 19 × 중성 21 × 종성 28 = 11,172`, 그중 사전 사용은 **2,450종(21.9%)**
- 한글 1음절 = UTF-8 **3바이트**. 선두 바이트 비트 패턴으로 길이를 판단해 묶어야 한다

### C 실무 함정 (반복해서 만날 것들)

1. 개행(`\n`)을 글자로 세지 말 것 → 4.91%가 3.87%로 틀어진다
2. `SetConsoleOutputCP(CP_UTF8)` — 콘솔 출력 깨짐 방지
3. `cl /utf-8` — 소스의 한글 문자열 리터럴 깨짐 방지 (**2번과 별개 문제**)
4. `fopen(..., "rb")` — 텍스트 모드는 Windows에서 개행을 변환
5. 배열 인덱싱 전에 **데이터 범위를 검사** — 범위 밖 값이 들어오면 메모리가 깨진다

### 검증

- **독립 재계산 / 다른 구현 / 전수 비교 / 실패 가능 / 종료코드** 5원칙
- 기대값을 코드에 박고 통과한 척하면 **가짜 검증**
- 검증기 자체를 검증하려면 **일부러 틀린 입력을 넣어 FAIL이 나오는지 본다**
