# 트라이그램 — 앞 두 글자를 보고 다음 글자를 뽑기

## 복습용 핵심 정리

> **한 줄 요약**: 트라이그램은 바이그램의 문맥을 1글자에서 **2글자**로 늘린 것이다. 확률표가 "앞 글자별"에서 "앞 두 글자 쌍별"(16.9만 개)로 늘어나고, 그 덕분에 "이 글자가 단어의 몇 번째인가"를 알게 되어 **사전 일치율이 41.7% → 57.3%** 로 올랐다. 구현에서 달라진 것은 **BOS 2개, 3그램 키(64비트), 문맥 창 밀기** 세 가지뿐이다. 그리고 n을 계속 키우면 사전을 외우는 **과적합**이 된다.

### 개념
- **P(c | a, b) = count(a, b, c) / count(a, b, ·)** — 앞 2글자 (a, b)를 문맥으로 쓰는 n=3인 N-그램
- 단어 앞에 **BOS 2개**, 뒤에 **EOS 1개**를 붙인다. 길이 L 단어 → 3그램 **L+1개** (바이그램과 같은 개수)
- 확률표 = 문맥 (앞1, 앞2)마다 하나 → 바이그램 2,451개 → **169,589개**
- 서로 다른 3그램 **654,039개** (바이그램 171,425개), 3그램 총 개수는 1,971,874로 같다
- **3차원 배열은 불가능** (2,452³ ≈ 147억 칸 ≈ **59GB**). 해시테이블 + CSR로 실제로 나온 65만 개만 저장한다
- 해시 키가 커진다: 최대 약 147억 > 2³² → **`int` 키로는 넘친다. 64비트 키가 필요하다**
- 탐욕적 디코딩: 바이그램 **"사"** → 트라이그램 **"사회"**. 문맥 (BOS, 사)가 "첫 글자 '사'"임을 알려 줘서 바로 끝나지 않는다

### 바이그램 vs 트라이그램 (실측, 같은 seed 1792592635, 각 1,000개)
| | 바이그램 | 트라이그램 |
|---|---|---|
| 사전 일치율 | 41.7% (417개) | **57.3%** (573개) |
| 1글자를 뺀 일치율 | 24.6% | **57.2%** |
| 1글자 단어 생성 수 | **227개** (사전 비율 0.32%) | 2개 |
| 3글자 일치율 | 10.7% | **62.7%** |
| 서로 다른 n그램 / 문맥 | 171,425 / 2,451 | 654,039 / 169,589 |
| 학습 시간 / 생성 메모리 | 약 36ms / 1.40MB | 약 133ms / 7.27MB |

### n을 키우면 (과적합)
- 평균 단어 길이는 3.69글자. n이 단어 길이에 가까워지면 문맥이 **단어 전체**를 덮어서 사전을 그대로 외운다
- 다음 글자 선택지가 **1개뿐인 문맥**의 비율: n=2 17.9% → n=3 49.7% → n=4 79.8% → n=6 85.2%
- 일치율이 높다고 좋은 모델이 아니다. **사전에 없지만 그럴듯한 단어**를 만들 수 있어야 한다

## 1. 트라이그램이란

### 바이그램의 한계에서 출발
바이그램은 앞 1글자만 본다. 그래서 같은 글자 '사'를 **첫 글자일 때와 끝 글자일 때 구별하지 못한다.**

- 바이그램에서 P(EOS | 사) = **25.8%** ('변호사', '의사'처럼 '사'로 끝나는 단어가 많아서)
- 이 값이 단어의 **첫 글자 '사'** 에도 똑같이 적용되어, '사' 다음에 단어가 바로 끝나 **1글자 단어**가 된다
- 그 결과 생성 1,000개 중 1글자 단어가 **227개**. 사전에서 1글자 단어는 0.32%(3개 정도)뿐이다

트라이그램은 문맥이 (BOS, 사)이면 "단어 첫머리의 사"라는 것을 안다.
- 사전에서 '사'로 시작하는 단어 4,614개 중 '사' 한 글자로 끝나는 것은 **1개**
- P(EOS | BOS, 사) = 1/4,614 = **0.02%**

### 확률 계산과 슬라이딩 윈도우
3글자 창을 한 칸씩 민다. 문맥이 2글자라서 단어 시작에 **BOS가 2개** 필요하다.

```
"나비"  →  [BOS BOS 나 비 EOS]
3그램    →  (BOS,BOS,나)  (BOS,나,비)  (나,비,EOS)
```

- **BOS가 2개인 이유**: 첫 글자를 뽑을 때도 문맥이 2글자여야 한다. (BOS, BOS)가 곧 "단어 첫 글자를 고르는 자리"다
- **EOS가 1개면 충분한 이유**: EOS가 뽑히면 생성이 끝나서 그 뒤의 문맥은 필요 없다
- 단어 사이에 걸친 3그램은 **세지 않는다**. `(비, EOS, BOS)`, `(EOS, BOS, BOS)`는 실제 문맥이 아니다

### 발견: (BOS, BOS) 행 = 바이그램의 BOS 행
강의 표의 `(BOS,BOS) → 사 4,614 / 가 4,448 / 자 4,105`는 바이그램의 `BOS → 사 4,614 ...`와 **같은 값**이다. BOS 2개든 1개든 "단어 첫 글자 분포"라는 같은 정보이기 때문이다. 트라이그램 빈도표의 맨 위 줄이 이 값이다.

### 규모
| | 바이그램 | 트라이그램 |
|---|---|---|
| 3그램(쌍) 총 개수 | 1,971,874 | 1,971,874 (같음) |
| 서로 다른 n그램 | 171,425 | **654,039** |
| 서로 다른 문맥 | 2,451 | **169,589** |

- 총 개수가 같은 이유: 길이 L 단어에서 둘 다 L+1개가 나온다
- 서로 다른 것이 3.8배로 늘어난다 → 같은 사전 데이터가 더 잘게 쪼개진다

## 2. 저장 구조 — 3차원 배열이 안 되는 이유와 64비트 키

### 2.1 Q. 3차원 배열 대신 그냥 해시테이블을 쓰면 되는 것 아닌가? (사용자 질문)
**맞다. 해시테이블을 쓴다.** 브리핑에서 두 가지 이야기를 한 문장에 섞어 써서 헷갈리게 했다. 따로 보면 이렇다.

| | 무엇의 문제인가 | 해결 |
|---|---|---|
| **59GB** | **배열**을 쓸 수 없는 이유 | 해시테이블을 쓴다 (질문하신 내용과 같음) |
| **64비트 키** | 해시테이블 **안에 키를 어떤 타입으로 담느냐** | 키 타입을 `int` → `unsigned long long` |

해시테이블에 넣으려면 3글자 (앞1, 앞2, 다음)를 **정수 하나로** 만들어야 한다.

| | 키 공식 | 최댓값 | `int`(최대 약 21억)에 |
|---|---|---|---|
| 바이그램 | `앞 × 2452 + 다음` | 2452² ≈ 600만 | 들어감 |
| 트라이그램 | `(앞1 × 2452 + 앞2) × 2452 + 다음` | 2452³ ≈ **147억** | **안 들어감** |

- Step3 해시 함수는 키를 `int`로 받는다. 그대로 복사하면 147억이 **잘려서 엉뚱한 값**이 되고, 서로 다른 3그램이 **같은 키로 합쳐질 수 있다.** 오류 메시지도 나지 않는다 (조용히 틀린다)
- 해결은 키 타입을 64비트로 바꾸는 것뿐이다. 곱하기 전에 64비트로 바꾸는 것도 중요하다. `int`끼리 곱하면 결과를 64비트에 담기 전에 `int` 범위에서 먼저 넘친다

```c
/* 곱하기 전에 64비트로 바꾼다. int끼리 곱하면 int 범위에서 먼저 넘친다 */
key = ((unsigned long long)g_seq[i] * V + (unsigned long long)g_seq[i + 1]) * V
    + (unsigned long long)g_seq[i + 2];
```

### 2.2 해시테이블 크기와 해시 함수
- 서로 다른 3그램 654,039개. 칸 수를 2²⁰(1,048,576)로 하면 적재율 **62%**, 2²¹(2,097,152)로 하면 **31%**
  - 선형 탐사는 칸이 많이 차면 빈 칸까지 멀리 가야 해서 느려진다 → 2²¹칸을 골랐다
- 해시 함수는 피보나치 해싱을 64비트로 키웠다: `(key × 11400714819323198485) >> (64 − bits)`
  - 11400714819323198485 = 2⁶⁴ ÷ 황금비. Step3의 `2654435761`(= 2³² ÷ 황금비)의 64비트판
  - 곱셈이 키의 모든 비트를 섞어 위쪽으로 올리므로, 위쪽 `bits`개 비트를 칸 번호로 쓰면 규칙적인 키도 고르게 흩어진다
- 빈 칸 표시는 `HT_EMPTY` = 64비트 최댓값. 0은 `(가,가,가)`의 키라서 쓸 수 없다

### 2.3 문맥 찾기 — 왜 이진 탐색인가
바이그램(Step3 ③)은 행 번호(= 앞 글자 번호)로 `row_start[앞]`을 바로 찾았다. 트라이그램은 문맥이 (앞1, 앞2)라서 **그렇게 하면 2452² ≈ 601만 칸짜리 `row_start`가 필요한데, 실제 문맥은 169,589개뿐이라 97%가 빈 칸**이다. 그래서 다르게 한다.

```
g_ctx_key   = [(가,가), (가,대), ...]     실제로 나온 문맥 키만, 오름차순  (169,589개)
g_ctx_start = [0, 2, 3, ...]             문맥 i의 후보 구간 = [start[i], start[i+1])
g_next_id   = [대, 소, 소, ...]           후보 글자 번호
g_cum       = [3, 4, 2, ...]             문맥 구간 안 누적 빈도 (문맥마다 0부터 다시)
```

뽑는 과정은 **이진 탐색 두 번**이다.
1. `g_ctx_key`에서 문맥을 찾는다 → 문맥 번호 `ci` (최대 18번 비교, 2¹⁸ = 262,144 ≥ 169,589)
2. `ci`의 구간에서 `g_cum`을 이진 탐색해 "누적 > r"인 첫 위치를 찾는다 (Step3 ③과 같음)

**바이그램 파일도 같은 방식(문맥 키 이진 탐색)으로 만든 이유**: 두 파일을 나란히 놓고 비교(diff)했을 때 **n이 달라서 생긴 차이만 보이게** 하려고, 그리고 시간·메모리를 비교할 때 자료구조 차이가 아니라 n 차이만 남기려고. (사용자 결정: 트라이그램은 해시+CSR, 바이그램도 같은 구성의 단일 파일)

### 2.4 메모리 (CSR만 남는다)
세기용 해시테이블은 CSR로 옮긴 뒤 해제한다. 생성 단계에서 남는 것:

| | 계산 | 바이트 |
|---|---|---|
| 바이그램 | 171,425 × 8 + 2,451 × 8 + 2,452 × 4 | 1,400,816 (1.40MB) |
| 트라이그램 | 654,039 × 8 + 169,589 × 8 + 169,590 × 4 | 7,267,384 (7.27MB) |

(8바이트 = 후보 번호 4 + 누적 빈도 4. 문맥 키 8, 문맥 시작 4)

## 3. 구현에서 달라진 부분 (바이그램 ↔ 트라이그램, 파일 `step4_bigram.c` ↔ `step4_trigram.c`)

주석을 빼고 diff하면 남는 차이는 아래뿐이다.

| 구역 | 바이그램 | 트라이그램 |
|---|---|---|
| seq 만들기 | 단어마다 앞에 BOS 1개 | BOS **2개** |
| 세기 | 키 = 앞 × V + 다음 | 키 = (앞1 × V + 앞2) × V + 다음, 경계 건너뛰기 조건 2개 |
| 문맥 키 (`make_ctx`) | `prev` | `prev1 × V + prev2` |
| 생성 | `prev = next` | `prev1 = prev2; prev2 = next` |
| 빈도표·검증 모드 | 열 3개 | `split_ctx`로 문맥을 둘로 쪼개 열 1개 추가 |
| 해시 크기 | 2¹⁹칸 | 2²¹칸 |

### 3.1 seq 만들기 — BOS 2개
```
cps = [나 비 -1 사 -1]
seq = [BOS BOS 나 비 EOS BOS BOS 사 EOS]
```
seq 길이 = 글자 수 + 단어 수 × 3 (바이그램은 × 2).

### 3.2 세기 — 단어 경계를 건너뛰는 조건
```c
for (i = 0; i + 2 < g_seq_n; i++) {
    if (g_seq[i] == g_eos || g_seq[i + 1] == g_eos) {
        continue;   /* (?, EOS, BOS) / (EOS, BOS, BOS): 단어 사이에 걸친 3그램 */
    }
    ...
}
```
- 바이그램은 `seq[i] == EOS`만 건너뛰면 됐다 (EOS 다음이 다른 단어의 BOS)
- 트라이그램은 창에 EOS가 **첫째 칸이나 둘째 칸**에 있으면 건너뛴다. EOS가 셋째 칸이면 `(나, 비, EOS)`처럼 정상 3그램이다

### 3.3 생성 — 문맥 창을 한 칸 민다
```
(BOS,BOS) → 사        단어 "사"
(BOS,사)  → 회
(사,회)   → EOS        → "사회"
```
```c
prev1 = prev2;   /* 가장 오래된 글자가 빠지고 */
prev2 = next;    /* 새 글자가 들어온다 */
```
뽑을 때 문맥을 못 찾는 일은 생기지 않는다. 문맥 (p, c)에 도달했다면 그 3그램 (?, p, c)가 사전 어떤 단어에 있었고, c가 EOS가 아니라서 그 단어에서 c 뒤에도 글자나 EOS가 있었기 때문이다. 그래도 방어로 검사한다.

### 3.4 단일 파일 + 목차
파일이 하나로 합쳐지면 길어져서 읽기 어렵다(약 1,200줄). 그래서 맨 위에 **구역 번호 / 시작 줄 / 이름 / 주요 함수** 목차를 넣었다. 줄 번호는 코드를 고치면 어긋나기 쉬워서, 검증기가 "목차의 줄 번호 = 실제 구역 머리 줄"을 확인한다 (5절 [7]).

### 4.3 해석
**왜 트라이그램의 일치율이 높은가.** 생성 단어를 3글자씩 잘라 보면 사전 어떤 단어 안에 실제로 있는 비율이 바이그램 **23.9%** (433/1,810), 트라이그램 **100%** (1,710/1,710, 구조상)이다.
- 바이그램은 2글자 조각만 사전에서 온 것이 보장된다. 서로 다른 단어의 2글자 조각을 **겹치는 글자 한 개**에서 이어 붙인 "그럴듯하지만 없는 단어"가 많다
- 트라이그램은 겹치는 부분이 **2글자**로 길어져서, 이어 붙인 결과가 실제 단어와 맞을 가능성이 크다

**왜 2글자 단어는 97%인가.** 트라이그램에서 2글자 단어 `ab`가 나오려면 `(BOS,BOS,a)` `(BOS,a,b)` `(a,b,EOS)`가 모두 사전에 있어야 한다. 즉 'ab로 시작하는 단어'와 'ab로 끝나는 단어'가 둘 다 있어야 해서 사실상 사전 단어만 나온다. 바이그램은 'a로 시작', 'ab', 'b로 끝남'이 따로 있기만 하면 된다.

**왜 길수록 떨어지나.** 문맥이 2글자뿐이라 앞쪽 글자를 잊은 채 이어 붙이므로, 단어가 길어질수록 전체가 한 단어와 맞을 확률이 줄어든다. 트라이그램도 8글자 이상은 0%다.

### 4.4 실제 단어 (seed 1792592635, 처음 15개)
```
바이그램:   구년하다  증*  선이*  찬*  청산화하다  다*  목*  잠병덕  대하멱  단저울꼬장맥
            유*  노랫구지집누비임진드루  초례*  원뿔같다  개찬하다*          (* = 사전에 있음)
트라이그램: 구조*  장학지의  빈모강*  청줄*  법왕자서  목봉색*  정명제  수치현도드락하식
            유찬하다*  전쟁*  농업부  일산대  기리병  굴치다  로열박이다
```
- 바이그램: 1글자(증, 찬, 다, 목, 유)가 눈에 띄게 많고, 긴 단어는 조각을 이어 붙인 모양이다 (노랫구지집누비임진드루)
- 트라이그램: 1글자가 거의 없고 `농업부`, `일산대`, `기리병`처럼 **사전에 없지만 한국어 같은** 단어가 나온다. 강의가 말한 "좋은 언어 모델"의 모습이다

### 4.5 탐욕적 디코딩: "사" → "사회"
- 바이그램: BOS → 사(4,614) → **EOS**(4,539) → 단어 "사"
- 트라이그램: (BOS,BOS) → 사 → (BOS,사) → **회**(308회, 1위) → (사,회) → EOS → 단어 "사회"
- 문맥 (BOS, 사)에서는 EOS가 4,614번 중 1번뿐이라 1위가 되지 못한다. 바이그램의 "사만 반복" 문제가 문맥 하나로 풀린다

### 4.6 시간과 메모리
| | 바이그램 | 트라이그램 |
|---|---|---|
| 학습 (세기 + CSR) | 약 36ms | 약 133ms |
| 1,000개 생성 | 약 1.1ms | 약 1.7ms |
| 생성 메모리 | 1.40MB | 7.27MB |
| 빈도표 파일 | 3.3MB | 15.5MB |

학습이 3.7배 느린 이유는 서로 다른 키가 3.8배 많아서 정렬할 양이 늘었기 때문이다. 생성은 이진 탐색이라 문맥이 69배(2,451 → 169,589개) 많아져도 시간 차이가 1ms 안팎이다.

## 5. 검증 (`step4_verify.py`)

### 5.1 독립성
- 기준값을 전부 `words.txt`에서 Python으로 **처음부터 다시** 센다 (튜플을 키로 쓰는 Counter). C의 출력을 기준으로 쓰지 않는다
- C는 해시 + CSR + 이진 탐색, Python은 딕셔너리와 직접 나열 — **다른 방식**이다
- [2]의 기준은 "n그램을 더한 값"이 아니라 "문맥이 나온 횟수"를 **따로** 센 값이다 (같은 쌍 세기 버그를 기준값까지 공유하지 않으려고)
- C가 결과 파일 헤더에 쓴 일치율은 믿지 않고, 단어 목록을 `words.txt`와 대조해 다시 센다

### 5.2 검사 항목 (바이그램·트라이그램 각각)
| 번호 | 확인 | 방법 |
|---|---|---|
| [1] | n그램 빈도 전수 (171,425 / 654,039개) | `--dump` 출력과 Python 재계산을 전부 비교 |
| [2] | 문맥 합계 | `--rows` vs 다른 방법으로 센 값 |
| [3] | r → 글자 대응 | 모든 후보 구간의 **시작·끝 r**(바이그램 34만 개 / 트라이그램 131만 개) + 무작위 1만 개 |
| [4] | 뽑기 분포 | 문맥 3개에서 10만 번 뽑아 **카이제곱 검정** (p ≥ 0.001) |
| [5] | 결과 파일 | 탐욕적 단어, 모든 단어의 n그램이 사전에 실재, `*` 표시, 일치율·길이별 수치 재계산 |
| [6] | 빈도표 | 형식·순서·확률 + **프로그램이 지금 만드는 표와 바이트 단위로 같은가** |
| [7] | 목차·주석 | 목차 줄 번호 = 구역 머리, 모든 구역에 `[목적][동작][이유]` |

### 5.3 [3]이 구간 경계를 보는 이유
뽑기의 이진 탐색에서 `>` 대신 `>=`를 쓰면 **구간의 끝 r만** 다음 후보로 밀린다. 무작위 r로는 이 버그가 거의 안 잡히므로 모든 구간의 시작·끝을 질의한다. (Step3에서 배운 것을 그대로 적용)

### 5.4 `--self-test` — 검증기가 실패할 수 있는가
망가진 입력 **18가지**를 흉내 내 넣고 전부 FAIL이 나는지 본다. 이번 단계에서 새로 넣은 것:
- **두 3그램이 합쳐짐** (64비트 키가 넘쳤을 때 생길 증상을 흉내) → 빠진 3그램으로 감지
- **단어 경계를 넘어 센 3그램** `(EOS, BOS, BOS)` → 없어야 할 n그램으로 감지
- 일치 수 +1, 3글자 일치율만 조작 → 재계산 값과 달라서 감지
- **목차 줄 번호가 1 어긋남**, 구역 머리 주석에서 `[이유]` 삭제 → 감지
- 복사한 바이그램 빈도표의 **1바이트 변경** → 감지

(키 넘침은 실제로 `int` 키로 돌려 본 것이 아니라 결과를 흉내 낸 입력이다. 이 검증기가 그런 증상을 잡을 수 있다는 확인이다.)

### 5.5 Step3과의 대조
바이그램을 새 구조(문맥 키 이진 탐색)로 옮겼는데도 **같은 seed에서 Step3 ③과 탐욕적 1개 + 생성 1,000개가 모두 같았고, 빈도표도 바이트 단위로 같았다.** 후보 순서(번호 오름차순)와 경계 규칙(누적 > r)이 같으면 자료구조를 바꿔도 결과가 같다는 Step3의 설계가 유지되었다.

## 6. 사용자 질문과 답 (표를 이해하지 못했던 부분)

### Q1. 길이별 사전 일치율은 왜 필요한가? 전체 일치율 하나면 되지 않나?
**전체 일치율만 보면 짧은 단어를 많이 만든 모델이 점수를 쉽게 딴다.** 1글자 단어('가', '나', '사' ...)는 거의 항상 사전에 있어서, 1글자를 많이 만들면 일치율이 저절로 오른다.

| | 바이그램 | 트라이그램 |
|---|---|---|
| 전체 일치 수 | 417개 | 573개 |
| 그중 1글자 단어 | **227개 (54.4%)** | 2개 (0.3%) |
| 전체 일치율 | 41.7% | 57.3% |
| **1글자를 빼고 다시 계산** | 190 / 773 = **24.6%** | 571 / 998 = **57.2%** |

- 바이그램 일치의 **절반 이상**이 1글자 단어에서 나왔다. 1글자를 빼면 24.6%로 떨어진다
- 트라이그램은 1글자를 거의 안 만들어서 빼도 거의 그대로다
- 그래서 실제 실력 차이는 전체 숫자의 +15.6%p가 아니라 **+32.6%p**에 가깝다. 전체 숫자는 이 차이를 가린다
- 비유: 시험에서 쉬운 문제(1글자)와 어려운 문제(3~4글자)의 정답률을 따로 보는 것

### Q2. '생성 단어 길이 분포 vs 사전' 표는 무엇을 보는 표인가?
**"모델이 사전 단어와 비슷한 길이로 단어를 만드는가"** 를 본다.
- 길이별 일치율 표 = **내용**이 사전과 맞나 / 길이 분포 표 = **길이**가 사전과 닮았나
- 사전 단어는 3~4글자가 60.5%이고 1글자는 0.32%뿐인데, 바이그램은 1,000개 중 1글자가 227개, 트라이그램은 2개다
- 두 표는 이어져 있다. 바이그램은 길이 분포가 1글자 쪽으로 치우쳤고(분포 표), 그 1글자가 거의 다 사전 단어라서 전체 일치율이 부풀려졌다(Q1)
- 사전 분포와의 차이(각 길이 비율 차이의 절반 합, 0이면 같은 분포): 바이그램 **33.3%p** / 트라이그램 **12.9%p**

### Q3. 모델이 1,000개를 확률 샘플링한 것처럼, 사전도 1,000개를 샘플링해서 비교한 것인가?
**아니다.** "사전" 칸은 뽑은 것이 아니라 `words.txt` 단어 **420,309개 전부**를 길이별로 센 값이다. 무작위성이 없다.

| 길이 | 사전 단어 수(전체) | 비율 = 개수 ÷ 420,309 | 1,000개로 환산 |
|---|---|---|---|
| 1 | 1,357 | 0.32% | 3.2 |
| 2 | 77,939 | 18.54% | 185.4 |
| 3 | 118,859 | 28.28% | 282.8 |
| 4 | 135,548 | 32.25% | 322.5 |
| 5 | 46,521 | 11.07% | 110.7 |
| 6 | 27,063 | 6.44% | 64.4 |
| 7 | 7,056 | 1.68% | 16.8 |
| 8 | 4,009 | 0.95% | 9.5 |
| 9 | 1,124 | 0.27% | 2.7 |
| 10+ | 833 | 0.20% | 2.0 |

- "1,000개로 치면 몇 개"는 비율을 감 잡기 쉽게 **환산**한 것일 뿐이다
- 개수가 달라도 비교할 수 있는 이유: 모델 칸 = 생성 1,000개 중 **비율**, 사전 칸 = 전체 중 **비율**. 둘 다 %다
- 사전은 전체를 셀 수 있으니 전체를 센다. 1,000개만 뽑으면 뽑을 때마다 값이 흔들린다 (1글자가 2개일 수도 5개일 수도 있다)
- 모델은 만들 수 있는 단어가 끝없이 많아 전체를 셀 수 없어서 1,000개로 **추정**한다 → seed마다 조금 흔들린다
- 모델이 사전을 완벽하게 흉내 낸다면, 아주 많이 생성했을 때 길이 비율이 이 사전 비율에 가까워져야 한다. 즉 사전 칸은 **목표 분포**다

### Q4. 3차원 배열이 아니라 해시테이블인데 왜 64비트 키가 필요한가?
2.1절 참고. 59GB는 **배열**을 못 쓰는 이유이고, 64비트는 해시테이블 **키 타입**의 문제다.

## 7. n을 키우면 어떻게 되나 (과적합 — 구현하지 않고 실측으로 설명)

### 강의의 질문과 답
- "n을 100까지 늘리면 좋은 거 아니야?" → 사전의 평균 단어가 3.69글자인데 앞 99글자를 보고 예측한다는 건 **사전을 통째로 외우는 것**이다. 생성되는 단어 = 사전 단어 그대로 복사. 일치율은 100%에 가까워지지만 새로운 단어를 못 만든다
- LLM에서도 같은 문제: 모델이 학습 데이터를 그대로 외우는 **과적합**

### "자동판매기"로 보는 선택지의 소멸 (6-그램, 문맥 앞 5글자)
`words.txt`에서 그 접두사로 시작하는 단어를 센 실측이다.

| 접두사 | 시작하는 단어 수 | 다음 글자 종류 |
|---|---|---|
| 자 | 4,105 | 431 |
| 자동 | 267 | 118 |
| 자동판 | **1** | 1 (매) |
| 자동판매 | 1 | 1 (기) |
| 자동판매기 | 1 | 1 (EOS) |

강의 그림은 4~5글자에서야 확정되는 것처럼 그렸지만, 실제로는 **3글자 "자동판"에서 이미 확정**이다.

### 선택지가 1개뿐인 문맥의 비율 (BOS/EOS 패딩 포함)
| n | 서로 다른 문맥 | 선택지 1개인 문맥 |
|---|---|---|
| 2 | 2,451 | 17.9% |
| 3 | 169,589 | 49.7% |
| 4 | 547,576 | 79.8% |
| 5 | 684,407 | 84.3% |
| 6 | 720,877 | 85.2% |

- 트라이그램에서 이미 문맥의 **절반**이 "외운 길" 하나뿐이다. n=4부터 80%를 넘는다
- 이 값은 구현한 프로그램이 아니라 별도 Python 실측이다 (이 저장소는 n=2, 3만 구현)

### 강의 수치와의 차이
| | 강의 | 이번 실측 |
|---|---|---|
| 바이그램 일치율 | 40% | 41.7% (1,000개) / 41.6% (10만 개) |
| 트라이그램 일치율 | 61.7% | 57.3% (1,000개) / 57.5% (10만 개) |

바이그램은 거의 같지만 트라이그램은 강의가 약 4%p 높다. **원인은 확정하지 못했다.** 강의는 1,000개라 5글자 단어 표본이 100개 안팎이라서 표본에 따라 흔들릴 수 있고, 강의의 패딩 방식이 다를 가능성도 있다. 10만 개로 재도 57.5%라서 단순한 표본 변동만으로 설명되지는 않는다.

## 8. AI와 작업하면서 얻은 교훈 (구현·검증·이론 관련)

### 8.1 평가 지표는 비교할 수 있게 되는 순간 먼저 제안해야 했다
**지적**: "사전 일치율이 왜 트라이그램에서야 나오나?"
- 일치율은 트라이그램 전용 지표가 아니라 **어떤 생성 모델에도 쓸 수 있다.** Step3 질의응답에서 이미 비공식적으로 쟀다 (19/50, 길이별 사전 단어 비율)
- Claude가 강의 순서만 따랐을 뿐 지표를 먼저 제안하지 않았다. 강의 AI 팁("AI는 검증을 명시적으로 지시해야 넣었다")과 같은 상황이었다
- **반영**: Step4에서는 두 프로그램이 일치율을 직접 계산해 결과 파일에 남기고, 검증기가 다시 센다
- **의심할 것**: 모델을 만들면 "이 모델이 좋아졌는지 어떻게 숫자로 말할 수 있나"를 먼저 묻는다

### 8.2 학습 목적에서는 "일반화"가 오히려 방해가 된다
**지적**: Claude가 "n을 인자로 받는 일반 N-그램(n=1~6)"을 추천했고 사용자가 거절했다.
- 취지: Step 폴더를 나눈 이유가 **각 단계를 독립적으로 남겨 공부하기 위해서**다. 서비스 모듈처럼 일반화하면 "무엇이 n 때문에 바뀌는가"가 코드에서 사라진다
- 공통된 부분은 이전 Step에서 **복사**하고 그 Step 전용으로 구현한다. 그 덕분에 바이그램 ↔ 트라이그램 diff에서 BOS 개수, 키 공식, 문맥 창 밀기가 한눈에 보인다
- **교훈**: 실무의 "좋은 설계"(재사용)가 학습의 "좋은 설계"(차이를 드러냄)와 다를 수 있다

### 8.3 걸러 낸 선택지는 걸렀다고 밝혀야 한다
**지적**: 강의의 AI 팁에는 자모 분리 분석이 나오는데 브리핑에서 언급조차 하지 않았다.
- 제외 근거: 자모 분리는 **n**이 아니라 **토큰 단위**를 바꾸는 것이다. Step4에 섞으면 "n 변화"와 "단위 변화" 두 변수가 동시에 바뀌어 일치율 비교가 무의미해진다. 또 자모 트라이그램은 문맥이 음절 1개도 안 되고, 생성 결과를 음절로 다시 조립하는 규칙이 필요하다 → 토크나이저 단계의 주제
- 솔직한 점: "고려했지만 뺐다"고 밝히지 않았다. 선택지를 걸렀으면 **거른 사실과 이유**를 적어야 한다
- **실험 설계 원칙**: 비교 실험에서는 한 번에 변수 하나만 바꾼다

### 8.4 서로 다른 두 문제를 한 문장에 섞지 말 것 (59GB vs 64비트)
"3차원 배열은 59GB라 못 쓴다. 키가 147억이라 64비트가 필요하다"를 한 문단에 썼더니, "배열 대신 해시를 쓰는데 왜 64비트가 필요하냐"는 질문이 나왔다.
- 두 이야기는 **다른 층**의 문제다: 배열을 못 쓴다(자료구조 선택) / 해시 키를 담을 타입(자료형 선택)
- **의심할 것**: 한 설명에서 "그래서"로 이어진 두 문장이 정말 인과관계인가. 앞 문장의 결론은 "해시를 쓴다"이고, 64비트는 그 **다음** 단계의 문제다

### 8.5 비유가 실제 계산 방식을 가린다 ("사전에서 1,000개를 뽑으면")
설명하려고 "사전 단어 1,000개를 무작위로 뽑으면 길이가 이렇게 나뉩니다"라고 했더니 "모델처럼 사전도 샘플링한 것이냐"는 질문이 나왔다.
- 실제는 420,309개 **전수**를 센 비율이다. 비유를 먼저 쓰고 계산 방식을 뒤에 쓰면 비유가 계산 방식으로 오해된다
- **교훈**: 실제 계산 방식을 먼저 말하고, 비유나 환산은 "환산한 것일 뿐"이라고 밝힌다

### 8.6 전체 지표 하나만 믿지 말 것
바이그램의 41.7% 중 절반 이상이 1글자 단어였다. **전체 평균은 구성이 다른 두 모델을 같은 눈금에 놓지 못한다.**
- 모델 비교에서는 전체 숫자와 함께 **구성(길이, 분포)별 숫자**를 같이 본다
- 지표가 "좋아 보이는" 이유가 모델의 실력인지, 지표의 약점을 건드린 것인지 분해해 본다

### 8.7 규칙을 만든 날 쓴 코드도 규칙을 안 지킬 수 있다 → 자동으로 검사하게 만들기
"학습용 주석 규칙"(구역마다 목적·동작·이유)은 Step3부터 적용하기로 했는데, 확인해 보니 `step3_bigram.c`의 구역 11개 중 셋을 모두 갖춘 구역이 **0개**였다.
- 결정: Step3은 그대로 두고 Step4부터 지킨다
- 사람이 매번 확인하지 않아도 되게 `step4_verify.py` [7]이 **모든 구역 머리에 [목적][동작][이유]가 있는지, 목차 줄 번호가 맞는지** 검사한다. 이 검사도 `--self-test`로 실패할 수 있음을 확인했다
- **교훈**: 규칙은 문서로만 두면 안 지켜진다. 검사할 수 있는 규칙은 검증기에 넣는다

### 8.8 비교 실험은 조건(seed)이 같아야 하고, 조건은 파일에서 확인한다
같은 seed로 바이그램을 돌리려고 트라이그램 결과 파일에서 seed를 꺼내는 명령을 썼는데, 이 환경에서 명령이 실패해 **seed가 빈 값**이 되었다. 프로그램은 빈 값을 **0**으로 받아들여 조용히 실행했다.
- 결과 파일 헤더에 seed가 기록돼 있어서 두 파일의 seed가 다른 것을 **헤더로 발견**했다 (일치율 42.1% vs 41.7%로 차이가 작아서 숫자만 봐서는 몰랐다)
- 앞 단계가 빈 값을 내면 뒤 단계가 조용히 돌아가지 않게 해야 한다 (`[ -n "$SEED" ] &&` 같은 확인)
- 그래서 비교 문서를 만드는 `--compare`는 **seed와 생성 개수가 같은 결과 파일 쌍만** 묶고, 두 파일이 검증을 통과해야만 문서를 만든다

### 8.9 같은 이름의 숫자도 정의가 다르면 다른 숫자다
앞서 10만 개 분석에서 "3글자 창이 사전에 실재하는 비율 56.4%"라고 적었는데, 이번에 쓴 값은 23.9%다.
- 앞의 것은 BOS/EOS가 붙은 조각까지 센 값이고, 이번 것은 **BOS/EOS 없는 순수 3글자 조각만** 센 값이다 (그리고 1,000개 기준)
- **교훈**: 수치를 인용할 때는 정의와 표본 크기를 같이 적는다

### 8.10 결정을 물을 때는 맥락과 선택지를 함께 써야 한다
브리핑 말미의 "① 바이그램과 비교할 기준값을 어디서 얻을까"는 사용자가 **무슨 소리인지 모르겠다**고 했다. 무엇이 문제인지, 선택지가 각각 무엇을 뜻하는지가 빠져 있었다.
- 사용자가 직접 정해 준 구성(바이그램도 같은 구성의 단일 프로그램)이 사실상 그 질문의 답이 되었다
- **교훈**: 결정 요청은 "무엇을 / 왜 / 선택지별 결과"를 한 번에 쓴다
