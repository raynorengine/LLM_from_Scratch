# N-그램 (n = 2 ~ 6) — n을 바꾸면 무엇이 달라지나

## 복습용 핵심 정리

> **한 줄 요약**: N-그램 프로그램 다섯 개(n = 2 ~ 6)는 **같은 코드에서 "앞 글자 수(n-1)"만 바꾼 것**이다. 단 하나의 예외는 6그램의 키 — 숫자 하나로 만들면 64비트를 넘어서 **문맥과 다음 글자를 따로 저장**해야 한다. 실험해 보니 사전 일치율은 n=2 42.8% → n=4 94.4% → n=6 100.0%로 올랐고, 사전에 없는 단어는 572개 → 56개 → 0개로 줄었다. 그 원인은 "선택지가 하나뿐이라서"가 아니라, **BOS 패딩 때문에 길이 n-2 이하인 단어는 구조적으로 사전 단어일 수밖에 없기 때문**이다.

### 개념
- n그램 = 앞 **n-1글자**(문맥)를 보고 다음 글자를 뽑는 모델. P(다음 | 문맥) = count(문맥, 다음) / count(문맥, ·)
- 단어 앞에 **BOS n-1개**, 뒤에 **EOS 1개**를 붙인다. 길이 L 단어 → n그램 **L+1개** (n과 무관)
- n=2 ~ 6 비교는 **모델 5개를 따로 만드는 것**이다. 서로 공유하는 것은 사전 데이터뿐
- 다섯 파일의 코드 차이는 세 종류다
  1. **n 때문에**: BOS 개수, 창 폭, 문맥 변수 개수, 표의 열 개수 (모든 파일 쌍)
  2. **크기 때문에**: 해시 칸 수 `HASH_BITS` 19 → 21 → 22
  3. **64비트 한계 때문에**: 6그램만 키 분리 (V⁶ ≈ 2.2×10²⁰ > 2⁶⁴ ≈ 1.8×10¹⁹)

## 1. 용어 — 글자, 단어, seq (사용자 질문)

> **Q.** *"`seq = [BOS BOS BOS 사 회 EOS]` 이게 뭐지? 우리는 글자 단위인데 왜 단어 단위로 이야기하지?"*

Claude가 "단어"와 "글자"를 섞어 쓰고, `seq`를 정의 없이 써서 생긴 혼란이다. 정리하면:

| 용어 | 뜻 | 예 |
|---|---|---|
| **글자** | n그램을 세는 단위. 모델이 한 번에 하나씩 뽑는 것 | 사, 회 |
| **단어** | words.txt의 한 줄. 사전 항목이자 모델이 만들어 내는 결과물 | 사회 |
| **BOS / EOS** | 단어의 시작·끝을 표시하는 가짜 글자 | — |
| **seq** | 코드의 `g_seq` 배열. 사전 42만 단어를 BOS·EOS로 감싸 **한 줄로 이어 붙인 글자 번호 배열** | 아래 |

- 세는 것도, 뽑는 것도 **글자 단위**다
- "단어"가 계속 나오는 이유: n그램을 **단어 안에서만** 세기 때문이다. "사회"의 '회'와 다음 단어의 첫 글자를 이어서 세지 않는다

트라이그램의 seq:
```
words.txt:  사회
            나비

g_seq:  BOS BOS 사 회 EOS BOS BOS 나 비 EOS ...   (실제로는 전부 숫자)
        └─── 단어 "사회" ───┘ └─── 단어 "나비" ───┘
```
이 배열을 글자 한 칸씩 밀면서 3글자씩 읽은 것이 3그램이다: `(BOS,BOS,사) (BOS,사,회) (사,회,EOS)`.
EOS에서 다음 단어 BOS로 넘어가는 묶음은 세지 않는다.

`[BOS BOS BOS 사 회 EOS]`는 **4그램 프로그램의 seq 중 "사회" 부분만** 잘라 보인 것이다 (4그램은 앞 3글자를 보므로 BOS 3개).

## 2. N-그램 = 트라이그램에서 숫자 하나를 바꾼 것 (사용자 질문)

> **Q.** *"step4의 trigram과 step5의 n-gram의 차이는? 코드만 같고 앞 글자 수가 n-1개만큼 된다는 거 아닌가? 슬라이싱을 n-1번씩 하나? step5 n-gram은 말이 n-gram이지 bigram ~ 6gram 총 5번 실행하는 거 아닌지?"*

**세 가지 모두 맞다.** 정확히 하면:

### 2.1 "5번 실행하는 것 아닌가?" → 그렇다
- n=2 모델, n=3 모델, …, n=6 모델은 **완전히 별개**다. n=4 모델은 n=3 결과를 이어 쓰지 않고 처음부터 다시 센다
- Step5에서 새로 배우는 것은 코드가 아니라 **"n을 바꾸면 결과가 어떻게 달라지나"라는 실험**이다

### 2.2 "슬라이싱을 n-1번씩 하나?" → 창의 폭이 넓어질 뿐, 미는 횟수는 같다
```
단어 "사회", n=4  →  [BOS BOS BOS 사 회 EOS]

위치 0: [BOS BOS BOS] 사      ← 창 폭 = n칸 (문맥 n-1 + 다음 1)
위치 1:     [BOS BOS 사] 회
위치 2:         [BOS 사 회] EOS
```
- 창은 항상 **글자 한 칸씩** 민다. 단어마다 **L+1번** (n과 무관) → n그램 총 개수는 n=2 ~ 6 모두 1,971,874
- 바뀌는 것은 위치마다 읽는 칸 수 (n칸)
- 생성할 때도 글자 하나를 뽑을 때마다 창을 한 칸 민다. 미는 데 드는 대입이 n-2번으로 늘 뿐이다

## 3. 다섯 파일의 코드 구조 비교 (구현 측면)

같은 폴더의 `step5_bigram.c` ~ `step5_6gram.c`를 **주석을 빼고 코드만** diff해서 확인했다.

| 비교 | 바뀐 코드 줄 수 | 차이의 원인 |
|---|---|---|
| bigram → trigram | 107 | n |
| trigram → 4gram | 134 | n + **만든 방식** (3.4절) |
| 4gram → 5gram | 91 | n 만 (가장 순수한 비교) |
| 5gram → 6gram | 156 | n + **키 분리** (3.3절) |

### 3.1 n 때문에 바뀌는 것 (모든 파일 쌍)
`4gram → 5gram`이 이 부분만 보여 준다. 각 구역에서 **숫자 하나 또는 변수 하나**가 늘어난다.

| 구역 | 4그램 | 5그램 | 왜 |
|---|---|---|---|
| [6] seq | `g_word_count * 4`, BOS 3줄 | `* 5`, BOS 4줄 | 문맥이 n-1글자라 첫 글자를 뽑을 때도 n-1칸을 채워야 함 |
| [8] 세기 루프 | `i + 3 < g_seq_n` | `i + 4 < g_seq_n` | 창의 마지막 칸이 배열 밖으로 나가지 않게 |
| [8] 경계 검사 | `seq[i]`, `[i+1]`, `[i+2]` 중 EOS | 4칸 중 EOS | 문맥 칸에 EOS가 있으면 단어 사이에 걸친 묶음 |
| [8] 키 | `key = key * V + ...` 4줄 | 5줄 | 글자 번호를 **V진법 자리**로 한 자리씩 붙임 |
| [9] 뽑기 | `pick(prev1, prev2, prev3, r)` | `prev4`까지 | 문맥 = 앞 n-1글자 |
| [10] 창 밀기 | `prev1=prev2; prev2=prev3; prev3=next;` | 한 줄 더 | 가장 오래된 글자가 빠지고 새 글자가 들어옴 |
| [12] 빈도표 | 열 `prev1 prev2 prev3 next` | `prev4` 추가 | 문맥 열이 n-1개 |
| [14] 검증 입력 | 이름 3개 읽기 | 4개 | 문맥 = n-1글자 |

키를 만드는 코드 (5그램):
```c
key = (unsigned long long)g_seq[i];                /* 1번째 자리 */
key = key * V + (unsigned long long)g_seq[i + 1];  /* 자리 하나 올리고 다음 글자 붙이기 */
key = key * V + (unsigned long long)g_seq[i + 2];
key = key * V + (unsigned long long)g_seq[i + 3];
key = key * V + (unsigned long long)g_seq[i + 4];  /* 마지막 자리 = 다음 글자 */
```
- 10진수 "352"를 `3 → 3×10+5 → 35×10+2`로 만드는 것과 같다. 여기서는 밑이 V = 2,452
- 자리마다 0 ~ 2,451이므로 서로 다른 n그램은 **반드시 서로 다른 키**가 된다
- **곱하기 전에 `unsigned long long`으로 바꾼다.** `int`끼리 곱하면 `int` 범위에서 먼저 넘친다

### 3.2 크기 때문에 바뀌는 것 — `HASH_BITS`
| | n=2 | n=3 | n=4 | n=5 | n=6 |
|---|---|---|---|---|---|
| 서로 다른 n그램 | 171,425 | 654,039 | 976,877 | 1,105,860 | 1,141,426 |
| `HASH_BITS` (칸 수) | 19 (52만) | 21 (210만) | 22 (419만) | 22 | 22 |
| 적재율 | 33% | 31% | 23% | 26% | 27% |
| 생성 단계 메모리 | 6.3MB | 25.2MB | 50.3MB | 50.3MB | 67.1MB |
- 선형 탐사는 칸이 많이 찰수록 빈 칸까지 멀어져 느려진다. 그래서 적재율을 30% 안팎으로 맞췄다 (70%를 넘으면 프로그램이 거부)
- 6그램 메모리가 더 큰 이유: 칸마다 "다음 글자" 4바이트가 더 있다 (3.3절)

### 3.3 64비트 한계 때문에 바뀌는 것 — 6그램의 키
**문제**: 5그램까지 키는 n그램 전체를 V진법 n자리 수 하나로 만들었다.

| n | 키 최댓값 V^n - 1 | 2⁶⁴ ≈ 1.8×10¹⁹ 에 |
|---|---|---|
| 4 | 3.6×10¹³ | 들어감 |
| 5 | 8.9×10¹⁶ | 들어감 (208배 여유) |
| 6 | **2.2×10²⁰** | **약 12배 넘침** |

넘친 값은 잘려서 **서로 다른 6그램이 같은 키**가 된다. 오류 메시지도 나지 않는다.
검증기로 흉내 내 보니 서로 다른 6그램 1,141,426개 중 **1,124,043개(98.5%)가 엉뚱한 글자 조합으로** 풀렸다 (`step5_verify.py --self-test`의 "6그램 키를 숫자 하나로" 사례).

**해결**: 해시 칸에 키를 두 칸으로 나눠 저장한다.
```c
typedef struct {
    unsigned long long *ctxs;    /* 문맥 = 앞 5글자를 V진법 5자리 수로 (최대 8.9×10^16, 64비트에 들어감) */
    int                *nexts;   /* 다음 글자 번호 */
    int                *counts;
    ...
} HashTable;

/* 같은 6그램인가 = 문맥도 같고 다음 글자도 같은가 */
if (ht->ctxs[i] == ctx && ht->nexts[i] == next) { ... }
```

**핵심 구분: "해시 값"은 넘쳐도 되고, "키"는 넘치면 안 된다.**
```c
static size_t ht_slot(const HashTable *ht, unsigned long long ctx, int next)
{
    unsigned long long h = ctx * (unsigned long long)g_vocab + (unsigned long long)next;  /* 넘쳐도 됨 */
    return (size_t)((h * FIB_MULT) >> (64u - ht->bits));
}
```
- `ht_slot`의 `ctx × V + next`는 6그램이면 넘친다. 그래도 괜찮다. 이 값은 **"어느 칸부터 찾아볼지"만** 정한다
- 넘쳐서 두 6그램이 같은 값이 되면 같은 칸 근처에서 출발할 뿐이다(충돌). 같은 6그램인지는 `ctxs`와 `nexts`를 **직접 비교**해서 판단하므로 섞이지 않는다
- 반대로 5그램까지의 `keys[i] == key` 비교는 키 자체가 정체성이라 넘치면 안 된다

6그램에서 이 변경이 퍼지는 곳:

| 구역 | 5그램 | 6그램 |
|---|---|---|
| [7] 해시 | `keys[]` 1개, `ht_add(ht, key)` | `ctxs[]`+`nexts[]`, `ht_add(ht, ctx, next)` |
| [8] 세기 | 5자리 `key` | 5자리 `ctx` + `ht_add(&g_ht, ctx, g_seq[i + 5])` |
| [9] 뽑기 | `ctx_base()` = 문맥 × V, 조회는 `base + b` | `ctx_key()` = 문맥, 조회는 `ht_get(ctx, b)` |
| [12] 표 | 키를 V로 나눠 6자리로 풀기 | `nexts[]`에서 다음 글자, `ctxs[]`를 풀어 5자리 |

### 3.4 n과 무관한 차이 — 만든 방식 때문 (동작은 같음)
`trigram → 4gram` diff가 `4gram → 5gram`보다 큰 이유. bigram·trigram은 **Step4에서 손으로 쓴 파일을 복사**했고, 4·5·6그램은 **Claude가 생성기로 만들었다**. 그래서 같은 일을 다르게 쓴 곳이 있다.

| 구역 | trigram (Step4 복사) | 4·5·6그램 (생성) |
|---|---|---|
| [8] 키 만들기 | `((a*V + b)*V) + c` 한 식 | `key = key * V + ...` 한 자리씩 |
| [12] 키 풀기 | `key / V / V`, `(key / V) % V` | `rest % V; rest /= V;` 반복 |
| [12] 표 정렬 비교 | `a1`, `a2` 변수로 직접 비교 | `da[]` 배열 + 반복문 |
| [14] `--dump` | 해시 칸 순서대로 출력 | 정렬된 표 순서로 출력 (정렬 비용이 더 듦) |
| [14] 문맥 읽기 | `name1`, `name2` | `name[3][32]` |

- 결과는 같다: n=2·3 빈도표가 Step4와 바이트 단위로 같고, `--dump`는 검증기가 순서와 무관하게 비교한다
- 다만 4그램 파일 머리말의 "*두 파일을 diff하면 n이 바뀐 부분만 보인다*"는 **trigram ↔ 4gram 사이에서는 사실이 아니다** (4 ↔ 5, 5 ↔ 6은 사실). 통일할지는 사용자 결정 대기

### 3.5 바뀌지 않는 것
- 해시테이블 하나로 세고 뽑는다. **후보 2,452개를 해시에 하나씩 물어 누적**하고, `누적 > r`이 되는 첫 글자를 고른다 (CSR 없음)
- `'>'` 비교, 탐욕적 디코딩, 사전 일치율, 결과 파일 형식, 시간 측정, 난수(rand30)

### 4.3 사전에 없는 단어 (결과 파일 앞부분)
- n=2: 첫서부대다소, 광하다뜬, 세가는수시민, 합적, 애송적삼림조과 …
- n=3: 조각나무이, 녹시딜, 치상해요, 동류근식물, 핸드카드뮴 …
- n=4: 단선스크린인쇄, 불국사연화교, 애기자나물, 붉은수염도미, 민권확장론, 사회문화기구 …
- n=5: 제이독립선언서, 네델란드부르죠아의회제, 핵융합에네르기리용률 (3개 전부)
- n=6: 없음
- 전체 목록은 `PART1_N-Gram/Step5/step5_compare.txt` [4]. **"그럴듯한가"는 숫자로 잴 수 없어서 직접 읽고 판단해야 한다**

## 5. 인사이트

### 5.1 일치율은 n=3 → 4에서 크게 오르고, 5 이후 거의 멈춘다
- 42.8 → 57.6 (+14.8%p) → **94.4 (+36.8%p)** → 99.7 → 100.0
- 사전에 없는 단어는 572 → 424 → **56** → 3 → 0
- 서로 다른 n그램 증가도 같은 모양: +282% → +49% → +13% → +3%. n=5 이후엔 **새로 배우는 패턴이 거의 없다**
- 이유: 사전 단어의 **79.4%가 4글자 이하**다 (평균 3.69글자). 문맥이 3 ~ 5글자면 대부분의 단어를 통째로 볼 수 있다

### 5.2 길이 n-2 이하인 단어는 구조적으로 사전 단어다 (가장 중요한 발견)
4그램이 "사회"(2글자)를 만드는 과정:
```
(BOS,BOS,BOS) → 사     "단어 첫 글자가 '사'인 단어가 있다"
(BOS,BOS,사)  → 회     "'사'로 시작하고 둘째 글자가 '회'인 단어가 있다"
(BOS,사,회)   → EOS    "'사회'로 시작해서 바로 끝나는 단어가 있다" = 사전에 "사회"가 있다
```
- 문맥에 BOS가 남아 있는 동안에는 문맥이 **"단어 처음부터 지금까지 전부"**다. 그래서 모델이 뽑을 수 있는 경로는 **사전 단어의 앞부분**뿐이다
- 길이 L 단어의 마지막 판단(EOS)은 문맥 (…, 마지막 n-1글자)에서 내린다. **L ≤ n-2면 그 문맥에도 BOS가 하나 이상 남아** 있다 → "이 글자들로 시작해서 바로 끝나는 단어"가 사전에 있어야만 EOS가 나온다 → **반드시 사전 단어**
- L = n-1이면 마지막 문맥에 BOS가 없다. 그래서 4그램의 3글자 단어는 보장되지 않는다 (실측 99.6%, 284개 중 1개가 사전에 없음)

| n | 보장되는 길이 | 실측 (두 seed 모두) |
|---|---|---|
| 2 | 없음 | 1글자도 99.5% (208개 중 1개 불일치) |
| 3 | 1글자 이하 | 1글자 100% |
| 4 | 2글자 이하 | 1 ~ 2글자 100% |
| 5 | 3글자 이하 | 1 ~ 3글자 100% |
| 6 | 4글자 이하 | 1 ~ 4글자 100% |

- n=6에서 일치율이 100%에 가까운 이유: 생성된 단어의 79.4%가 4글자 이하라서 **보장 범위 안**이다. 5글자 이상은 보장은 아니지만 문맥 5글자가 단어 대부분을 덮어서 거의 맞는다 (seed 2026에서는 6글자 63개 중 1개가 사전에 없음)

### 5.3 "선택지가 하나뿐이라서 외운다"는 절반만 맞다
| | n=2 | n=3 | n=4 | n=5 | n=6 |
|---|---|---|---|---|---|
| 후보가 1개뿐인 **문맥**의 비율 | 17.9% | 49.7% | 79.8% | 84.3% | 85.2% |
| 실제 생성 중 **선택지 없이 뽑힌 단계** | 0.0% | 7.2% | 30.7% | 33.0% | 33.2% |
- 문맥 목록으로 보면 n=6의 85%가 외길이다. 하지만 **실제로 생성할 때 지나가는 문맥**으로 세면 33%뿐이다. 많이 지나가는 문맥(BOS로 시작하는 단어 앞부분)은 후보가 많다
- 그래도 n=6은 100% 사전 단어를 만든다. 선택지가 있어도 **고를 수 있는 것이 전부 사전 단어의 다음 글자**이기 때문이다 (5.2절)
- 교훈: "외길이라서 외운다"는 그럴듯한 설명이지만, **생성에서 실제로 쓰이는 빈도로 가중해서 다시 세면** 다른 그림이 나온다

### 5.4 새 단어는 대부분 "사전 단어 이어 붙이기"다
사전에 없는 단어 중 **2글자 이상 사전 단어 두 개 이상으로 나눌 수 있는** 비율:

| | n=2 | n=3 | n=4 | n=5 |
|---|---|---|---|---|
| 새 단어 수 | 572 | 424 | 56 | 3 |
| 사전 단어 조합 | 146 (26%) | 175 (41%) | **39 (70%)** | 1 |
- n=4 예 (프로그램이 찾은 분해, 각 조각이 words.txt에 있음):
  단선+스크린인쇄, 애기자+나물, 사회+문화+기구, 핵동력+공업, 다공성+크롬산칼륨, 나무잎+검댕이병
- n=4 새 단어 중 조합이 아닌 것: 붉은수염도미, 민권확장론, 데이비드슨, 영점엔트로 …
- n=4의 새 단어는 대부분 **사전 단어 두 개가 이어지는 자리에서 문맥 3글자가 양쪽에 걸쳐 이어진** 경우다
- 주의 1: 2글자 사전 단어가 7.8만 개나 되어서, 아무렇게나 만든 글자열도 우연히 나뉠 수 있다 (n=2의 26%가 그 정도). 그러니 이 비율은 **n끼리의 상대 비교**로만 본다
- 주의 2: 프로그램은 "나뉘는 방법 하나"를 찾을 뿐 뜻이 통하는 분해를 고르지 않는다 (예: 불국+사연+화교)

### 5.5 생성 단어의 길이 분포가 n=4부터 사전과 거의 같아진다
| 길이 | 사전 | n=2 | n=3 | n=4 | n=6 |
|---|---|---|---|---|---|
| 1 | 0.32% | **20.8%** | 0.3% | 0.2% | 0.2% |
| 4 | 32.25% | 12.0% | 20.7% | 32.4% | 33.7% |
| 10+ | 0.20% | **4.9%** | 1.4% | 0.6% | 0.2% |
- n=2는 "지금 몇 번째 글자인지"를 몰라서 1글자 단어와 아주 긴 단어를 둘 다 많이 만든다
- n=4부터는 단어 길이 감각이 사전과 거의 같다

### 5.6 탐욕적 디코딩도 n=4에서 멈춘다
- n=2 "사" → n=3 "사회" → n=4 ~ 6 **"사회적교육학"** (같은 단어)
- 탐욕적 경로(문맥마다 가장 많이 나온 글자)가 n=4 ~ 6에서 같다. 문맥을 4글자 이상 봐도 매 단계 1등 글자가 바뀌지 않았다는 뜻이다

### 5.7 비용
| | n=2 | n=3 | n=4 | n=5 | n=6 |
|---|---|---|---|---|---|
| 학습(세기) | 55ms | 134ms | 138ms | 162ms | 183ms |
| 생성 1,000개 | 521ms | 711ms | 669ms | 856ms | 906ms |
- 생성은 n이 커져도 크게 늘지 않는다: 한 번 뽑을 때 **후보 2,452개를 묻는 횟수는 n과 무관**하다. 늘어난 만큼은 해시 칸이 커져 메모리 접근이 느려진 몫이다
- 시간은 실행마다 흔들린다 (같은 바이그램이 Step4 실행에서는 226ms). 경향만 본다

### 5.8 강의 보고값과 나란히 (목표가 아니라 비교용)
| | n=2 강의 | n=2 실측 | n=3 강의 | n=3 실측 | n=6 강의 | n=6 실측 |
|---|---|---|---|---|---|---|
| 전체 | 40% | 42.8% | 61.7% | 57.6% | 100% | 100.0% |
| 2글자 | 79% | 87.1% | 98% | 97.5% | - | 100% |
| 3글자 | 17% | 20.1% | 65% | 59.9% | - | 100% |
| 5글자 | 0% | 0.0% | 27% | 17.9% | - | 100% |
- 강의 출처: raw 2-6 표(n=2·3), raw 2-7 본문(n=6). 강의는 seed·패딩 같은 조건을 밝히지 않았다
- 강의의 n=4·5 평가("그럴듯하면서 새로운 단어")는 정성적이라 숫자로 대조할 수 없다. 4.3절 목록을 보고 판단한다

### 5.9 일반화 vs 암기 — 이 실험이 보여 주는 것
- 일치율이 높을수록 좋은 모델이 아니다. n=6은 100%지만 **새 단어를 하나도 만들지 못했다** = 사전 복사기
- n=2·3은 새 단어가 많지만 대부분 사전 단어로 나뉘지 않는 조각이다
- n=4는 일치율 94.4%를 유지하면서 새 단어 56개를 만들었고, 그중 70%가 사전 단어 조합이다
- **어느 n이 "좋은가"는 목적에 달렸다.** 사전에 있는 단어를 재현하려면 큰 n, 새 단어를 만들려면 작은 n. 이것이 강의가 말한 트레이드오프이고, 그 경계가 이 데이터에서는 **n=4 ~ 5 사이**에서 보인다 (n=5의 새 단어는 3개뿐)

## 6.5 Step2 ~ Step5 코드 계보 — 같은 뼈대인가, 그때그때 새로 짰나 (사용자 질문)

> **Q.** *"step2 unigram, step3 bigram, step4 bi·tri, step5 bi ~ 6gram. 코드 구조가 거의 같은데 핵심 로직만 다른 건지, 그때그때 구현해서 다른 건지?"*

**답: Step3에서 만든 뼈대를 Step4·5가 그대로 물려받았고, 바뀐 건 핵심 로직이다. Step2만 별개의 작은 프로그램이다.**
같은 이름의 함수를 단계끼리 주석을 빼고 비교한 결과:

| 구간 | 그대로 물려받은 것 (코드 동일) | 바뀐 것 |
|---|---|---|
| Step2 → Step3 | `rand30`, `rand_below`, `next_output_path` 3개뿐 | 나머지 전부. Step2는 **Step1의 빈도표 파일을 읽고**, Step3부터는 **words.txt를 직접 읽는다** |
| Step3 → Step4 | `now_ms`, `rand30`, `rand_below`, `utf8_*`, `load_file`, `scan_words`, `in_dictionary`, `name_to_id`, `word_to_string`, `next_output_path` | 파일 4개 → 1개, 함수 포인터 구조 제거, seq 만들기를 `build_seq`로 분리, 해시 키 `int` → 64비트 |
| Step4 → Step5 (bi, tri) | 전부 (이름만 `step5_`) | 없음 |
| Step5 tri → 4 → 5 → 6 | 공통 구역 전부 | n에 따라 바뀌는 구역 + 6그램 키 분리 (3절) |

단계마다 **핵심 로직**만 보면:

| | 문맥 | 저장 | 뽑기 |
|---|---|---|---|
| Step2 유니그램 | 없음 | 글자별 빈도 배열 (Step1 결과) | 누적 빈도 + **이진 탐색** |
| Step3 ① 배열 | 앞 1글자 | 2,452 × 2,452 배열 | 행을 순서대로 누적 |
| Step3 ② 해시 | 앞 1글자 | 해시 (`int` 키) | 후보 2,452개 순차 조회 |
| Step3 ③ CSR | 앞 1글자 | 해시로 센 뒤 CSR | 행 안 **이진 탐색** |
| Step4·5 | 앞 n-1글자 | 해시 (64비트 키, 6그램은 2칸 키) | 후보 2,452개 순차 조회 (= Step3 ②) |

- **뽑기의 원리는 Step2부터 Step5까지 하나다**: r을 0 ~ (합계-1)에서 뽑고 `누적 > r`이 되는 첫 후보를 고른다. 바뀐 것은 "누적을 어떻게 찾느냐"(이진 탐색 / 순차 조회)뿐이다
- Step4·5의 뽑기는 Step3 ②의 `hash_pick`과 거의 같다. 차이는 키 타입(`int` → `unsigned long long`)과 `base`를 `ctx_base()`로 만드는 것뿐이다
- 그때그때 새로 짠 흔적은 두 군데다
  - **Step2**: 입력이 다르다(빈도표 파일). 그래서 UTF-8 해석·seq·사전 조회가 없다
  - **Step5 4 ~ 6그램**: 생성기로 만들어 trigram과 작성 방식이 다른 곳이 5군데 있다 (3.4절)

## 8. AI와 작업하면서 얻은 교훈 (구현·검증·이론 관련)

### 8.1 강의 결과는 목표가 아니라 비교 대상이다
- Claude가 강의의 n별 품질표를 "핵심"으로 내세우고, n=6이 100%인 이유까지 미리 설명했다 → 사용자: *"억지로 만들면 절대 안 됨"*
- 실측이 강의와 다르면 다르다고 적는다. 실제로 n=3은 강의 61.7% vs 실측 57.6%로 다르고, n=6은 seed에 따라 99.9%도 나온다
- 이렇게 두니 5.2절처럼 **강의에 없던 정확한 원인**(길이 n-2 이하 보장)을 데이터에서 찾을 수 있었다

### 8.2 수치를 셀 때는 구현과 같은 전제로 센다
- 오전 기록의 "n이 커질수록 n그램이 줄어든다" 표는 **BOS를 1개만** 붙여 센 값이었다. 구현은 n-1개를 붙인다
- 같은 전제로 다시 세니 반대 결론(n이 커질수록 늘어난다)이 나왔다
- 확인 방법: n=2·3 값이 이미 검증된 Step4 출력과 같은지 먼저 본다 → 같으면 세는 방법이 구현과 맞는 것

### 8.3 "단순한 설명"도 실제 쓰임으로 가중해서 다시 확인한다
- "n이 크면 선택지가 하나뿐이라 외운다" — 문맥 목록 기준 85%라 그럴듯하다
- 실제 생성 경로 기준으로는 33%뿐이었다. 진짜 원인은 BOS 패딩이 만드는 접두사 구조였다 (5.2, 5.3)

### 8.4 주석에 쓴 주장도 확인한다
- 4그램 머리말에 "두 파일을 diff하면 n이 바뀐 부분만 보인다"고 썼지만, 코드만 diff해 보니 trigram ↔ 4gram에는 **만든 방식 차이**가 섞여 있었다 (3.4)
- 동작은 같아도 학습 교재로서는 "차이 = n"이라는 약속이 깨진다. 주장은 실제 diff로 확인하고 적어야 한다

### 8.5 예시는 쓰기 전에 데이터로 확인한다
- 5.4절 초안에 "사회문화기구 = 사회문화 + 기구", "민권확장론 = 민권 + 확장론"이라고 썼다. 문서를 마무리하며 확인해 보니 **둘 다 틀렸다** ("사회문화", "확장론"은 사전에 없음. 민권확장론은 아예 조합이 아님)
- 비율(70%)은 프로그램으로 셌지만, 예시는 "그럴듯해 보이는 것"을 손으로 골라 확인 없이 붙였다
- 고친 뒤에는 프로그램이 실제로 찾은 분해만 예시로 쓴다. CSR 설명을 쓸 때 받은 지적("예시는 출처가 있어야 한다")과 같은 뿌리다

### 8.6 실행 시간 추정은 단계별로 더한다
- 검증 시간을 "60 ~ 90초"로 추정했지만 실제는 **3분 23초**였다
- Python 기준 계산(12초)만 보고, 4 ~ 6그램의 큰 출력(최대 114만 줄)과 빈도표(최대 41MB)를 읽는 비용을 빼먹었다
- 추정은 가장 큰 단계 하나가 아니라 **단계별 합**으로, 또는 작은 경우 하나를 먼저 재서 곱하기로 한다
