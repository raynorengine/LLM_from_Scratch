## 1. 무엇이 달라졌나 — 단어에서 문장으로

Step1~5까지는 **단어**를 만들었다. 국어사전 42만 단어를 재료로 `사회적교육학` 같은 것을 뽑았다.
Step6은 **문장**을 만든다. 소설 6.7만 문장을 재료로 `하고 내가 웃으며 말했다.` 같은 것을 뽑는다.

놀랍게도 **수식은 하나도 바뀌지 않는다.**

```
P(다음 글자 | 앞 n-1글자) = count(앞 n-1글자, 다음) / count(앞 n-1글자, ·)
```

Step5의 트라이그램 식과 글자 하나 다르지 않다. 바뀌는 것은 **"무엇을 한 덩어리로 보는가"** 뿐이다.

| | Step1~5 (단어 생성) | Step6 (문장 생성) |
|---|---|---|
| 한 덩어리 | 단어 하나 (`사회`) | 문장 하나 (`리자놀은 죽어 있었습니다.`) |
| BOS/EOS가 표시하는 것 | 단어의 시작·끝 | **문장**의 시작·끝 |
| 글자의 종류 | 한글 음절만 2,450종 | 공백·구두점·숫자·영문까지 **1,596종** |
| 평균 길이 | 3.69글자 | **28.04글자** (약 7.6배) |
| 재료 | `words.txt` 42만 단어 | `novel_sentences.txt` 6.7만 문장 |

실제로 바뀌는 지점은 딱 세 곳이다. 아래 2~4절이 그 세 곳이다.

## 2. 첫 번째 변화 — 공백도 글자다

### 왜 필요한가

단어를 만들 때는 빈칸이 필요 없었다. `사회적교육학`에 공백이 들어갈 자리가 없다.
문장은 다르다. `리자놀은 죽어 있었습니다` 에서 빈칸을 빼면 `리자놀은죽어있었습니다` 가 되어 문장이 아니다.

그래서 **공백과 구두점(`.` `,` `?` `!` `"` `…`)을 하나의 글자로 취급해 n그램 통계에 함께 넣는다.**

### 구현상 무슨 뜻인가 (중요)

"공백 처리 코드를 추가한다"가 아니다. **아무것도 추가하지 않는다**는 뜻이다.

공백은 그냥 글자 번호 하나(`0`번)를 받고, 세기·뽑기 코드는 그것이 공백인지 한글인지 모른다.
`step6_3gram.c`의 세기 구역에 "공백이면 이렇게 한다"는 분기가 **단 하나도 없다.**

```c
/* [8] 세기 — 공백을 위한 특별 처리가 없다 */
key = ((unsigned long long)g_seq[i] * V + (unsigned long long)g_seq[i + 1]) * V
    + (unsigned long long)g_seq[i + 2];
ht_add(&g_ht, key);
```

이게 "공백도 글자다"의 진짜 의미다. 공백을 **특별하게 다루지 않기로** 결정한 것이다.

### 실제 데이터에서 공백은 어떤 글자인가

모델이 읽는 코퍼스(`novel_sentences.txt`, 1,877,291글자) 기준이다.

| 순위 | 글자 | 빈도 | 비율 |
|---|---|---|---|
| **1위** | **(공백)** | **405,739** | **21.6%** |
| 2위 | `.` | 62,089 | 3.3% |
| 3위 | `다` | 53,638 | 2.9% |
| 4위 | `이` | 49,002 | 2.6% |
| 5위 | `는` | 37,665 | 2.0% |

공백이 **21.6%** 를 차지하는, 압도적으로 가장 흔한 글자다. 한글 `이`보다 8.3배 많다.
모델은 사실상 "언제 빈칸을 넣을지"를 가장 많이 학습한다.

(원본 `novel_test_data.txt`에는 공백이 437,534개였다. 문장으로 쪼갤 때 **문장 사이 공백
31,795개를 버렸기** 때문에 모델이 보는 코퍼스에서는 405,739개다 — 8절 참고)

그래서 **3그램만으로도 공백 위치는 자연스럽게 나온다.** 강의가 말한
*"글자가 랜덤하게 이어지지만 공백 위치 정도는 자연스럽게 나온다"* 가 이 숫자로 설명된다.

### 결과로 확인

3그램이 만든 문장이다.

```
그 끈으로 외쳤다.
테스트레일리 아니다.
사람이 갑자기가 5식민지의 식료 탱크가 새로운 지도 있었다.
```

어절 길이와 빈칸 위치는 한국어처럼 보인다. 의미는 없다. 정확히 강의가 예고한 모습이다.

## 3. 두 번째 변화 — BOS/EOS가 문장 경계로

### 질문: 반드시 BOS/EOS가 앞뒤로 있어야 하나? 구현적으로는?

**둘 다 반드시 필요하다.** 이유가 서로 다르다.

#### BOS가 n-1개 필요한 이유 — 없으면 "시작할 데가 없다"

문맥은 앞 n-1글자다. 그런데 문장의 **첫 글자**를 뽑으려 할 때 앞에 글자가 **0개**다.
채울 것이 없으면 모델에 물어볼 수가 없다. 질문 자체가 성립하지 않는다.

```
7그램으로 문장을 시작하려면 앞 6글자가 필요한데... 앞에 아무것도 없다
    ?  ?  ?  ?  ?  ?  ->  첫 글자?        (물어볼 수 없다)
  BOS BOS BOS BOS BOS BOS  ->  첫 글자      (물어볼 수 있다)
```

BOS로 채우면 `(BOS, BOS, ..., BOS)` 라는 **"문장이 아직 시작도 안 했음"을 뜻하는 문맥**이 생기고,
그 문맥 뒤에 온 글자들의 통계 = **문장 첫 글자의 분포**가 된다.

실측: 문맥 `(BOS×6)` 의 합계 = **66,961** (= 문장 수). 후보 = **831종** (문장 첫 글자로 쓰인 글자 종류).

덤으로 얻는 것이 있다. BOS 패딩 덕분에 모델이
**"문장 맨 앞의 `그`"와 "문장 중간의 `그`"를 다른 것으로 구분**한다. 앞 문맥이 다르기 때문이다.

> **대안은 없나?**
> 원본에서 아무 6글자를 골라 시작점으로 쓸 수도 있다. 하지만 그러면 문장 시작 통계를
> 전혀 배우지 못하고, 결과가 "문장 중간부터 잘라낸 것"처럼 나온다.

#### EOS가 필요한 이유 — 없으면 "끝낼 줄 모른다"

EOS가 없으면 생성이 멈출 근거가 없다. 길이 상한에서 강제로 자르는 수밖에 없고,
그러면 모든 문장이 똑같은 길이에서 뚝 끊긴다.

EOS가 있으면 모델이 통계로 배운다: **"마침표와 닫는 따옴표 다음에는 문장이 끝난다."**
그래서 생성된 문장이 `.` 나 `?"` 로 자연스럽게 마무리된다.

실제 7그램 결과를 보면 전부 종결부호로 끝난다.

```
하고 내가 웃으며 말했다.
"당신은 남을 믿을 줄 모르는 걸 어떡해?"
그로부터 한참 동안 팔짱을 끼고 있었다.
```

#### 구현: BOS/EOS는 어떻게 존재하는가

실제 글자가 아니므로 **글자 번호 뒤에 붙는 특수 번호 2개**다.

```
글자 번호:  0 (공백)  1 (!)  2 (")  ...  1595 (｣)      <- 실제 글자 1,596종
특수 번호:  1596 = BOS       1597 = EOS
            ----------------------------------------
            V = 1,598  (뽑기 후보를 훑을 때 쓰는 번호 개수)
```

이 `V = 1,598`이 뒤에서 **7그램 가능 여부를 가르는 숫자**가 된다 (5절).

#### 눈여겨볼 비대칭 하나

- **BOS는 문맥에만 나오고, 다음 글자 후보로는 절대 안 나온다.** 빈도가 0이라 뽑히지 않는다
- **EOS는 후보에 포함되고**, 뽑히면 생성이 끝난다

즉 BOS는 "입력 전용", EOS는 "출력 가능"이다.

#### 패딩 개수와 n그램 개수

문장 `나비` (2글자)를 3그램으로 처리하면:

```
패딩:  BOS BOS 나 비 EOS
3그램: (BOS,BOS,나)  (BOS,나,비)  (나,비,EOS)      ->  3개
```

**길이 L 문장 → n그램 L+1개.** n과 무관하다.

그래서 전체 n그램 수가 n=3이든 7이든 똑같다. 이건 검증에 쓸 수 있는 아주 좋은 성질이다.

```
전체 n그램 = 글자수 + 문장수 = 1,877,291 + 66,961 = 1,944,252   (n = 3, 5, 7 모두)
```

실측으로 세 n 전부 이 값이 나왔다. 패딩을 하나라도 잘못 넣으면 이 값이 깨진다.

## 4. 세 번째 변화 — 글자 테이블을 넓은 범위에서 만든다

### 질문: 여기서는 글자 table을 안 만드나? 데이터를 순회해서 만드는 것인가?

**만든다. 그리고 그렇다 — 데이터를 순회해서 만든다.** Step1~5도 같은 일을 했다.

방식은 **2-pass**다.

```
1차 순회:  데이터를 훑으며 "이 글자가 쓰였다"고 표시만 한다
              used[' '] = 1, used['가'] = 1, used['!'] = 1, ...
2차 순회:  표시된 글자에만 코드포인트 오름차순으로 0, 1, 2 ... 번호를 준다
              ' ' -> 0,  '!' -> 1,  '"' -> 2,  ...  '｣' -> 1595
              그 뒤에 BOS = 1596, EOS = 1597
```

**왜 2-pass인가?** 번호를 코드포인트 순서로 주려면 "어떤 글자들이 나오는지"를 먼저 다 알아야 한다.
한 번 훑으면서 동시에 번호를 매길 수는 없다.

### 압축 번호 — 왜 코드포인트를 그대로 안 쓰나

글자를 `U+AC00` 같은 코드포인트 그대로 번호로 쓰면 번호 범위가 **65,536개**가 된다.
실제로 쓰인 1,596개만 번호를 받게 하면 **1,598개**로 줄어든다. 이것을 **압축 번호**라고 부른다.

이게 왜 중요한가? 키 크기가 번호 개수의 거듭제곱으로 커지기 때문이다.

```
코드포인트를 그대로:  65,536^6 = 8.3 x 10^28     <- 64비트에 절대 안 들어감
압축 번호:            1,598^6  = 1.67 x 10^19    <- 64비트에 들어감
```

**압축 번호가 7그램을 가능하게 만든 핵심 장치다.** (5절에서 이어진다)

### Step5에서 바뀐 두 곳

| | Step5 (단어) | Step6 (문장) |
|---|---|---|
| 글자 표시 배열 | `used[11172]` — 한글 음절 전용 | `used[65536]` — 코드포인트 전 범위 (64KB) |
| UTF-8 디코더 | 3바이트 전용 | **1 ~ 3바이트 전부** |

두 번째가 실제로 필요했던 이유 — 실측 결과다.

| UTF-8 바이트 수 | 글자 종류 | 예 |
|---|---|---|
| 1바이트 | 80종 | 공백, `.`, `A`, `5` |
| **2바이트** | **1종** | **NBSP (U+00A0)** |
| 3바이트 | 1,515종 | 한글 음절, `“`, `…` |

2바이트 글자가 **딱 1종** 있다. NBSP 268개. 이것 하나 때문에 디코더를 확장해야 했다.

> **NBSP 함정**: Non-Breaking Space는 눈에는 공백처럼 보이지만 코드에서는 완전히 다른 글자다.
> 이 데이터는 NBSP를 **문장 안의 단어 구분 공백**으로 쓴다 (`베일리는[NB] 머릿속에서`).
> "추가 정제 안 함" 방침이라 별개 글자로 두고, 빈도표에서는 `<NBSP>` 로 적어 구분한다 (7절).
> **이 글자 하나가 분할기와 검증기 양쪽에서 함정이 됐다.** 8절 "함정 5"에서 자세히 다룬다.

실측 코드포인트 범위는 **U+0020 ~ U+FF63** 으로 전부 U+FFFF 이하였다.
그래서 `used[65536]` 배열 하나로 전부 덮인다. 해시테이블이 필요 없었다.

### 번호를 등장 순서가 아니라 코드포인트 순서로 매긴 이유

강의 2-8 [보충]은 *"처음 보는 글자가 나타날 때마다 고유한 정수 ID를 부여"* 라고 한다 (등장 순서).
이 구현은 **코드포인트 오름차순**을 쓴다. 강의와 다르게 한 것이다.

이유는 **재현성**이다.

다음 글자를 뽑을 때 후보를 **번호 순서로 훑으며 누적**한다 (6절).
번호가 실행마다 달라지면 같은 seed를 줘도 다른 글자가 뽑힌다.

- 모델의 **확률**은 어느 방식이든 똑같다 (번호는 이름표일 뿐)
- 하지만 **뽑히는 글자**는 번호 순서에 따라 달라진다

같은 seed로 결과를 재현해야 검증이 성립하므로 Step5와 같은 코드포인트 순서를 유지했다.

## 5. 7그램이 가능해진 이유 — 가장 재미있는 발견

### Step5는 왜 n ≤ 6 이 한계였나

n그램 하나를 해시테이블에 넣으려면 **키**가 필요하다. 글자 번호들을 V진법 숫자로 이어 붙여 만든다.

```
3그램 키 = (앞1 x V + 앞2) x V + 다음        <- V진법 3자리 수
```

이 키는 `unsigned long long`(64비트)에 들어가야 한다. 64비트의 최댓값은 **1.8447 x 10^19** 이다.

Step5(단어 생성)는 V = 2,452 였다. 그래서 n=6에서 문맥이 터졌다.

```
Step5:  V^6 = 2,452^6 = 2.17 x 10^20   >   2^64 = 1.8447 x 10^19    (약 12배 초과)
```

### 문장 데이터에서는 들어간다

문장 데이터는 글자 종류가 **2,450 → 1,596** 으로 줄었다. 한글 음절이 사전보다 적게 쓰인 것이다.

```
Step6:  V^6 = 1,598^6 = 1.6652 x 10^19   <   2^64 = 1.8447 x 10^19    여유 1.108배
```

**간신히 들어간다.** 여유가 11%뿐이다. 그래서 강의가 예시로 든 7그램이 가능해졌다.

| n | 문맥 크기 `V^(n-1)` (V=1,598) | 64비트 |
|---|---|---|
| 5 | 6.52 x 10^12 | 넉넉 (283만 배 여유) |
| 6 | 1.04 x 10^16 | 넉넉 (1,770배 여유) |
| **7** | **1.67 x 10^19** | **간신히 (1.108배)** |
| 8 | 2.66 x 10^22 | 초과 (1,400배) |

### 상한은 글자 종류 1,623종

`V^6 < 2^64` 를 풀면 **V ≤ 1,625**, 즉 글자 종류 **1,623종**이 상한이다.
현재 1,596종이므로 **여유가 27종뿐**이다.

이것이 "추가 정제를 하더라도 글자 종류를 늘리는 방향은 안 된다"의 이유다.
정제한다고 전각 따옴표를 새 기호로 바꾸거나 하면 7그램이 바로 깨진다.

### 왜 "조용히" 깨지는가 — 가장 무서운 부분

키가 64비트를 넘으면 **넘친 비트가 그냥 버려진다.** 오류도, 경고도 나지 않는다.

그 결과 **서로 다른 7그램이 같은 키가 되어 빈도가 합쳐진다.**
프로그램은 정상 종료하고, 문장도 멀쩡해 보이고, 통계만 틀린다.

그래서 구현에 실행마다 확인하는 검사를 넣었다. 그리고 **곱하기 전에** 나눗셈으로 확인한다.

```c
/* V를 6번 곱하되, 곱하기 전에 "넘칠 것인가"를 나눗셈으로 확인한다.
   먼저 곱해 버리면 넘친 뒤라 검사 자체가 무의미해진다 */
for (i = 0; i < 6; i++) {
    if (V == 0 || acc > cap / V) {
        /* 오류로 종료 */
    }
    acc *= V;
}
```

**"넘쳤는지 확인하려고 곱해 보면 이미 늦었다"** — 이게 오버플로 검사의 기본 요령이다.

### n=7만 키를 쪼갠다

7그램 키를 숫자 하나로 만들면 `V^7 = 2.66 x 10^22` 으로 터진다.
그래서 **문맥과 다음 글자를 따로 저장**한다.

```
n = 3, 5 :  keys[칸] = V진법 n자리 수 하나          (키 1개)
n = 7    :  ctxs[칸]  = 앞 6글자 (V진법 6자리)      (키 2개로 쪼갬)
            nexts[칸] = 다음 글자 번호
```

"같은 n그램인가?"를 판단할 때 **문맥과 다음 글자를 둘 다 비교**한다.

### 해시 값은 넘쳐도 되고, 키는 안 된다

이게 처음 보면 혼란스러운 부분이다. 칸 번호를 정할 때는 `문맥 x V + 다음` 을 쓰는데,
이 값은 **넘쳐도 괜찮다.**

| | 역할 | 넘치면? |
|---|---|---|
| **키** (문맥, 다음) | "이 둘이 같은 n그램인가"를 판단하는 **신분증** | 서로 다른 n그램이 같아져 버린다 → **치명적** |
| **해시 값** | "어느 칸부터 찾아볼지"만 정하는 **출발점** | 두 n그램이 같은 칸에서 출발할 뿐 = 그냥 충돌 → **괜찮다** |

충돌이 나도 키(문맥+다음)를 직접 비교해 구분하므로 섞이지 않는다.
**"신분증은 유일해야 하지만, 집 주소는 겹쳐도 된다"** 정도로 이해하면 된다.

## 6. 뽑기 — 문맥 다음 글자를 어떻게 고르나

해시테이블은 `"이 n그램이 몇 번 나왔나?"` 에는 바로 답한다.
하지만 `"이 문맥 다음에 올 수 있는 글자 목록"` 은 **모른다.** 키가 칸 전체에 흩어져 있기 때문이다.

그래서 **가능한 다음 글자 1,598개를 전부 물어본다.**

```
문맥 (그, 러) 다음에 올 글자를 뽑는 과정

1) 합계 구하기:  b = 0 ~ 1,597 전부 조회해 횟수를 더한다
2) 난수:         r = 0 ~ (합계 - 1)
3) 고르기:       b = 0, 1, 2 ... 순서로 다시 조회하며 누적하다가
                 "누적 > r" 이 되는 첫 b 를 고른다
```

나온 적 없는 후보는 0이 돌아와 누적이 그대로이므로 뽑히지 않는다.

### `>` 와 `>=` 의 차이가 전부를 가른다

문맥 `(가, 로)` 뒤에 `수` 2번, `등` 1번이 나왔다고 하자. 합계 3, r은 0~2.

```
후보를 번호 순으로 누적:   ... 등에서 1 ... 수에서 3  (나머지는 0이라 그대로)

'>' 로 비교 (올바름)                 '>=' 로 비교 (틀림)
  r=0 -> 1 > 0  첫 참 = 등  (1/3)     r=0 -> 0 >= 0 이 번호 0번(공백)에서 이미 참!
  r=1 -> 3 > 1  첫 참 = 수             -> 한 번도 안 나온 글자가 뽑힌다
  r=2 -> 3 > 2  첫 참 = 수  (2/3)     r=1 -> 1 >= 1  등  (수의 몫을 등이 가져감)
```

`>=` 를 쓰면 **두 가지가 동시에 망가진다.**

1. `r = 0` 일 때 누적이 0인 후보(한 번도 안 나온 글자)가 뽑힌다
2. 구간이 한 칸씩 밀려 확률이 전부 어긋난다

이 한 글자가 모델 전체의 정확성을 결정한다. 그래서 검증에서 **구간의 양 끝을 콕 찔러 본다** (9절).

## 7. 공백을 빈도표에 어떻게 적나 — Step6에서 새로 생긴 문제

빈도표는 한 줄이 n그램 하나이고 **탭으로 열을 구분**한다.

```
prev1	prev2	next	count	percent
```

그런데 공백이 글자다. 그대로 쓰면 이렇게 된다.

```
     	그	러	12	4.521739        <- 첫 열이 공백인데 빈 칸처럼 보인다
```

사람도 검증기도 **열을 구분할 수 없다.** 그래서 **표시 이름**을 쓴다.

| 글자 | 표시 이름 |
|---|---|
| 스페이스 | `<SP>` |
| NBSP (U+00A0) | `<NBSP>` |
| 제어문자 | `<U+XXXX>` |
| BOS / EOS | `BOS` / `EOS` |
| 그 외 전부 | 글자 그대로 (`가`, `.`, `"`, `A`) |

```
<SP>	그	러	12	4.521739        <- 구분된다
```

**꺾쇠를 쓸 수 있었던 근거**: 데이터에 `<` 와 `>` 가 **없음을 전수 확인**했다.
만약 `<` 가 데이터에 있었다면 `<SP>` 가 실제 글자와 구별되지 않아 다른 표기를 찾아야 했다.
이렇게 "표기를 정할 때는 그 표기가 데이터와 충돌하지 않는지 먼저 확인한다."

### 단, 결과 파일의 문장은 글자 그대로

빈도표는 기계가 읽는 표이지만 결과 파일은 **사람이 문장을 읽는 용도**다.
그래서 결과 파일에는 진짜 공백을 쓴다.

```
빈도표:     <SP>	그	러	12	4.521739
결과 파일:  1	하고 내가 웃으며 말했다.
```

같은 데이터를 **독자에 따라 다르게 표기**하는 것이다.

## 8. 문장 분할 — 원본은 "한 줄 = 한 문장"이 아니었다

### 왜 쪼개야 했나

원본 `novel_test_data.txt`는 한 줄에 여러 문장이 뭉쳐 있었다.

```
줄 길이:  평균 54.49글자 / 중앙 37 / 최대 4,104글자
```

한 줄을 한 문장으로 쓰면 모델이 **"마침표 뒤에도 문장이 계속된다"** 를 배운다.
그러면 EOS가 희박해져 생성이 잘 끝나지 않는다. 최대 4,104글자짜리 "문장"도 생긴다.

그래서 종결부호(`.` `!` `?` `…`)로 쪼개 **66,961문장** (평균 28.04글자) 으로 만들었다.

### 핵심 설계 결정: 분할을 C에 넣지 않았다

분할을 C 프로그램 안에 넣고, 검증 프로그램도 같은 분할을 하게 하면 어떻게 될까?

**둘이 같은 분할 버그를 함께 갖게 된다.** 그러면 검증이 통과해도 아무 의미가 없다.
`CLAUDE.md`의 검증 규칙 2번 *"같은 로직을 복사하면 같은 버그를 함께 가지므로 검증이 아니다"* 가
바로 이 상황을 막으려는 규칙이다.

그래서 **전처리로 분리**했다.

```
novel_test_data.txt  --(step6_prepare.py, 1회)-->  novel_sentences.txt
                                                        |
                              +-------------------------+-------------------------+
                              |                                                   |
                       C 프로그램 (모델을 만든다)                    검증 프로그램 (모델을 따진다)
```

분할은 **한 번만** 하고, C와 검증기는 **같은 파일**을 읽는다. 분할 규칙이 검증을 오염시킬 여지가 없다.

### 분할에서 실제로 걸린 함정 4개

소박하게 `.?!` 로 쪼개면 깨진다. 전부 "원본 글자가 결과에 안 담긴 것"으로 드러났다.

1차 시도:  “아리스, 눈을 떠 보아요.

**비대칭이다.** 여는 따옴표가 3배 넘게 많다. 즉 **`“` 가 닫는 역할도 하고 있다.**

그 결과 `.“` 로 끝나는 줄이 **13,419건** 있었고, 거기서 **외톨이 `“` 조각 1,553개**가 생겼다.

처음 설계는 "글자 없는 조각(`“` 같은 것)은 버린다"였는데, **그게 곧 손실이었다.**
→ "버리지 않고 **앞 문장에 붙인다**"로 바꿔 손실 0을 달성했다.

### 손실 검사 — 무엇을 어떻게 비교하나

`step6_prepare.py`에 검사를 박아 두었다. 글자를 **두 부류로 나눠 다른 기준**을 적용한다.

```
모든 글자를 종류별로 전수 집계해 원본과 결과를 비교한다

  버려도 되는 공백 (ASCII 스페이스·탭)
      -> 줄어드는 것은 허용. 몇 개가 줄었는지 보고한다
      -> 늘어나면 실패

  그 밖의 모든 글자 (NBSP 포함)
      -> 하나라도 변하면 실패 (늘어도, 줄어도)
```

- **종류별로 전수 집계하는 이유**: 합계만 비교하면 "`A` 하나 사라지고 `B` 하나 늘어난" 경우를 못 잡는다
- **상위 몇 개만 보지 않는 이유**: NBSP 268개, `｣` 6개처럼 **드문 글자에서 난 손실**이 실제 버그였다
- **"버려도 되는 공백"을 좁게 정의한 이유**: 이게 이번에 실제로 걸린 함정이다. 바로 다음 절

검사를 통과하지 못하면 **파일을 쓰지 않고** 종료 코드 1로 끝낸다.
통과하지 못한 파일을 남기면 그걸 입력으로 쓴 모든 결과가 의심스러워지기 때문이다.

최종 결과:

```
모든 글자 비교:  원본 1,909,086  ->  결과 1,877,291
                 차이는 U+0020 31,795자 제거뿐 (문장 사이 공백, 의도됨)
                 NBSP 268개를 포함한 나머지 모든 글자는 개수가 완전히 같다
```

### 함정 5. 검사가 볼 수 없는 영역이 있었다 — NBSP

위 검사는 처음에 이렇게 되어 있었다.

```python
before = Counter(ch for ch in 원본 if not ch.isspace())    # 공백류를 아예 제외
after  = Counter(ch for ch in 결과 if not ch.isspace())
```

"공백은 일부러 버리니까 검사에서 빼자"는 생각이었다. 여기에 **맹점**이 있었다.

**Python의 `str.isspace()`는 NBSP(U+00A0)도 공백으로 본다.**

```python
" ".isspace()   # True
```

그런데 이 데이터는 NBSP를 **문장 안의 단어 구분 공백**으로 쓴다 (실측 268개).

```
베일리는[NB] 머릿속에서 우주인...
국장은 몹시 불안한[NB] 태도로 말했다.
```

NBSP는 모델에서 **자기 글자 번호를 받는 실제 글자**다. 그런데 분할기가 경계에서
`isspace()`로 공백을 건너뛸 때 NBSP도 함께 버렸고, **검사는 공백류를 아예 보지 않으니
"손실 0"이라고 보고했다.** 실제로는 31개가 사라져 있었다.

더 고약한 것은 **이 검사가 그 부류에 대해 아무것도 보장하지 못한다**는 점이다.
어떤 버그가 NBSP를 전부 날려도, 공백을 엉뚱하게 끼워 넣어도 조용히 통과한다.

#### 고치는 과정에서 한 번 더 걸렸다

1차 수정: "공백류는 **줄어드는 것만** 허용하고, 늘어나면 실패" 로 바꿨다.
→ **여전히 NBSP를 못 잡았다.** "공백류"라는 분류가 NBSP까지 덮고 있었기 때문이다.

2차 수정(최종): **"버려도 되는 공백"을 `isspace()`가 아니라 ASCII 스페이스·탭으로 한정**했다.

```python
SKIPPABLE_WS = " 	"      # 이것만 경계에서 버릴 수 있다. NBSP는 데이터 글자다
```

- 분할기: 경계에서 `SKIPPABLE_WS`만 건너뛴다 → NBSP 268개 **전부 보존**
- 검사: `SKIPPABLE_WS`만 감소를 허용 → NBSP가 사라지면 **FAIL**
- `.strip()`도 `.strip(SKIPPABLE_WS)`로 바꿨다. `strip()`은 양 끝의 NBSP까지 떼낸다

#### self-test에 맹점 검사를 추가했다

고친 뒤 "정말 잡히는가"를 확인하는 검사를 넣었다.

```
4a. 원본에는 NBSP가 있고 결과에는 없는 입력을 준다  -> FAIL이 나와야 한다
4b. 결과에 공백을 일부러 더 넣은 입력을 준다        -> FAIL이 나와야 한다
```

예전 설계에서는 **둘 다 조용히 통과했다.** 지금은 둘 다 FAIL을 낸다.

```
[self-test] 4a. NBSP가 사라지면 FAIL이 나와야 한다 (공백류 맹점 점검)
  OK: U+00A0 NO-BREAK SPACE: 원본 4 -> 분할 0
[self-test] 4b. 공백이 늘어나면 FAIL이 나와야 한다
  OK: U+0020 SPACE: 원본 17 -> 분할 21
```

#### 여기서 배울 것

> **"검사에서 제외한다"는 결정은 "그 부류는 앞으로 아무도 안 본다"는 뜻이다.**

제외할 때는 **제외 범위를 최소로, 명시적으로** 잡아야 한다.
`isspace()` 처럼 **남이 정한 분류**를 그대로 쓰면 그 분류에 뭐가 들어 있는지 모르는 채
검사 범위가 뚫린다. 이번에는 "`isspace()` 안에 NBSP가 있다"는 것을 몰라서 뚫렸다.

그리고 **고친 뒤에는 반드시 "원래 못 잡던 것을 이제 잡는가"를 확인**해야 한다.
1차 수정은 그럴듯했지만 실제로는 아무것도 바뀌지 않았다. self-test를 돌려 보고서야 알았다.

### 질문: "소실"이라니, 글자가 없어졌다는 건가?

**원본 파일은 전혀 건드리지 않았다.** `novel_test_data.txt`는 지금도 그대로다.
"소실"은 **내가 만든 결과물에 원본 글자가 안 담긴 것**을 가리킨 말이었다.

읽기 → 변환 → 쓰기 과정에서 **입력에 있던 것이 출력에 없으면** 그게 손실이다.
원본을 지우는 것과는 전혀 다른 일이다.

> 이 질문에서 내 설명의 오류도 하나 드러났다 (11절 교훈 1번).

## 9. 검증 — 어떻게 "맞다"고 말할 수 있나

검증기는 C와 **다른 방식**으로 센다. 같은 로직을 베끼면 같은 버그를 공유한다.

| | C 구현 | 검증 프로그램 |
|---|---|---|
| n그램을 표현하는 방법 | 글자를 번호로 바꿔 **V진법 정수 키** | **문자열 슬라이스** (`padded[i:i+n]`) |
| BOS/EOS | 번호 1596 / 1597 | 데이터에 없는 문자 `U+0000` / `U+0001` |
| 문장 경계 처리 | 전체를 한 배열로 잇고 "문맥에 EOS 있으면 건너뛴다" | **문장마다 따로** 패딩해서 센다 |

방식이 다르지만 결과는 같아야 한다. 경계 처리에 버그가 있으면 여기서 어긋난다.

### 검사 8종과 각각이 잡는 것

| 검사 | 무엇을 보나 | 이게 잡는 버그 |
|---|---|---|
| **[1] 규모** | 문장·글자·종류·V·전체·서로다른·문맥 수 | 읽기 단계의 오류 |
| | 특히 `전체 = 글자수 + 문장수` | **패딩 개수 오류** (BOS를 n개 넣는 등) |
| **[2] --dump** | n그램 **전체**의 키 집합과 빈도 | 해시 충돌 처리 오류, **키 겹침(오버플로)** |
| **[3] --rows** | 문맥 합계 전수 | 난수 범위 오류 |
| **[4] 빈도표** | 파일을 **바이트 단위로** 비교 | 정렬 순서, 확률 반올림, 표기 — 전부 한꺼번에 |
| **[5] --map** | 누적 구간의 **양 끝** r | `>` vs `>=` 밀림 |
| **[6] --hist** | 20만 번 뽑아 분포가 비례하는지 | 난수 편향 |
| **[7] 소스 목차** | 머리말 목차의 줄 번호 | 문서와 코드의 불일치 |
| **[8] 결과 파일** | **생성 문장의 모든 n그램이 코퍼스에 있는지** | **생성 로직 오류** |

### 특히 잘 설계된 검사 세 개

#### [4] 바이트 비교 — 가장 강한 검사

빈도표를 "읽어서 숫자만 맞춰 보는" 방식으로는 정렬이 한 줄 밀린 것을 못 잡는다.
**표 전체를 독립적으로 만들어 바이트로 비교하면** 한 글자만 달라도 걸린다.

```
3그램  4,084,564 바이트   전부 일치
5그램 27,124,782 바이트   전부 일치
7그램 55,294,038 바이트   전부 일치
```

C의 `fprintf("%.6f")` 와 Python의 `f"{x:.6f}"` 가 같은 반올림 규칙(IEEE 754)을 쓰기 때문에
확률 문자열까지 똑같이 나온다.

#### [5] 왜 구간의 "양 끝"만 찌르나

후보 `c` 가 차지하는 구간이 `[p, p+k)` 라면 `r = p` 와 `r = p+k-1` 두 개만 물어본다.

**가운데 값은 구간이 밀려도 같은 후보가 나올 수 있어서 버그를 못 잡는다.**
경계만 정확히 찌르면 밀림을 반드시 잡는다. 적은 질의로 최대 효과를 내는 방법이다.

```
3그램 69,468건 / 5그램 39,654건 / 7그램 24,232건   전부 일치
```

#### [8] 생성 로직을 "결과만 보고" 검증하는 방법

생성 과정을 흉내내지 않고도 생성이 맞았는지 확인할 수 있다.

> 모델은 **센 n그램만 뽑을 수 있다.**
> 따라서 생성된 문장을 쪼갰을 때 나오는 n그램이 하나라도 코퍼스에 없으면 그건 버그다.

문맥 창을 두 칸씩 밀거나, 창 밀기 순서를 틀리면 코퍼스에 없는 n그램이 섞여 **반드시 걸린다.**
생성 코드를 한 줄도 안 보고 결과만으로 검증하는, 아주 경제적인 검사다.

### self-test — 검증기도 검증해야 한다

"통과"만 찍는 검증기는 검증기가 아니다. **틀린 입력에 FAIL을 내는지** 먼저 보여야 한다.

```
빈도 하나를 1 올린다        -> 바이트 비교가 7번째 줄에서 차이를 잡아냄     OK
n그램 하나를 지운다          -> 8번째 줄에서 차이를 잡아냄                  OK
표시 이름 규칙을 바꾼다      -> 1277번째 줄에서 차이를 잡아냄               OK
닫는 따옴표를 일부러 지운다  -> 손실 1종 적발                              OK
```

FAIL이 나오면 self-test는 **성공**이다. FAIL이 안 나오면 그 검사는 아무것도 못 잡는 것이므로 실패다.

## 10. 결과 해석 — n이 커지면 무슨 일이 일어나나

### 실측 규모

| n | 패턴수 (서로 다른 n그램) | 문맥 수 | 세기 시간 | 생성(15개) | 메모리 | 빈도표 |
|---|---|---|---|---|---|---|
| 3 | 171,051 | 38,032 | 10.9ms | 7.5ms | 6.3MB | 4.08MB |
| 5 | 821,221 | 473,641 | 41.6ms | 11.6ms | 25.2MB | 27.1MB |
| 7 | 1,319,934 | 1,092,883 | 76.1ms | 14.4ms | 67.1MB | 55.3MB |

- 패턴수는 n이 커질수록 늘지만 **증가 폭은 줄어든다** (3→5 +380%, 5→7 +61%)
- 가능한 조합은 V배씩 늘어나는데 실제 n그램은 132만 개에서 멈춘다 → **데이터에 있는 것만 저장**하는 해시테이블의 이점
- 세기 시간은 n에 비례해 늘지만(창이 길어져서), 생성 시간은 거의 늘지 않는다.
  한 글자 뽑는 비용은 **후보 수 1,598개**로 정해지고 n과 무관하기 때문이다

### 생성 품질 (seed 1792649450, 각 15문장)

**3그램** — 얼핏 문장 같지만 의미가 없다

```
행진이 보도했다.
테스트레일리 아니다.
그러면 엉덩이에 있었다.
"그럼, 우주선을 배멀미를 떠올랐다.
```

**5그램** — 구절 단위로 읽히기 시작한다

```
카디스 박사의 주위를 돌고 있다가, 이런 것들을 통해서 빠져 나왔다.
그러나 저는 발견되지 않아도 되는 깊은 숲이 있었다.
소리에는 두 사람은 비행기를 몰아, 앞질러 가려는 것이었다.
```

**7그램** — 원본 소설의 문체가 느껴진다

```
하고 내가 웃으며 말했다.
"당신은 남을 믿을 줄 모르는 걸 어떡해?"
둘이 제트 함정에서 올라오니, 거기에는 커다란 구멍이 뚫려 있었다.
```

강의가 예고한 n별 특징이 **실제로 재현됐다.**

### 암기가 시작된다 — 7그램에서 20%

생성 문장이 원본에 **통째로** 있는 비율이다.

| n | 원본 그대로 | 그 문장 |
|---|---|---|
| 3 | 0 / 15 = 0.0% | — |
| 5 | 1 / 15 = 6.7% | `"괜찮습니다.` |
| **7** | **3 / 15 = 20.0%** | `"기운을 내요."` · `“그럼 가봐.` · `"좋습니다.` |

원본 그대로 나온 것은 **전부 짧은 대화문**이다. n=5에서 이미 하나 나왔고, n=7에서 셋이 됐다.

**왜 짧은 문장이 그대로 나오는가?**

7그램의 문맥은 앞 6글자다. 문장이 6글자 이하면 **문맥이 BOS 패딩으로 거의 다 덮인다.**

```
"좋습니다.  (6글자)

첫 글자를 뽑을 때:   (BOS BOS BOS BOS BOS BOS)  ->  "
둘째를 뽑을 때:      (BOS BOS BOS BOS BOS  " )  ->  좋
셋째를 뽑을 때:      (BOS BOS BOS BOS  "  좋)  ->  습
```

문맥이 "문장 처음부터 지금까지 전부"를 담고 있다.
그러면 그 문맥을 가진 n그램은 원본의 그 문장 하나뿐일 가능성이 높고,
**원본을 그대로 복원할 수밖에 없다.**

> **Step5에서 본 것과 같은 현상이다.**
> education/06 5.2 *"BOS n-1 패딩 때문에 길이 n-2 이하 생성 단어는 반드시 사전 단어"* —
> 단어에서 본 것이 문장에서 그대로 반복된다. 단위만 바뀌었을 뿐 원리가 같다.

### 일반화 vs 암기 — 그래서 n은 몇이 좋은가

education/06에서 본 트레이드오프가 여기서도 그대로 나타난다.

```
n 이 작으면  ->  패턴이 부족해 의미 없는 글자 나열 (3그램)
n 이 크면    ->  훈련 데이터를 그대로 외운다       (7그램에서 20%)
```

문장 생성에서는 이 트레이드오프가 **단어보다 완만하다.**
단어는 평균 3.69글자라 n=6에서 100% 암기였지만,
문장은 평균 28.04글자라 n=7에서도 20%다. **덩어리가 길면 외우기 어렵다.**

### 평가 지표를 바꿔야 했던 이유

Step5는 **사전 일치율을 길이별로** 쪼개 봤다 (1글자, 2글자, ... 10글자 이상).
문장에는 그대로 쓸 수 없다.

- 단어는 3.69글자라 같은 길이의 단어가 수백~수천 개씩 있어 길이별 비율이 의미 있었다
- 문장은 평균 28글자에 최대 358글자라 **길이별로 나누면 칸마다 표본이 몇 개뿐**이다

그래서 전체 일치율만 센다. 강의도 이 어려움을 인정한다 —
*"데이터양이 많아지기 때문에 생성된 결과가 원본 텍스트에 있는 문장인지 확인하기가 단순하지 않다."*

그리고 **"그럴듯한 새 문장인지"는 숫자로 재지 못한다.**
결과 파일의 문장을 사람이 직접 읽어 판단해야 한다. 강의의 평가도 정성적이다.

## 11. AI와 작업하며 얻은 교훈

### 1. 숫자를 보고할 때 "의도된 동작"과 "버그"를 섞지 말 것

처음에 손실을 **44,760자**라고 보고했다. 사용자가 *"이게 뭔소리인지 모르겠다"* 고 물어
다시 재니 실제로는 **12,942자**였다.

44,760은 **공백을 포함해 센 값**이었고, 그중 약 41,017자는
"문장 사이 공백을 **일부러** 버린 것"이라 버그가 아니었다.

- 검사 자체는 공백을 제외하고 했는데(공백은 의도적으로 버리므로), 보고할 때 포함한 수를 썼다
- **의심해야 할 신호**: 숫자가 비정상적으로 크면 "그 안에 정상 동작이 섞인 게 아닌가" 를 먼저 보라

그리고 "소실"이라는 말도 부정확했다. 원본이 훼손된 것처럼 읽힌다.
**"결과물에 안 담겼다"** 가 맞는 표현이었다.

### 2. 검증기가 내 추측을 잡아냈다

C 파일 머리말의 목차 줄 번호(`[1] 78줄 | 설정값과 전역 상태`)를 **추측으로 적었다.**
`[7]` 검사가 15개 구역 전부 어긋남을 보고했다.

```
FAIL [7] step6_3gram.c 목차 줄 번호
     (구역 15개 / 어긋남 15개 (구역, 적힌줄, 실제줄) = [(1, 76, 78), (2, 147, 140), ...])
```

- **사람이 눈으로 맞추면 반드시 틀리는 종류의 일**은 검증기에 맡겨야 한다
- 이 검사가 없었으면 틀린 목차가 그대로 남아 나중에 읽을 때 헤맸을 것이다

### 3. "검증 대상"을 빠뜨리지 말 것 — 빈도표

처음 올린 구현 계획에 **빈도표가 없었다.** 결과 파일과 비교 파일만 있었다.

빈도표는 단순 부산물이 아니다. **검증의 핵심**이다 — 전수 비교가 성립하는 지점이 거기다.
모델 전체를 사람이 읽을 수 있는 형태로 꺼내 놓는 것이고, 그게 있어야
"모델이 맞다"를 바이트 단위로 증명할 수 있다.

### 4. 의심스러운 수치는 확인하고 넘어가라 — 좋은 사례

검증 결과에서 n=5와 n=7의 `--hist` 수치가 **완전히 동일**했다.

```
n=5:  후보 831개 중 최대 편차 3.62시그마 (8: 관측 84 기대 56.7)
n=7:  후보 831개 중 최대 편차 3.62시그마 (8: 관측 84 기대 56.7)
```

값을 복사한 버그로 의심해 확인했다. 결과:

| n | 후보 최다 문맥 | 후보 | 합계 |
|---|---|---|---|
| 3 | `는 ` (는+공백) | 837종 | 34,922 |
| 5 | `BOS×4` | 831종 | 66,961 |
| 7 | `BOS×6` | 831종 | 66,961 |

n=5와 n=7 모두 **"문장 시작 문맥"** 이 뽑혔고, 문장 첫 글자의 분포는 **n과 무관하게 같다.**
seed도 같으니 히스토그램이 동일한 것이 **맞았다.** 버그가 아니었다.

- **얻은 것**: 같은 수치가 두 번 나오면 의심하되, 확인하고 결론을 내릴 것
- **개선**: 혼동을 막으려고 검증 출력에 **고른 문맥을 함께 찍도록** 바꿨다.
  `문맥 'BOSBOSBOSBOSBOSBOS' / 합계 66,961 / 후보 831개` — 이제 왜 같은지 출력만 봐도 안다

### 5. 검사에서 제외한 것은 아무도 안 본다 (NBSP 사건)

이번 세션에서 가장 값진 교훈이다. 자세한 경위는 8절 "함정 5"에 있고, 여기서는 교훈만 정리한다.

손실 검사를 `if not ch.isspace()` 로 써서 공백류를 통째로 제외했다.
그런데 `isspace()` 안에는 **NBSP가 들어 있고**, 이 데이터는 NBSP를 실제 글자로 쓴다.
그래서 NBSP 31개가 사라졌는데도 검사는 **"손실 0"** 이라고 보고했다.

- **교훈 1**: "검사에서 제외한다"는 결정은 **"그 부류는 앞으로 아무도 안 본다"** 는 뜻이다.
  제외 범위는 최소로, 그리고 **내가 직접 열거해서** 잡아야 한다
- **교훈 2**: `isspace()` `isalpha()` 처럼 **남이 정한 분류**를 검사 범위에 쓰면
  그 안에 뭐가 들어 있는지 모르는 채로 구멍이 생긴다
- **교훈 3**: 1차 수정("공백류는 줄어도 된다")은 그럴듯했지만 **아무것도 바뀌지 않았다.**
  분류가 여전히 NBSP를 덮고 있었다. **고친 뒤에는 "원래 못 잡던 것을 이제 잡는가"를
  반드시 확인**해야 한다. self-test를 돌려 보고서야 알았다
- **교훈 4**: 이 결함은 **문서를 쓰려고 숫자를 다시 재다가** 발견됐다.
  "공백이 437,534개"라고 쓰려다 "그게 원본 기준인가 분할본 기준인가"를 확인한 것이 계기였다.
  **숫자의 출처를 따지는 습관이 결함을 찾아낸다**

### 6. 또 추측으로 숫자를 썼다

이 문서를 쓰면서 `--map` 질의 수를 **69,470 / 39,664** 라고 적었다. 실제는 **69,468 / 39,654** 였다.
기억에 남은 자릿수에 그럴듯한 값을 채운 것이다.

- 코퍼스가 55자 늘었으니 질의 수도 당연히 바뀌는데, 재지 않고 **예전 값을 어림해서 적었다**
- 교훈 4와 같은 뿌리다: **확인하지 않고 그럴듯한 값을 채워 넣는 습관**
- 이 저장소의 education 문서는 나중에 코드와 대조하며 읽게 된다. 지어낸 숫자는 그때 혼란을 만든다

### 7. 설명이 불명확하면 같은 질문이 두 번 온다

`"table은 누가 만드는데???"` 를 두 번 물어봤다. 내 설명의 문제였다.

- 파일 목록을 `step6_3gram_table.txt   (5, 7)` 처럼 **줄여 적어서** 3그램 표 하나만 만드는 것처럼 읽혔다
- `prepare.py`(입력 데이터를 만든다)와 빈도표(모델을 꺼낸다)를 **한 문단에 섞어** 썼다

고친 방법: 파일을 줄이지 않고 **전부 나열** + **역할 분담 표** + **실행 순서** +
실제 `step5_trigram_table.txt` 앞부분을 **보여 주기**.

**추상적인 설명이 안 통하면 실물을 보여 주는 것이 가장 빠르다.**

## 12. 복습용 핵심 정리

### 단어 → 문장, 바뀌는 것 3가지

1. **공백도 글자다** — 특별 처리를 **추가하지 않는** 것이 핵심. 공백은 그냥 번호 0번
2. **BOS/EOS가 문장 경계** — BOS n-1개는 "시작할 데"를, EOS는 "끝낼 근거"를 준다
3. **글자 번호를 넓은 범위에서** — `used[11172]` → `used[65536]`, UTF-8 1~3바이트

### 꼭 기억할 숫자

| 값 | 의미 |
|---|---|
| **1,596종** | 실제로 쓰인 글자 (한글 1,497 + 비한글 99) |
| **1,598 = V** | BOS/EOS 포함. 뽑기 후보 수이자 키의 진법 |
| **66,961문장 / 1,877,291글자** | 분할 후 코퍼스 (평균 28.04글자) |
| **1,944,252** | 전체 n그램 수. **n과 무관** (= 글자수 + 문장수) |
| **1,623종** | 7그램을 유지할 수 있는 글자 종류 상한 (여유 27종) |
| **1.108배** | `2^64 / V^6`. 7그램 키의 여유 |

### 원리 다섯 가지

1. **길이 L 문장 → n그램 L+1개** (n과 무관). 패딩 오류를 잡는 검산식
2. **압축 번호가 7그램을 가능하게 한다.** 코드포인트 그대로면 `65536^6`, 압축하면 `1598^6`
3. **키는 유일해야 하고, 해시 값은 겹쳐도 된다.** 신분증 vs 집 주소
4. **오버플로는 곱하기 전에 나눗셈으로 확인한다.** 곱해 보면 이미 늦다
5. **누적 비교는 `>` 다.** `>=` 면 한 번도 안 나온 글자가 뽑히고 확률이 밀린다

### 검증에서 배울 것 네 가지

1. **다른 방식으로 구현하라.** C는 정수 키, 검증기는 문자열 슬라이스
2. **바이트 단위 전수 비교**가 가장 강하다. 정렬·반올림·표기를 한꺼번에 검증
3. **경계를 찔러라.** 구간의 양 끝만 물어보면 밀림을 반드시 잡는다
4. **결과만으로 생성 로직을 검증할 수 있다.** "생성된 n그램이 코퍼스에 있는가"
5. **검증기도 검증하라.** 틀린 입력에 FAIL이 나오는 것까지 확인해야 "통과"를 신뢰할 수 있다

### 다음 강의 예고

지금까지는 **글자** 단위였다. 다음은 **단어(토큰)** 단위로 간다.
한국어는 조사가 붙는 **교착어**라 `사람이` `사람을` `사람은` 이 다 다른 단어로 보인다.
그래서 **형태소 분석기**로 의미 있는 단위로 쪼갠 뒤 n그램을 센다.

그때 **"처음 보는 토큰마다 정수 ID를 부여"** 하는 방식을 쓰는데,
그건 이번 4절에서 글자에 번호를 매긴 것과 **완전히 같은 원리**다 (강의 2-8 [보충]).
이번에 글자 테이블을 이해해 두면 그때 토큰 테이블은 그냥 단위만 바뀐 것으로 보인다.
