# 바이그램 — 앞 글자를 보고 다음 글자를 뽑기

## 복습용 핵심 정리

> **한 줄 요약**: 바이그램은 "앞 글자별 확률표 + 표를 바꿔 가며 뽑기"다. 유니그램의 표 1개가 앞 글자마다 하나씩, 2,451개로 늘어난다. 모델 자체는 단순하지만 **표가 대부분 0(97%)이라 어떻게 저장하고 어떻게 뽑느냐**가 구현의 핵심이고, 같은 모델을 배열 / 해시 / 해시+CSR 세 가지로 구현해 보면 **결과는 글자 하나까지 같고 속도·메모리만 다르다**.

### 개념
- **P(다음 | 앞) = count(앞, 다음) / count(앞, ·)** — 조건부 확률. n=2인 N-그램
- 쌍은 **단어 안에서만** 2글자 창(슬라이딩 윈도우)으로 센다
- **BOS/EOS**: 단어 시작·끝 표시. 문자열이 아니라 한글과 겹치지 않는 **번호 하나**. 덕분에 "어떤 글자로 시작하나", "어디서 끝나나"를 배우고, 길이를 정하지 않아도 EOS가 나오면 단어가 끝난다
- 확률표 = 앞 글자마다 1개 → **2,451개**(글자 2,450 + BOS). 각 표의 합 = 그 글자의 유니그램 빈도
- 탐욕적 디코딩 → 매번 **"사"**. BOS 다음 1위가 '사'이고, **'사' 다음 1위가 EOS**이기 때문 (강의는 앞 절반만 설명)

### 저장 구조 — "없는 것은 만들지 않는다"의 두 단계
| 단계 | 버리는 것 | 방법 | 크기 |
|---|---|---|---|
| 0 | 없음 | 11,172² 배열 | 약 500MB |
| 1 | 안 쓰는 글자 8,722종 | 압축 번호 + 2,452² 배열 | 약 24MB |
| 2 | 쓰는 글자끼리라도 안 붙는 쌍(97%) | 해시테이블 / CSR | 4.2MB / 1.4MB |

### 세 구현 비교 (실측, result_01)
| | ① 배열 | ② 해시만 | ③ 해시 + CSR |
|---|---|---|---|
| 세기 | `freq[a][b]++` | 해시에 +1 | 해시에 +1 |
| 뽑기 | 행 2,452칸을 앞에서부터 누적 | 후보 2,452개를 해시에 하나씩 물어보며 누적 | 행 구간 안에서 이진 탐색 |
| 10,000개 생성 | 27.7ms | **485.0ms** | **3.7ms** |
| 메모리 | 24.07MB | 4.21MB | **1.38MB** |
| 결과 | 세 구현 모두 **완전히 같음** | | |

## 1. 바이그램이란

### 유니그램과의 차이
| | 유니그램 | 바이그램 |
|---|---|---|
| 세는 것 | 글자 하나의 빈도 | **두 글자 짝**의 빈도 |
| 질문 | 어떤 글자가 많이 나오나 | 어떤 글자 **다음에** 어떤 글자가 많이 오나 |
| 확률 | P(글자) | **P(다음 \| 앞)** — 조건부 확률 |
| 문맥 | 없음 | 바로 앞 글자 1개 |

- 유니그램은 '다'가 많을 뿐 글자끼리 이어지지 않았다 ("다다다다", "기멀시혁기"). 바이그램은 앞 글자를 조건으로 다음 글자를 고르므로 **글자끼리 이어지는 첫 단계**다.
- 강의 비유: **두 글자 끝말잇기**. 앞 글자를 보고 다음 글자를 고른다.

### 조건부 확률 계산
```
P(b | a) = count(a, b) / count(a, ·)
           └ a 다음에 b가 온 횟수   └ a 다음에 무엇이든 온 총 횟수
```
- 예: '사' 다음에 무언가 온 횟수 17,600, 그중 '회' 583 → P(회 | 사) = 583 / 17,600 = **3.31%**

### 쌍 뽑아내기 — 슬라이딩 윈도우
2글자 창을 한 칸씩 옮기며 쌍을 뽑는다.
```
가가대소:  [가 가] 대 소  →  가 [가 대] 소  →  가 가 [대 소]
           가가              가대              대소
```
강의 예시 (단어 3개):
| 단어 | 추출된 바이그램 |
|---|---|
| 가가 | 가가 |
| 가가대소 | 가가 가대 대소 |
| 가가대소하다 | 가가 가대 대소 소하 하다 |

합치면 가가 3 / 가대 2 / 대소 2 / 소하 1 / 하다 1. '가' 다음에는 '가'(3번)가 '대'(2번)보다 확률이 높다 (3/5 vs 2/5).

### 단어 안에서만 센다
- words.txt는 **단어 목록**이다. "사과" 다음 줄에 "나비"가 있다고 해서 '과' 다음에 '나'가 오는 게 아니다.
- 그래서 앞 단어의 끝 글자와 다음 단어의 첫 글자는 쌍으로 세지 않는다.

## 2. BOS / EOS — 단어의 시작과 끝

### 왜 필요한가
- **BOS** (Begin Of Sequence), **EOS** (End Of Sequence)
- "나비" → `[BOS] 나 비 [EOS]` → 쌍 3개: BOS→나, 나→비, 비→EOS
- 배우게 되는 것
  - **BOS 행**: 어떤 글자로 단어가 시작하기 쉬운가 (첫 글자 분포)
  - **X → EOS**: 어떤 글자 뒤에서 단어가 끝나기 쉬운가
- 생성: BOS에서 출발 → 다음 글자 뽑기 반복 → **EOS가 뽑히면 끝**
  - 유니그램은 언제 끝낼지 몰라서 길이를 미리 정해야 했다 (10자 고정). 바이그램은 끝내는 시점까지 확률로 배운다.

### Q. `<BOS>`가 실제로 5글자로 입력되나? 그럼 `<S>`처럼 짧게 하는 게 낫지 않나?
**아니다. BOS/EOS는 글자가 아니라 번호 하나다.**
- 프로그램 안에서 글자는 전부 번호(id)로 바뀐다. 한글 글자는 0 ~ 2,449번을 쓰므로 **남는 번호 2,450 = BOS, 2,451 = EOS**로 정한다. 실제 글자와 절대 겹치지 않는다.
- "나비" → `[2450, 나의 번호, 비의 번호, 2451]` — 번호 4개
- `<BOS>`, `<S>`, `BOS`는 사람이 보라고 **화면에 찍을 때 쓰는 이름표**일 뿐이라 길이는 상관없다. 이 구현은 강의와 맞춰 `BOS`/`EOS`로 출력한다.
- ⚠ 오히려 위험한 것: 진짜로 텍스트에 `"<BOS>나비<EOS>"`를 붙여 넣고 2글자 창으로 자르면 `<B`, `BO`, `OS` 같은 엉터리 쌍이 생긴다. 그래서 반드시 번호로 처리한다.

## 3. 바이그램의 확률표는 어떻게 생겼나

### Q. 유니그램은 2,450종 글자에 대해 확률표를 하나 만들었다. 바이그램은?
**앞 글자마다 확률표가 하나씩 있다.**

유니그램: 표 1개, 칸 2,450개, 합계 100%
```
다 4.91% | 하 3.10% | 이 ... | ... (2,450칸)
```

바이그램: 앞 글자마다 표가 따로 있고, **각 표가 그 자체로 합계 100%** (실측)
```
BOS 다음 표:  사 1.10% | 가 1.06% | 자 0.98% | 고 0.97% | ...  (2,189칸)
사  다음 표:  EOS 25.79% | 회 3.31% | 이 2.49% | 리 2.41% | ... (592칸)
다  다음 표:  EOS 93.68% | 리 1.01% | 이 0.35% | 지 0.21% | ... (446칸)
힛  다음 표:  왕 100%                                          (1칸)
```
- 표 개수 **2,451개** = 글자 2,450 + BOS. EOS 다음에는 아무것도 오지 않으므로 EOS 표는 없다.
- 표마다 크기가 크게 다르다. 최소 1칸, 중앙값 11칸, 최대 2,189칸(BOS). 전부 합치면 171,425칸.
- **생성 = 표를 바꿔 가며 뽑기.** BOS 표에서 '사'를 뽑으면 → '사' 표로 가서 다음을 뽑고 → '회'가 나오면 '회' 표로 → EOS가 나오면 끝.

### 발견: 표의 합계 = 유니그램 빈도
- '다' 표의 합계는 **76,241**. Step1에서 센 '다'의 빈도와 정확히 같다.
- 이유: EOS가 있으니 **모든 글자 뒤에는 반드시 무언가(다음 글자 또는 EOS)가 온다.** 따라서 "a 뒤에 무언가 온 횟수" = "a가 나온 횟수".
- 바이그램 표를 가로로 다 더하면 유니그램이 된다. → 검증 항목 [2]로 사용했다.

### EOS 확률이 들어 있다
- '다' 표의 93.68%가 EOS다. 사전 단어 대부분이 "~다"로 끝나기 때문이다 ('하다'만 44,128쌍).
- 바이그램은 **"여기서 끝낼 확률"을 표 안에 갖고 있다.** '다'가 뽑히면 거의 확실히 단어가 끝난다.

### Q. BOS 표를 가로로 2,189칸 쓰면 못 읽는다. 한 줄에 하나씩 써야 하지 않나?
맞다. 실제 파일(`step3_bigram_table.txt`)은 **쌍 하나 = 한 줄**로 저장했다.
```
# prev	next	count	percent
BOS	사	4614	1.097764
BOS	가	4448	1.058269
...                       ← BOS 표 2,189줄
사	EOS	4539	25.789773
사	회	583	3.312500
...
```
- 171,425줄. 0인 쌍은 쓰지 않는다 ("없는 조합은 만들지 않는다").
- 확률을 소수 6자리로 쓰는 이유: 소수 2자리면 빈도 1짜리(1/420,309 = 0.000238%)가 `0.00%`로 보인다.
- 행 순서: BOS 먼저, 그다음 가나다순. 행 안: 빈도 내림차순.

## 4. 저장 구조 고민 — 이번 단계의 핵심

모델 자체(세고 나누기)는 단순하다. 어려운 것은 **171,425개의 쌍을 어떻게 저장하고, 생성할 때 어떻게 빨리 뽑느냐**다.

### 4.1 강의의 설명: 500MB → 24MB → 해시
강의 영상:
- 2차원 배열 `freq[앞 글자][뒷 글자]`
  - 한글 11,172자 → 11,172 × 11,172 × 4바이트 ≈ **500MB** → 너무 크다
  - 실제로 쓰이는 2,450자만 번호를 매기면 2,450 × 2,450 × 4바이트 ≈ **24MB** → 적절
- "모든 조합이 다 글에 존재하는 것이 아니다. **없는 조합에 메모리를 쓰지 않는 것이 중요하다.**"
- 강의 문서: 이렇게 많은 조합을 효율적으로 저장하기 위해 **해시테이블**을 쓴다.

### 4.2 "없는 것은 만들지 않는다"에는 두 단계가 있다
| 단계 | 버리는 것 | 방법 | 크기 |
|---|---|---|---|
| 0. 아무것도 안 버림 | 없음 | 11,172² 배열 | 500MB |
| 1. **글자 단위** | 사전에 안 나오는 글자 8,722종 | 압축 번호 → 2,452² 배열 | 24MB |
| 2. **쌍 단위** | 쓰는 글자끼리라도 실제로 안 붙는 쌍 | 해시테이블 / CSR | 4.2MB / 1.4MB |

- 강의의 24MB 배열은 **1단계까지** 적용한 것이다.
- 그런데 24MB 표도 약 600만 칸 중 값이 있는 칸은 17만 칸(2.8%)이다. **97.2%가 0**이다. 예: '가'와 '힛'은 둘 다 사전에 있지만 "가힛"이라는 쌍은 없을 수 있다. 1단계는 이걸 못 거른다.
- 강의 원칙을 끝까지 적용하면 2단계, 즉 해시테이블로 간다.
- 강의가 "해시 **또는** 2차원 배열"이라고 한 것은: 24MB면 요즘 컴퓨터에 부담이 없으니 **배열도 실용적으로 충분**하고, 원리를 따지면 해시가 맞다는 뜻으로 이해할 수 있다.

### 4.3 Q. "압축 단계를 뺐다"는 게 무슨 말인가?
글자에 번호를 붙이는 방법은 두 가지다.

| | A. 압축 번호 | B. 코드포인트 번호 |
|---|---|---|
| 방법 | 실제로 나온 2,450종만 0 ~ 2,449로 다시 번호 | `코드포인트 - 0xAC00` 그대로 (가=0 … 힣=11,171) |
| 범위 | 2,452개 (+BOS/EOS) | 11,174개 (+BOS/EOS) |
| 준비 | "어떤 글자가 나오나" 목록이 필요 | 계산 한 번이면 끝 |
| 빈 번호 | 없음 | 안 나오는 8,722종의 번호가 빈다 |

- **압축이 의미 있는 건 2차원 배열일 때뿐이다.** 배열은 [앞][뒤] 칸을 전부 미리 만들어야 하기 때문 (A: 24MB, B: 500MB).
- **해시테이블은 실제로 나온 쌍만 저장**하므로 번호 범위가 메모리에 영향을 주지 않는다. 그래서 해시를 쓰면 압축 단계가 필요 없다.
- 남는 조건은 "키가 정수 범위에 들어가나"뿐이다. 키 = a × 11,174 + b → 최대 124,858,275 < int 최대 2,147,483,647.

> **최종 구현에서는** 세 구현이 모두 **A(압축 번호)**를 쓴다. 해시는 압축이 필요 없지만, 세 구현이 같은 번호를 써야 **순수하게 자료구조 차이만 비교**되기 때문이다 (5장).

### 4.4 해시테이블

#### 해시테이블이란
- **키(key) → 값(value)**을 저장하는 자료구조. 여기서 키 = 쌍 (사, 회), 값 = 583(횟수)
- **해시 함수**가 키로 저장 위치를 계산 → 데이터가 많아도 평균적으로 한 번에 찾는다
- Python의 `dict`, `Counter`가 해시테이블이다. C에는 없어서 직접 만들었다.

#### Q. 해시테이블은 메모리에 배열표를 만드는 건가?
**그렇다. 해시테이블도 메모리에서는 그냥 배열이다.** 다른 것은 **어느 칸에 넣을지 정하는 방법**과 **칸에 무엇을 적는지**다.
```
칸 번호     0      1      2     ...   524,287
keys   [  -1  | 7341 |  -1  | ... |  152  ]   ← 이 칸에 든 쌍이 무엇인지 (키)
counts [   0  |  583 |   0  | ... |   12  ]   ← 그 쌍의 빈도
```
| | 2차원 배열 | 해시테이블 |
|---|---|---|
| 칸 수 | 2,452 × 2,452 ≈ 600만 | 2¹⁹ = 524,288 |
| 칸의 의미 | **위치 자체가 쌍** ('사' 행 '회' 열 = (사,회)) | 위치에 의미 없음. 아무 쌍이나 들어올 수 있음 |
| 칸 찾기 | `사 × 2452 + 회` | 해시 함수로 칸 번호 계산 → 키가 맞는지 확인 |
| 칸에 적는 것 | 빈도만 | **키 + 빈도** |
| 빈 칸 | 안 나오는 쌍 약 583만 개 | 일부러 남긴 여유 칸 약 35만 개 |

- 2차원 배열은 **가능한 모든 쌍**에 고정 자리를 준다.
- 해시테이블은 **실제로 나온 쌍에만** 자리를 준다. 어떤 쌍이 나올지 미리 모르니 해시 함수로 **흩어서 배정**하고, 위치만으로는 무슨 쌍인지 모르니 **칸에 키를 같이 적는다.**
- 왜 2/3나 비워 두나: 꽉 차면 충돌(서로 다른 키가 같은 칸)이 늘어 빈 칸을 찾아 멀리 가야 한다. 그래서 약 33%만 차게 넉넉히 잡았다. 해시테이블도 공짜가 아니다 — 524,288 × 8바이트 ≈ **4.2MB**.

### 4.5 CSR — 강의에 없는, Claude가 추가한 개념

#### Q. CSR이 뭔가?
**CSR(Compressed Sparse Row, 압축 희소 행)**: 대부분 0인 표에서 0이 아닌 칸만 **행(앞 글자) 순서대로 한 줄로 이어 붙여** 저장하는 방식.

강의 예시를 2차원 표로 그리면 25칸 중 5칸만 쓴다.
```
        가  대  소  하  다
  가 [  3   2   0   0   0 ]
  대 [  0   0   2   0   0 ]
  소 [  0   0   0   1   0 ]
  하 [  0   0   0   0   1 ]
  다 [  0   0   0   0   0 ]
```
CSR은 0을 버리고 행 순서로 붙인다.
```
위치          0    1    2    3    4
다음 글자   [ 가,  대,  소,  하,  다 ]
행 안 누적  [ 3,   5,   2,   1,   1  ]   ← 행마다 0부터 다시 누적
            └─가 행─┘ └대┘ └소┘ └하┘

row_start   가=0  대=2  소=3  하=4  다=5  (끝=5)
```
- `row_start[a]` ~ `row_start[a+1]` 직전이 **a 다음에 올 수 있는 후보 구간**
- 비유: **국어사전 옆면의 ㄱ·ㄴ·ㄷ 색인**. 색인만 보면 그 글자 구간이 어디서 시작해 어디서 끝나는지 바로 안다.
- 뽑기는 Step2와 똑같다. 범위만 좁아진다: '가' 다음을 뽑으려면 구간 [0, 2), 합계 5 → r ∈ [0, 5) → 구간 안에서 "누적 > r인 첫 칸"을 이진 탐색 (r = 0~2 → 가, r = 3~4 → 대)

#### Q. CSR을 왜 꺼냈나?
- 해시테이블은 "(가, 대)가 몇 번?"에는 바로 답하지만, 생성할 때 필요한 질문인 **"'가' 다음 후보가 전부 뭐지?"에는 답하지 못한다.** 키가 칸 전체에 흩어져 있기 때문이다.
- 강의는 해시테이블에 **저장**하는 데서 끝나고, 거기서 **어떻게 뽑는지**는 다루지 않는다. 그 빈자리를 채우려고 꺼낸 것이다.
- 강의 문서와 (전달받은) 영상 내용 어디에도 CSR은 나오지 않는다. **Claude 단독 계획에서 나온 개념**이다.

#### Q. 현업에서 쓰나?
- **희소 데이터를 다루는 곳에서는 표준 형식이다.**
  - SciPy `scipy.sparse.csr_matrix` (파이썬 희소 행렬의 기본 형식)
  - scikit-learn 문서-단어 행렬(TF-IDF): 문서마다 어휘 대부분이 0 → 우리 바이그램 표와 같은 상황
  - NVIDIA cuSPARSE, PyTorch `torch.sparse_csr_tensor`
  - 그래프 처리: "노드 a와 연결된 노드 전부" = "'가' 다음 후보 전부"와 똑같은 질문
- **현대 LLM 본체와는 거리가 있다.** GPT 같은 모델은 n-그램 빈도표를 쓰지 않고, 내부가 0이 거의 없는 밀집 행렬이라 CSR이 주인공이 아니다.
- 강의가 추천한 Karpathy의 makemore는 2차원 배열 방식이다. 영어 소문자 26개 + 특수 토큰 1개 = 27 × 27 배열이면 끝나기 때문이다. 한글은 글자 종류가 2,452개라 배열이 커지는 문제가 생긴다.

#### Q. CSR을 쓰는 것과 안 쓰는 것의 차이는? (Claude 설명 정정 포함)
처음에 Claude는 "해시만 쓰면 '가' 다음 후보를 찾으려고 표 전체(약 105만 칸)를 훑어야 한다"고 했다. **과장이었다.** 글자 2,452종이 정해져 있으면 **후보 2,452개를 하나씩 해시에 물어보면 된다.** 정정한 비교:

| | 해시만 | 해시 + CSR |
|---|---|---|
| 글자 하나 뽑는 비용 | 해시 조회 최대 2,452번 | 비교 약 10번 |
| 구조 | Step2의 **순차 탐색** 버전 | Step2의 **이진 탐색** 버전 |
| "없는 조합" 원칙 | 메모리에는 안 만들지만 **매번 물어본다** | 메모리에도 안 만들고 **묻지도 않는다** |

- 결과는 완전히 같고 속도만 다르다.
- 단어 20개 정도면 해시만으로도 충분하다. CSR은 대량 샘플링(검증용 수십만 번)에서 의미가 커진다.

## 5. 왜 코드를 세 가지 버전으로 만들었나

### 결정 과정
토론 끝에 선택지가 세 개로 정리됐다.
- **① 압축 + 2차원 배열**: 강의 영상이 "적절하다"고 한 방식. 가장 단순
- **② 해시만 (후보 2,452개 순차 조회)**: 강의 문서의 해시테이블 그대로
- **③ 해시 + CSR**: Claude 단독 계획. 강의 원칙을 끝까지 적용 + 빠른 뽑기

말로 비교하는 것보다 **셋 다 구현해서 같은 조건으로 돌려 보고 직접 비교**하기로 했다 (사용자 결정).
- 같은 seed로 단어 20개씩 만들어 한 결과 파일에 구현별로 구분해서 넣는다
- 구현별로 걸린 시간을 잰다

### 공정한 비교를 위한 설계
| 설계 | 이유 |
|---|---|
| **공통 부분은 한 파일**(`step3_bigram.c`), 구현별로 다른 부분(세기·뽑기)만 파일 3개 | 공통 코드가 같아야 차이가 자료구조에서만 나온다. 각 구현 파일엔 다른 부분만 있어서 나란히 놓고 비교하기 좋다 |
| 세 구현 모두 **같은 압축 번호** 사용 | 해시는 원래 압축이 필요 없지만, 번호가 같아야 순수하게 자료구조만 비교된다 |
| **난수는 main이 뽑고**, 구현은 `pick(앞 글자, r)`만 | 세 구현이 똑같은 r 순서를 받는다 |
| 후보를 **번호 오름차순**으로 누적, 경계 규칙 **`누적 > r`** 통일 | 같은 r이면 같은 글자 → **같은 seed면 단어가 글자 하나까지 같아야 한다.** 다르면 버그 |
| 시간은 학습 / 20개 / **10,000개** 세 가지 | 20개는 μs 단위라 측정할 때마다 흔들린다. 10,000개로 차이를 분명히 본다 |
| 최대 길이 20자 | 탐욕적 디코딩이 루프에 빠지면 EOS를 영영 못 만날 수 있다 |

### 공통 약속 — 함수 포인터 묶음 (`step3_bigram.h`)
C에는 클래스가 없어서, 세 구현이 "같은 이름·같은 모양의 함수"를 내놓게 하려고 **함수 주소를 담는 구조체**를 쓴다.
```c
typedef struct {
    const char *name;                                    /* array / hash / csr */
    int       (*build)(const int *seq, long long n, int vocab, int eos);  /* 학습 */
    long long (*row_total)(int prev);                    /* 앞 글자 행의 합계 */
    int       (*pick)(int prev, long long r);            /* 누적 > r 인 첫 후보 */
    int       (*greedy)(int prev);                       /* 빈도 최대 후보 */
    long long (*count)(int prev, int next);              /* 쌍 빈도 */
    size_t    (*memory)(void);
    void      (*release)(void);
} BigramModel;
```
main은 지금 돌리는 게 ①인지 ③인지 몰라도 `m->pick(prev, r)`만 부르면 된다. 그래서 시간 측정·생성 코드를 한 번만 쓰고 세 구현에 똑같이 적용할 수 있다.

### 공통 처리 흐름 (`step3_bigram.c`)
```
[1] words.txt 읽기 → 실제 나온 글자에 코드포인트 순서로 번호 (가=0, ... 2,449), BOS=2450, EOS=2451
[2] 모든 단어를 BOS ... EOS로 감싼 번호 배열(seq) 만들기
      "나비", "사과" → [BOS 나 비 EOS BOS 사 과 EOS]
      쌍은 seq[i], seq[i+1]. 단 seq[i]가 EOS면 건너뜀 (다음 칸은 다른 단어의 BOS)
[3] 구현마다: 학습 → 20개 생성 → 10,000개 생성 → 탐욕적, 각각 시간 측정
[4] 세 구현의 결과가 같은지 비교 (20개 + 10,000개 체크섬 + 탐욕적)
[5] 결과 파일 + 전체 빈도표 저장
```

단어 생성 (세 구현 공통):
```c
int prev = g_bos;
for (;;) {
    int next = greedy ? m->greedy(prev)
                      : m->pick(prev, rand_below(m->row_total(prev)));  /* 난수는 여기서 */
    if (next == g_eos) break;                   /* EOS면 단어 끝 */
    if (w->len == MAX_LEN) { w->truncated = 1; break; }   /* 20자 넘으면 잘림 */
    w->ids[w->len++] = next;
    prev = next;                                /* 다음 표로 이동 */
}
```
- EOS인지 **먼저** 확인하고 길이를 검사한다. 딱 20자에서 EOS가 나온 단어는 잘린 것으로 치지 않기 위해서다.

## 6. 세 구현 코드 해설

### 6.1 ① 압축 번호 + 2차원 배열 (`step3_bigram_array.c`)

#### 자료구조
```
freq[prev * vocab + next] = (prev, next) 쌍의 빈도      ← 2,452 × 2,452칸 = 약 24MB
row_sum[prev]             = prev 행의 합계
```
- 2차원 배열 `freq[a][b]`를 1차원으로 펴서 `freq[a * vocab + b]`로 쓴다.
  - 이유: vocab(2,452)은 실행해 봐야 아는 값이라 `int freq[2452][2452]`처럼 크기를 고정해 선언할 수 없다. 한 덩어리로 할당하고 "a행 b열 = a × vocab + b번째 칸"으로 계산한다.
  - 24MB는 스택(보통 1MB)에 둘 수 없어서 `calloc`으로 힙에 할당한다. `calloc`은 0으로 채워 주므로 "아직 안 나온 쌍 = 0"이 된다.

#### 세기
```c
for (i = 0; i + 1 < n; i++) {
    int a = seq[i];
    int b = seq[i + 1];
    if (a == eos) continue;          /* 단어 경계 */
    g_freq[a * vocab + b]++;
    g_row_sum[a]++;                  /* 행 합계도 같이 */
}
```

#### 뽑기 — 행을 앞에서부터 누적
```c
const int *row = g_freq + prev * g_vocab;   /* prev 행의 시작 칸 */
long long cum = 0;
for (b = 0; b < g_vocab; b++) {
    cum += row[b];
    if (cum > r) return b;
}
```
- '가' 행: 가=3, 대=2(나머지 0) → b=가에서 누적 3 (r=0,1,2면 '가'), 그 뒤 0인 칸들을 지나며 누적 그대로 3, b=대에서 누적 5 (r=3,4면 '대')
- **0인 칸(약 97%)도 전부 읽는다.** 이것이 ③과의 속도 차이다.
- 행마다 누적 배열을 미리 만들면 이진 탐색이 되지만 24MB짜리 배열이 하나 더 필요하다. 이 구현은 강의의 "배열 하나" 방식을 그대로 보여 주는 것이 목적이라 매번 더한다.

### 6.2 ② 해시테이블만 (`step3_bigram_hash.c`)

#### 해시 함수 — 키를 칸 번호로 (피보나치 해싱)
```c
return ((unsigned)key * 2654435761u) >> (32u - ht->bits);
```
- 키에 2654435761을 곱하고(32비트를 넘는 부분은 버려짐), 결과의 **상위 19비트**를 칸 번호로 쓴다 → 0 ~ 524,287
- 왜 이렇게: 키 = prev × 2452 + next라 값이 규칙적이다 (같은 행은 연속, 행이 바뀌면 2,452씩 건너뜀). `키 % 칸수`처럼 아래 비트만 쓰면 이 규칙이 칸 배치에 그대로 남아 특정 구역에 몰릴 수 있다. 곱셈은 모든 비트를 섞어 위쪽으로 올려 보내므로 위쪽 비트를 쓰면 고르게 흩어진다.
- 2654435761 ≈ 2³² / 황금비. 비트를 잘 섞는다고 알려져 있어(Knuth) 관례적으로 쓰는 값이다.

#### 추가 — 오픈 어드레싱 + 선형 탐사
```c
unsigned i = ht_slot(ht, key);
for (;;) {
    if (ht->keys[i] == key) { ht->counts[i]++; return 1; }     /* 이미 있음: +1 */
    if (ht->keys[i] == -1)  { ht->keys[i] = key;               /* 빈 칸: 새로 넣기 */
                              ht->counts[i] = 1; ht->used++; return 1; }
    i = (i + 1u) & ht->mask;                                    /* 충돌: 옆 칸으로 */
}
```
- 예: (사,회)가 100번 칸으로 계산됐는데 100번에 (가,나)가 있으면 → 101번 칸을 본다
- 충돌 처리에는 체이닝(칸마다 연결 리스트)과 오픈 어드레싱(옆 빈 칸 찾기)이 있다. 오픈 어드레싱은 배열 두 개로 끝나서 쌍마다 `malloc`할 필요가 없고, 옆 칸은 메모리상 바로 옆이라 빠르다.
- 칸 수를 2의 거듭제곱으로 한 이유: `(i + 1) % 칸수` 대신 `(i + 1) & mask`로 끝 칸 다음에 0번 칸으로 돌아간다 (칸 8개면 mask = 0b111, 7+1 = 0b1000 & 0b111 = 0).
- 빈 칸 표시를 0이 아니라 -1로 하는 이유: 키 0 = (가, 가) 쌍이라 0은 실제로 쓰이는 키다.
- 70% 넘게 차면 실패로 처리. 2¹⁹칸에 17만 개면 33%만 찬다.

#### 조회
- 추가와 같은 순서로 칸을 따라가다가 같은 키를 만나면 빈도, **빈 칸을 만나면 "없음"**.
- 빈 칸에서 멈춰도 되는 이유: 그 키가 있었다면 추가할 때 이 빈 칸 이전 어딘가에 들어갔어야 한다. 삭제를 하지 않으니 중간에 빈 칸이 새로 생기지 않는다.

#### 뽑기 — 후보 2,452개를 하나씩 물어보기
```c
int base = prev * g_vocab;          /* prev 행의 첫 키 */
long long cum = 0;
for (b = 0; b < g_vocab; b++) {
    cum += ht_get(&g_ht, base + b);  /* 배열 칸 읽기 → 해시 조회로 바뀐 것뿐 */
    if (cum > r) return b;
}
```
- 구조는 ①과 똑같다. 차이는 "배열 칸 읽기"가 "해시 조회"로 바뀐 것.
- '사' 행은 실제 후보가 592개인데 최대 2,452번을 묻는다. **없는 쌍을 확인하는 데 대부분의 시간을 쓴다.**

### 6.3 ③ 해시로 세고 CSR로 뽑기 (`step3_bigram_csr.c`)

#### 왜 바로 CSR에 세지 않고 해시로 먼저 세나
CSR은 "행마다 몇 칸인지"를 알아야 자리를 잡을 수 있는데, 그건 **다 세어 봐야 안다.** 그래서 크기를 몰라도 되는 해시로 먼저 세고, 다 센 뒤 크기가 확정되면 CSR로 옮긴다. 세는 부분은 ②의 해시테이블 함수를 그대로 빌려 쓴다.

#### 해시 → CSR 변환 (4단계)
```
1) 해시테이블의 채워진 칸만 꺼내 (키, 빈도) 배열을 만든다    ← 해시 순서라 뒤죽박죽
2) 키 오름차순으로 정렬 (qsort)
   키 = prev × vocab + next 이므로 정렬하면 prev별로 모이고, 같은 prev 안에서는 next 오름차순
3) 행마다 칸 수를 세서 누적 → row_start
   예: 가 2칸, 대 1칸, 소 1칸 → row_start = 0, 2, 3, 4 ...
4) 행 안에서 빈도를 누적 → cum (행이 바뀌면 0부터)
```
3단계 코드:
```c
for (i = 0; i < g_pairs; i++)
    g_row_start[items[i].key / vocab + 1]++;     /* 행 a의 칸 수를 a+1 자리에 센다 */
for (a = 0; a < vocab; a++)
    g_row_start[a + 1] += g_row_start[a];        /* 앞에서부터 누적 */
```
- 한 칸 밀어서 세는 이유: 누적이 끝나면 `row_start[a]` = "a보다 앞 행들의 칸 수 합" = 행 a가 시작하는 위치가 된다.
- 2단계에서 계수 정렬 대신 **qsort**를 쓴 이유: 계수 정렬로 행별 자리만 잡으면 O(n)이지만 행 안 순서가 해시 칸 순서(뒤죽박죽)로 남는다. 세 구현이 같은 결과를 내려면 후보가 번호 오름차순이어야 하므로, 키 정렬 한 번으로 행 묶기와 행 안 정렬을 동시에 끝낸다.
- 변환이 끝나면 세기용 해시는 해제한다. 생성 단계엔 CSR(1.38MB)만 남는다.

#### 뽑기 — 행 구간 안에서 이진 탐색
```c
int lo = g_row_start[prev];
int hi = g_row_start[prev + 1] - 1;   /* 행의 마지막 위치 */
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (g_cum[mid] > r) hi = mid;     /* '>' 가 핵심 */
    else                lo = mid + 1;
}
return g_next_id[lo];
```
- Step2 `sample_index`와 같은 upper_bound. 다른 점은 탐색 범위가 전체가 아니라 **prev 행 구간**이라는 것뿐.
- '가' 행 (위치 0~1, cum = 3, 5): r=2 → mid=0, 3 > 2 → hi=0 → '가' / r=3 → mid=0, 3 > 3 아님 → lo=1 → '대'
- '사' 행(592칸)이면 최대 10번 비교 (2¹⁰ = 1,024 ≥ 592)

### 7.5 Q. 세 구현의 결과가 같은 건 seed가 같아서인가?
**같은 seed는 필요조건이지만 그것만으로는 부족하다.** 아래 세 가지가 함께 맞아야 같은 단어가 나온다. 그래서 "결과가 같다"는 사실 자체가 세 구현이 모두 맞다는 검증이 된다.

**① 같은 난수열**
- 구현마다 생성 직전에 `srand(seed)`를 다시 호출 → 세 구현이 똑같은 난수열에서 출발한다.
- 난수는 구현 안이 아니라 **main에서 뽑는다.** 구현은 받은 r로 `pick(앞 글자, r)`만 한다. 그래서 세 구현이 r을 같은 순서·같은 개수로 받는다.

**② 같은 후보 순서**
- 같은 r이라도 후보를 어떤 순서로 누적하느냐에 따라 뽑히는 글자가 달라진다.
  ```
  '가' 행을 [가 3, 대 2] 순서로 누적:  가 = r 0~2,  대 = r 3~4   → r=0이면 '가'
  '가' 행을 [대 2, 가 3] 순서로 누적:  대 = r 0~1,  가 = r 2~4   → r=0이면 '대'
  ```
  두 경우 모두 '가' 확률은 3/5로 같다. 분포는 맞지만 **같은 r에 다른 글자**가 나온다.
- 그래서 세 구현 모두 **번호 오름차순**으로 누적하게 맞췄다.
- ③ CSR에서 계수 정렬 대신 키 정렬(qsort)을 쓴 이유가 이것이다. 계수 정렬이면 행 안 순서가 해시 칸 순서(뒤죽박죽)로 남아서, **seed가 같아도 ③만 다른 단어**를 만든다 (확률은 맞지만).

**③ 같은 경계 규칙과 올바른 구현**
- 세 구현 모두 "누적 > r 인 첫 후보". 하나라도 `>=`로 쓰거나 빈도를 하나 잘못 세면, 그 구현만 어느 순간 다른 글자를 뽑고 거기서부터 단어가 갈라진다.

**그래서**
- result_01에서 20개 샘플과 10,000개 대량 생성(약 4.7만 번 뽑기)이 전부 일치했다(`same_output YES`) = **세 가지 다른 자료구조가 모든 뽑기에서 같은 답을 냈다.** 자료구조는 결과를 바꾸지 않고 속도·메모리만 바꾼다는 것을 직접 확인한 셈이다.
- 반대로 구현마다 seed를 다르게 주면, 세 구현이 모두 맞아도 단어가 다르게 나온다. 그러면 결과만 보고는 구현이 맞는지 판단할 수 없다. "같은 seed"를 고른 이유다.

### 7.6 Q. 프로그램을 3개로 따로 안 만들고 헤더 + 모듈 3개 + 실행 파일 하나로 만든 건 실행 시간 측정 때문인가?

| 탐욕적 | 사 | 사 | 난수를 쓰지 않으므로 항상 같다 |
| 사전 단어 | 8 / 20 | 8 / 20 | 비슷한 비율. 역시 대부분 한두 글자 (망, 옥, 단, 선 / 노류, 분포, 주파, 대기) |
| 10,000개 생성 | 27.7 / 485.0 / 3.7ms | 22.2 / 485.3 / 3.9ms | 수치는 흔들리지만 **순위(③ < ① < ②)와 배율은 유지** |
| 20개 생성 | 0.049 / 0.836 / 0.015ms | 0.045 / 1.266 / 0.014ms | ②가 0.8 → 1.3ms로 크게 흔들림. μs 단위 측정은 참고용 |
| 빈도표 | 171,425줄 | 바이트 단위로 동일 | 같은 데이터에서 세므로 매번 같다 |

- result_02에는 9글자 단어가 두 개 나왔다 ("와르똬뱅이수중점질", "지구무구무대접신령"). 쌍 하나하나는 사전에 실제로 있는 쌍이지만 전체로는 말이 안 된다. 앞 글자 하나만 보는 바이그램의 한계가 긴 단어에서 더 잘 드러난다.
- "지구무구무대접신령"의 "구무구무"처럼 같은 쌍이 반복되기도 한다. 바로 앞 글자만 기억하므로 '무' 다음에 '구', '구' 다음에 '무'가 다시 나와도 막을 방법이 없다.

### 7.8 Q. 글자를 생성하는데 왜 한 글자나 두 글자 단어가 이렇게 많나?
**바이그램은 지금 단어의 몇 번째 글자를 뽑고 있는지 모르기 때문이다.**

#### 실제 사전과 비교 (Python으로 바이그램 단어 20만 개 생성, 같은 확률표)
| 길이 | 사전 | 바이그램 생성 |
|---|---|---|
| 1자 | **0.32%** | **21.3%** (약 66배) |
| 2자 | 18.5% | 20.7% |
| 3자 | 28.3% | 17.2% |
| 4자 | 32.3% | 12.6% |
| 5자 | 11.1% | 8.7% |
| 6자 | 6.4% | 6.0% |
| 7자 | 1.7% | 4.2% |
| 8자 | 1.0% | 2.9% |
| 9자 이상 | 0.47% | 6.5% |

- 사전에 한 글자 단어는 1,357개(0.3%)뿐인데, 모델은 다섯 개 중 하나를 한 글자로 만든다.
- result_01, result_02에서도 20개 중 4개씩(20%)이 한 글자였다. 계산과 맞는다.
- 2자는 비슷하지만, 사전에서 가장 흔한 3~4자가 크게 모자라고 7자 이상은 너무 많다.

#### 원인: 단어 끝의 '사'와 첫머리의 '사'를 구분하지 못한다
단어를 끝낼지(EOS) 정하는 근거는 **바로 앞 글자 하나뿐**이다.
- P(EOS | 사) = **25.8%**. 사전 전체의 '사' 17,600번 중 4,539번이 단어 끝에 온 '사'다 (변호사, 의사, 교사 …).
- 그런데 모델은 BOS 다음 **첫 글자로 '사'를 뽑았을 때도** 같은 25.8%를 쓴다.
- 실제로 '사'로 시작하는 단어 4,614개 중 '사' 한 글자로 끝나는 단어는 **1개**뿐이다 (0.02%).
- 단어 끝에 자주 오는 글자일수록 더 심하다.

| 글자 | P(EOS \| 글자) | 실제로 그 글자 하나로 된 단어 / 그 글자로 시작하는 단어 |
|---|---|---|
| 다 | 93.7% | 1 / 2,096 |
| 기 | 46.7% | 1 / 3,561 |
| 이 | 36.8% | 1 / 4,060 |
| 사 | 25.8% | 1 / 4,614 |
| 가 | 15.1% | 1 / 4,448 |

모델 입장에서는 첫 글자 뒤에서 25~90% 확률로 단어를 끝내니 한 글자 단어가 쏟아진다.

#### 긴 단어도 너무 많은 이유
- 모델은 지금까지 몇 글자를 썼는지도 기억하지 못한다. 매 글자마다 "이번에 끝낼까?"를 앞 글자 하나만 보고 정한다.
- 평균적으로 글자마다 약 27% 확률로 끝나는 **동전 던지기를 반복**하는 셈이다 (사전 전체: 단어 420,309개 ÷ 글자 1,551,565자 ≈ 27%).
- 그러면 1자에서 끝나는 경우가 가장 많고 길이가 늘수록 조금씩 줄어드는 모양이 된다. 실제 사전은 3~4자에 봉우리가 있고 1자나 9자 이상은 드물다. 이 봉우리를 만들지 못해서 **짧은 쪽과 긴 쪽이 동시에 과하게** 나온다.

#### 트라이그램이 이걸 줄이는 방식 (다음 단계 예고)
- 트라이그램은 **앞 두 글자**를 본다. 첫 글자를 뽑은 직후의 문맥은 (BOS, 사)다.
- P(EOS | BOS, 사) = 1 / 4,614 ≈ 0.02% → "단어 첫머리의 '사'"임을 알기 때문에 한 글자로 끝낼 확률이 거의 0이 된다.
- 트라이그램을 구현하면 이 길이 분포가 얼마나 사전에 가까워지는지 비교해 볼 것.

### 7.9 Q. 바이그램을 10글자로 고정해서 생성하면 어떻게 되나?
**바이그램은 "언제 끝내는가(EOS)"까지 배운 모델이라 길이를 바깥에서 강제하면 모델과 충돌한다.** 고정하는 방법이 셋이고 결과가 다르다 (Python 실험, 확률표는 C 구현과 같음).

#### (A) EOS를 금지하고 10글자까지 계속 뽑기
EOS를 후보에서 빼고, 남은 후보들로 확률을 다시 나눠서 뽑는다.
```
북유저냐르네랄리서하
왈각하다닫긴급수정연
릉성표하다닐산석지네
보데기체세영하다리주
```
- 전부 정확히 10자지만 **"하다"가 단어 중간에 낀다.** '다' 다음은 93.7%가 EOS라 모델은 끝내고 싶어 하는데, 막으니 남은 6%(리, 이, 지 …)에서 억지로 이어 간다.
- 다음 글자로 **EOS밖에 없는 글자가 163개** 있다 (예: 읖, 갏). 이걸 뽑으면 갈 곳이 없어 막힌다 → 2만 개 중 18개가 막힘.
- 사전에 있는 단어 **0개** (2만 개 중).
- 모델이 배운 분포를 **강제로 바꾸는** 방법이다.

#### (B) 평소처럼 만들고 10글자가 나온 것만 남기기 (거절 샘플링)
```
습장센스미숙약술설송
번치접계문제신행하다
생태양성백합성직되다
간무명자유성알종매듭
```
- 끝맺음이 자연스럽다 ("~하다", "~되다"). 끝내는 시점을 모델이 직접 골랐기 때문이다.
- 효율이 나쁘다. 10자가 나올 확률이 **1.39%** → 평균 **72번** 만들어야 1개.
- **모델 분포를 바꾸지 않는 유일한 방법.** "이 모델이 10글자 단어를 만든다면 이렇게 만든다"를 그대로 보여 준다.
- 그래도 내용은 말이 되지 않는다. 앞 글자 하나만 보니 길수록 의미가 흩어진다. 사전의 10글자 단어는 463개뿐이라 우연히 맞기도 어렵다 (예: 가는다리애기좀진드기, 가운데흰뒤날개밤나비).

#### (C) EOS가 나오면 새 단어를 이어 붙여 10칸 채우기
유니그램처럼 길이만 채운다. `|`는 단어 경계.
```
왈가|궐공장|메기경
보포클|기중혼|샛길
신금살망셍이하다|콩
```
- 10글자짜리 한 단어가 아니라 **짧은 단어들의 나열**이다. 7.8의 "짧은 단어가 많은 문제"가 그대로 보인다.
- (실험 코드가 `|`도 한 칸으로 세서 한글은 10자보다 적게 나왔다.)

#### 정리
| 방법 | 길이 | 자연스러움 | 모델 분포 | 비용 |
|---|---|---|---|---|
| (A) EOS 금지 | 정확히 10 | 중간에 "하다"가 끼고, 막히기도 함 | **왜곡** | 빠름 |
| (B) 10글자만 채택 | 정확히 10 | 끝맺음 자연스러움 | **그대로** | 72배 |
| (C) 이어 붙이기 | 10칸 | 짧은 단어의 나열 | 그대로 | 빠름 |

- 유니그램은 EOS가 없어서 길이를 고정해도 문제가 없었다. **바이그램부터는 "언제 끝내는가"도 모델이 배우는 대상**이라, 길이를 강제하면 (A)처럼 모델과 부딪힌다.
- 현대 LLM에서도 같은 구조다. 문장 끝 토큰(EOS)이 나오면 생성을 멈추고, "최대 길이"는 무한 생성을 막는 안전장치로만 쓴다. 이 구현의 MAX_LEN 20도 같은 역할이다.

### 7.10 관찰: "사전 단어의 일부를 만들 뿐, 실제 단어 같다는 느낌은 안 든다"
**바이그램이 보장하는 것은 "붙어 있는 두 글자"뿐이다.** 그래서 서로 다른 단어의 조각을 **겹치는 글자에서 이어 붙인** 결과가 나온다.

#### 실제로 어떻게 이어 붙었나 — 쌍마다 그 쌍을 가진 실제 단어
```
"정보단순"
BOS→정   정, 정가 ...
정→보    가정보, 경영정보시스템 ...      ┐ "정보"
보→단    대보단, 민보단, 보단             ┤ ← '보'에서 다른 단어로 갈아탐
단→순    단순, 단순가설 ...               ┘ "단순"
순→EOS   가나다순, 화순 ...
```
- 진짜 단어 "정보"와 "단순"이, 또 다른 단어에서 온 "보단"이라는 조각으로 연결됐다. 모델은 '보' 다음에 무엇이 오는지만 볼 뿐, 그게 어느 단어의 '보'였는지 모른다.
- "지구무구무대접신령" = 지구 / 구무 / 무구 / 구무 / 무대 / 대접 / 신령 — 쌍은 전부 사전에 있지만 전체는 어느 단어에도 없다.
- "바닥거리다" = "바닥" + "~닥거리다"(까닥거리다)를 '닥'에서 이어 붙임.
- 강의 비유 그대로 **두 글자 끝말잇기**다.

#### 두 글자를 넘어서면 실제와 어긋난다 (바이그램 단어 10만 개로 측정)
- 2글자 창: **100%** 사전에 존재 (구조상 당연)
- 3글자 창 (BOS/EOS 포함): **56.4%**만 사전에 존재 → 나머지는 "보단순"처럼 실제로는 없는 연결

길이별로 생성 단어가 실제 사전 단어인 비율:
| 길이 | 1자 | 2자 | 3자 | 4자 | 5자 | 6자 이상 |
|---|---|---|---|---|---|---|
| 사전 단어 비율 | 98.7% | 80.3% | 16.2% | 9.1% | 0.3% | 0% |

결과 파일의 `*`가 대부분 한두 글자인 이유다. 짧으면 두 글자 범위 안에 다 들어가서 맞을 수밖에 없고, 길수록 이어 붙인 자리가 늘어 진짜 단어와 멀어진다.

#### 왜 "단어 같은 느낌"이 안 드나
- 한국어 단어는 정보, 단순, 바닥처럼 **두 글자 이상이 한 덩어리인 형태소**로 이루어진 경우가 많다. 사람은 그 덩어리 단위로 단어를 알아본다.
- 바이그램은 덩어리의 경계를 모르고 아무 글자에서나 갈아탄다 → 익숙한 조각은 보이는데 전체는 낯설다.

#### 다음 단계와의 연결
- 트라이그램은 앞 두 글자를 보므로 **3글자 창이 항상 사전에 있게** 된다 (56.4% → 100%). 더 단어 같아진다.
- 대신 n을 키울수록 "본 적 있는 조합"만 쓰게 되어 결국 **사전 단어를 그대로 베끼는 쪽**으로 간다. 새로우면서 그럴듯한 단어 사이의 균형이 N-그램의 핵심 고민이고, 신경망 언어모델로 넘어가는 이유이기도 하다.

### 7.12 Q. 한 글자로 끝나는 단어는 두 번째 뽑기에서 EOS를 만난 것인가? 단어가 끝나는 건 대부분 그런 건가?
**그렇다. 그리고 "대부분"이 아니라 모든 단어가 EOS를 만나서 끝난다.** 언제 만나느냐만 다르다.

```
뽑기 1: BOS → 호          (BOS 표에서 뽑음)
뽑기 2: 호  → EOS         (호 표에서 뽑음) → 끝. "호" (1글자)

뽑기 1: BOS → 정
뽑기 2: 정  → 하
뽑기 3: 하  → 다
뽑기 4: 다  → EOS         → 끝. "정하다" (3글자)
```
- **단어 길이 = EOS가 나오기 전까지 뽑은 글자 수.** 2번째에서 EOS → 1글자, 3번째 → 2글자, 4번째 → 3글자.
- EOS가 끝까지 안 나오면 20자에서 강제로 자르고 `~` 표시. result_01~03에선 한 번도 없었다 → 지금까지 나온 단어는 **전부** EOS로 끝났다.

#### 한 글자 단어의 확률 (result_03의 실제 예)
한 글자가 되려면 두 번의 뽑기가 연달아 이렇게 나와야 한다.
| 단어 | 1번째: BOS → 그 글자 | 2번째: 그 글자 → EOS | 곱 |
|---|---|---|---|
| 호 | 0.37% | **24.9%** | 0.092% |
| 과 | 0.23% | **41.4%** | 0.094% |
| 길 | 0.09% | **44.4%** | 0.039% |
| 측 | 0.08% | **16.9%** | 0.014% |
| 닻 | 0.01% | **20.8%** | 0.002% |

- 특정 글자가 첫 글자로 나올 확률은 작지만, **어떤 글자가 나오든 그 뒤 EOS 확률이 15~45%로 높다.**
- 첫 글자 2,189종을 전부 더하면 한 글자로 끝날 확률이 **21.3%**가 된다.
- EOS가 이렇게 일찍 나오는 이유는 7.8의 위치 문제다. "호 → EOS 24.9%"는 단어 끝의 '호'(번호, 기호, 신호 …)에서 나온 값인데, 첫 글자 '호'에도 그대로 쓴다.
- 정리: **끝나는 원리(EOS를 만나면 끝)는 맞게 동작한다. 문제는 EOS가 너무 이른 시점에 나온다는 것**이다.

### 7.13 Q. "어떤 글자 뒤에서 끝날 확률이 높다"는 것은 반영됐나? (~기, ~적, ~법, ~사, ~하기)
**반영됐다. 바이그램 표의 "글자 → EOS" 확률이 바로 그것이다. 다만 글자 하나 단위로만 반영된다.**

#### 반영된 것: 글자마다 끝날 확률이 다르다 (평균 27.1%)
| 끝 글자 | P(EOS \| 글자) | 평균과 비교 | 예 |
|---|---|---|---|
| 다 | **93.7%** | 훨씬 높음 | ~하다, ~되다 |
| 법 | **69.1%** | 높음 | 형법, 상법, 문법 |
| 기 | **46.7%** | 높음 | 보기, 쓰기, 기기 |
| 적 | 30.2% | 약간 높음 | 목적, 실적 |
| 사 | 25.8% | 평균 수준 | 의사, 판사, 교사 |
| 가 | 15.1% | 낮음 | 가격, 가능 (주로 앞에 옴) |
| 하 | **1.2%** | 매우 낮음 | 거의 항상 뒤에 '다' |

- 모델은 '법'·'기' 뒤에서 잘 끝나고, '하' 뒤에서는 거의 안 끝난다는 걸 배웠다. 생성 결과에 "~하다", "~되다"가 많은 이유.
- '적'과 '사'가 생각보다 낮은 이유: 단어 끝뿐 아니라 **첫머리·중간에도 많이** 나오기 때문이다 (적극, 적용, 사회, 사과). 확률은 그 글자가 나온 모든 자리를 합쳐서 계산된다.

#### 반영 안 된 것 ①: 위치
앞 두 글자를 보면 차이가 드러난다.
| 상황 | 바이그램 (앞 1글자) | 앞 2글자를 보면 |
|---|---|---|
| 첫 글자 '법' 뒤에서 끝남 | 69.1% | P(EOS \| BOS, 법) = **0.2%** |
| '형' 다음 '법' 뒤에서 끝남 | 69.1% | P(EOS \| 형, 법) = **81.5%** |
| 첫 글자 '사' 뒤에서 끝남 | 25.8% | P(EOS \| BOS, 사) = **0.02%** |
| '판' 다음 '사' 뒤에서 끝남 | 25.8% | P(EOS \| 판, 사) = **48.7%** |
| 첫 글자 '기' 뒤에서 끝남 | 46.7% | P(EOS \| BOS, 기) = **0.03%** |

- 바이그램은 "형법의 법"과 "첫머리의 법"에 같은 69.1%를 쓴다. 그래서 첫 글자로 '법'이나 '기'를 뽑으면 바로 끝나 버린다.
- **끝 글자의 성질을 잘 배운 것이 오히려 첫 글자에서 부작용(한 글자 단어 폭증)을 낸다.**

#### 반영 안 된 것 ②: 두 글자 이상의 어미
- "~하기"처럼 두 글자짜리 끝맺음은 배울 수 없다. '기' 앞에 '하'가 있었는지 모르기 때문이다.
  - 바이그램: P(EOS | 기) = 46.7% — 하기 / 보기 / 쓰기를 구분 못 함
  - 앞 2글자: P(EOS | 하, 기) = 33.9%, P(EOS | 보, 기) = 54.8%
- 참고: 이 사전에서 "~하기"로 끝나는 단어는 19개뿐이다 (사전은 동사를 "~하다" 형태로 싣는다). 이 데이터에선 원래 약한 패턴이다.

#### 정리
| | 바이그램 |
|---|---|
| "이 글자 뒤에서 잘 끝난다" (법, 기, 다) | ✅ 반영 |
| "이 글자 뒤에서는 안 끝난다" (하) | ✅ 반영 |
| "단어 끝에 있을 때만 끝난다" (위치) | ❌ 첫 글자에도 같은 확률 → 한 글자 단어 폭증 |
| "~하기, ~스럽다 같은 여러 글자 어미" | ❌ 앞 1글자만 봄 |

→ 트라이그램은 (BOS, 법)으로 "첫 글자인지"를 알고, (형, 법)처럼 두 글자 패턴도 구분하므로 ❌ 두 가지를 크게 줄인다.

## 9. Claude 단독 계획 vs 강의 — 비교

강의 자료를 받기 전에 Claude가 "원래 알고 있는 방식"으로 세운 계획(devlog/2026-10-21.md 보존)과 강의 내용을 비교한다.

| 항목 | Claude 단독 계획 | 강의 | 비교 |
|---|---|---|---|
| 모델 | P(b\|a) = count(a,b) / count(a,·) | 조건부 확률 | 같음 |
| 세는 범위 | 단어 안에서만 | 단어 안에서만 (슬라이딩 윈도우) | 같음 |
| 시작/끝 토큰 | `<S>` / `<E>` | BOS / EOS ([보충]에서 등장) | 같은 개념, 이름만 다름 |
| 생성 종료 | EOS가 나오면 끝 | (BOS/EOS로 끝을 학습) | 같음 |
| 세기 자료구조 | 해시테이블 (오픈 어드레싱) | 해시테이블 **또는** 압축 2차원 배열 | 강의가 선택지를 하나 더 제시 |
| 메모리 논거 | "2.79%만 사용 → 희소 구조" | "500MB → 24MB, 없는 조합은 만들지 마라" | 같은 원칙. 강의는 단계적으로 설명 |
| 뽑기 구조 | **CSR + 행 이진 탐색** | 다루지 않음 | **가장 큰 차이** |
| 탐욕적 디코딩 | "반복 루프에 빠지는 걸 보여주기" | "'사'만 반복" | 같은 결론. 강의는 구체적 결과 제시, 이유는 절반만 |
| 스무딩 | 하지 않음 (생성만 하므로) | 언급 없음 | 같음 |
| 검증 | 전수 비교·카이제곱·self-test | (해당 없음) | 프로젝트 규칙 |

**Claude 계획이 실제 구현에서 바뀐 점**
- 압축 번호: 처음엔 압축 → "해시면 압축이 필요 없다"며 뺐다가 → 최종적으로 **공정한 비교를 위해 세 구현 공통으로 압축**
- CSR 구성: 계수 정렬(O(n)) → **키 qsort** (행 안 순서를 번호 오름차순으로 맞춰야 세 구현 결과가 같아짐)
- 해시만으로 뽑으면 "표 전체를 훑어야 한다" → **후보 2,452개를 묻는 방식**으로 정정

**Claude가 예측하지 못한 것**
- 탐욕적 결과가 정확히 "사" 한 글자이고, 그 이유가 "사 → EOS"라는 것 (실측으로 처음 확인)
- ① 배열이 ② 해시보다 17배 빠르다는 것 (같은 칸 수를 확인하므로 비슷할 거라 예상할 수 있었지만, 메모리 접근 패턴 차이가 컸음)

## 10. AI와 작업하며 얻은 교훈 (이번 단계)

- **숫자에는 출처가 있어야 한다.** 브리핑에서 "전에 말한 167,399개"라고만 해서 "그걸 언제 말했지?"라는 혼란이 생겼다. 실제 출처는 이전 세션의 PROGRESS.md 기록(BOS/EOS 없이 센 값)이었다. 같은 "서로 다른 쌍 수"도 BOS/EOS 포함 여부에 따라 167,399 / 171,425로 다르다. **어떤 조건에서 센 숫자인지**까지 확인해야 한다.
- **AI의 설명도 과장될 수 있다.** "해시만 쓰면 표 전체를 훑어야 한다"는 설명은 틀렸고, "CSR 쓰는 거랑 안 쓰는 거랑 차이를 다시 설명해 달라"는 질문에서 정정됐다. 이해가 안 되는 설명은 다시 물어보는 것이 검증이 된다.
- **강의 설명도 실측하면 더 정확해진다.** "사로 시작하는 단어가 많아서"는 절반만 맞았다. 데이터로 경로를 따라가 보니 "사 다음이 EOS"라는 두 번째 조건이 있었다.
- **말로 비교하지 말고 돌려 보기.** 배열·해시·CSR의 장단점을 말로만 따졌다면 "배열이 해시보다 17배 빠르다"는 걸 몰랐을 것이다. 같은 조건으로 실행하고 결과가 같은지까지 확인해야 비교가 공정하다.
- **AI가 한 계산도 확인할 것.** "20개 중 9개가 사전 단어(45%)"라고 보고했지만 실제로 세어 보면 탐욕적 줄 "사"를 빼고 **8개(40%)**였다. 결과 파일의 `*` 줄 수를 그대로 센 실수다.

8. 탐욕적 디코딩이 "사"인 두 가지 이유는? → BOS 다음 1위 '사' + '사' 다음 1위 EOS
9. 세 구현이 같은 단어를 만드는 것이 seed 때문만이 아닌 이유는? → 후보 순서·경계 규칙까지 같아야 함. 그래서 일치 = 세 구현이 맞다는 검증
10. 실행 파일 하나로 만든 이유는? → 같은 데이터·같은 측정 코드로 공정하게 시간 측정, 결과 일치를 바로 비교, 파일엔 자료구조 차이만
11. 바이그램이 한 글자 단어를 사전보다 66배 많이 만드는 이유는? → 위치를 모름. 단어 끝 '사'의 EOS 확률(25.8%)을 첫 글자 '사'에도 적용
12. 길이를 10자로 고정할 때 모델 분포를 바꾸지 않는 방법은? → 거절 샘플링 (평소대로 만들고 10자만 채택, 채택률 1.39%)
13. 생성 단어가 "실제 단어 같지 않은" 이유는? → 서로 다른 단어의 2글자 조각을 겹치는 글자에서 이어 붙임. 3글자 창은 56.4%만 실재
14. 한 글자 단어는 어떻게 만들어지나? → BOS → 글자 → (2번째 뽑기에서) EOS. 모든 단어는 EOS를 만나 끝나고, 길이 = EOS 전까지 뽑은 글자 수
15. "~법 뒤에서 잘 끝난다"는 반영됐나? → P(EOS|법) = 69.1%로 반영. 하지만 위치(첫 글자 '법')와 2글자 어미(~하기)는 구분 못 함
