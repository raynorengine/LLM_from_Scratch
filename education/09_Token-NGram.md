# 3-a. 토큰에 번호 붙이기

## 왜 번호가 필요한가

N-그램 표가 저장하는 것은 결국 이것이다.

```
(앞 토큰들) 다음에 (이 토큰)이 → 몇 번 나왔다
```

여기서 토큰을 `세기/NNG` 같은 **문자열 그대로** 들고 다니면, 같은 토큰인지 볼 때마다 **글자를 하나씩 맞춰 봐야 한다.** 우리 데이터는 토큰이 146만 개다. 느리고, 메모리도 문자열 길이만큼 든다.

번호로 바꾸면 **정수 비교 한 번**이면 끝난다.

> **질문: 토큰화가 제대로 됐는지 확인하려고 번호를 붙이는 건가?**
> 아니다. 둘은 별개다.
> - **번호 붙이기** = n그램을 정수로 세기 위한 **준비**
> - **토큰화가 제대로 됐나** = **검증**(`step7-3a_verify.py`)이 따로 한다

## Step1~6에도 있었다

이 작업이 Step7에서 새로 생긴 것처럼 보이지만, **Step4·5·6 전부 하고 있었다.** 코드 안에 묻혀 있어 단계로 보이지 않았을 뿐이다.

```c
// step6_5gram.c:415
g_cp_to_id[c] = used[c] ? g_chars++ : -1;   /* 코드포인트 -> 글자 번호 */
```

진짜로 달라지는 것은 **번호를 어떻게 찾느냐**다.

| | Step1~6 (글자) | Step7 (형태소) |
|---|---|---|
| 번호 받는 대상 | 글자 1개 | `세기/NNG` 같은 토큰 |
| 종류 | 1,562종 | **16,918종** |
| 찾는 법 | **배열 한 방** `g_cp_to_id[코드포인트]` | **해시 테이블** |

글자는 **코드포인트라는 이미 정해진 숫자**가 있다. 그걸 배열 첨자로 쓰면 번호가 바로 나온다. 64KB짜리 배열 하나로 끝이다.

토큰은 **문자열**이라 첨자로 쓸 숫자가 없다. `세기/NNG`를 몇 번 칸에서 찾을지 **계산해야** 하고, 그게 해시 테이블이다.

**앞 Step에서 배열 한 줄이던 것이 자료구조 하나로 커졌다.** 그래서 이번에는 단계를 따로 뗐다.

## 왜 Step1~6은 번호표를 파일로 남기지 않았나

Step1~6의 결과물을 보면 번호표가 없다.

| Step | 결과물 | 들어 있는 것 |
|---|---|---|
| Step1 | `step1_char_freq_result.txt` | 글자 + **빈도** |
| Step4~6 | `step6_3gram_table.txt` | **n그램 빈도표** |

빈도표마저 글자를 번호가 아니라 **글자 그대로** 적는다.

```
# prev1  prev2  next  count
BOS      BOS    "     13457
```

**이유는 "만들 필요가 없어서"다.** 글자 번호는 **코드포인트만 알면 언제든 똑같이 다시 만들 수 있다.** 데이터를 한 번 훑어 "어떤 글자가 나왔나" 표시하고 코드포인트 순으로 번호를 매기면 끝이다. 저장해 둘 가치가 없는 정보다.

Step7에서 달라진 이유는 **양이 아니라 재생성 비용**이다.

| | Step1~6 | Step7 |
|---|---|---|
| 번호의 근거 | **코드포인트** — 유니코드가 이미 정해 둔 것 | **없다. 우리가 정한다** |

`세기/NNG`가 몇 번인지는 **우리가 정한 약속**이다. 그 약속을 적어 두지 않으면 **다음 프로그램이 같은 번호를 쓴다는 보장이 없다.**

> **이건 현대 LLM에서도 똑같다.**
> 토크나이저의 어휘 파일(`vocab.json`, `tokenizer.json`)을 모델과 **함께 배포**하는 이유가 이것이다. 학습할 때 쓴 번호와 추론할 때 쓴 번호가 다르면 모델은 완전히 다른 말을 듣게 된다. **번호는 모델의 일부다.**
> `step7-3a_vocab.txt`가 그 어휘 파일에 해당한다.

## 구현에서 짚을 것 둘

### ① 해시값은 "어디부터 찾을지"만 정한다

```c
unsigned int pos = str_hash(s, len) & HASH_MASK;
for (;;) {
    int idx = g_slot[pos];
    if (idx < 0) break;                          /* 빈 칸 = 처음 보는 토큰 */
    if (strlen(g_vocab[idx].text) == len &&
        memcmp(g_vocab[idx].text, s, len) == 0)  /* 문자열을 직접 비교 */
        { g_vocab[idx].freq++; return idx; }
    pos = (pos + 1u) & HASH_MASK;                /* 충돌 -> 다음 칸 */
}
```

서로 다른 토큰이 같은 칸을 가리키는 일(**충돌**)은 일어난다. 정상이다. 그래서 같은 토큰인지는 반드시 **문자열을 직접 비교해서** 판단한다.

**해시값만 믿고 같다고 처리하면 다른 토큰이 하나로 합쳐지고, 오류도 나지 않는다.** Step6에서 n그램 키가 64비트를 넘으면 조용히 깨지던 것과 같은 종류의 함정이다.

### ② 번호를 "등장 순서"가 아니라 "사전순"으로 매긴다

```c
qsort(g_vocab, g_vocab_n, sizeof(Vocab), cmp_vocab);   /* strcmp 기준 */
for (int i = 0; i < g_vocab_n; i++)
    g_vocab[i].id = ID_BASE + i;                       /* 2번부터 */
```

등장 순서로 매겨도 입력이 같으면 결과는 같다. 그런데 **검증이 불가능해진다.**

Python 검증기가 같은 번호를 독립적으로 만들려면, 등장 순서 방식에서는 **C가 파일을 읽은 순서까지 똑같이 흉내 내야 한다.** 그러면 "다른 방식으로 교차검증한다"는 원칙이 깨진다.

사전순은 입력 순서와 무관하다. 어느 쪽이 먼저 읽든 같은 번호가 나온다. Step6에서 글자 번호를 등장 순서가 아니라 코드포인트 오름차순으로 매긴 것과 같은 이유다.

> **함정 하나**: 정렬 기준이 C는 `strcmp` = **UTF-8 바이트 순서**인데, Python의 기본 문자열 정렬은 **코드포인트 순서**다. 한글에서는 결과가 다를 수 있다.
> 검증기에서 `key=lambda s: s.encode("utf-8")` 로 명시해 맞췄다. **기준이 무엇이냐보다 양쪽이 같은 기준을 쓰느냐가 중요하다.**

## 결과

| 항목 | 값 |
|---|---|
| 문장 / 토큰 | 64,376 / 1,460,593 (2단계와 정확히 일치) |
| **어휘** | **16,918종** (BOS=0, EOS=1 포함하면 16,920) |
| 해시 적재율 | 51.6% (2¹⁵ = 32,768칸) |

```
0	BOS	0
1	EOS	0
2	!./SF	3
3	!/SF	2677
4	,/SP	15453
...
329	<S>	408173
```

BOS/EOS는 토큰 파일에 나오지 않아 빈도가 0이다. 문장 앞뒤에 붙이는 것은 다음 단계(3-b)의 일인데, **번호만 미리 잡아 두는 것은 다음 단계가 번호 체계를 다시 만들지 않게 하려는 것**이다.

### 빈도 1위가 공백이다

```
  329  <S>      408,173     ← 2위의 7배
   19  ./SF      55,091
10243  었/EP     39,216
 3420  다/EF     32,179
  483  ᆫ/ETM    17,393     ← 08 문서에서 본 그 자모 토큰
```

**전체 토큰의 27.9%가 공백이다.** n그램이 보는 문맥의 1/4 이상이 공백이라는 뜻이고, 다음 단계에서 n을 정할 때 영향을 준다.

### 어휘 수가 2단계와 1 차이 나는 이유

2단계 보고서는 16,917종, 3-a는 16,918종이다. **`<S>` 하나 차이다.** 2단계의 통계는 `<S>`를 "형태소"가 아니라고 보아 뺐고, 3-a는 `<S>`도 번호를 받는 토큰이므로 넣었다.

버그가 아니라 **정의의 차이**다. 이런 차이는 발견했을 때 어느 쪽이 맞는지 정하고 **기록해 두지 않으면 나중에 버그로 오해**하게 된다.

## 복습용 핵심 정리 (3-a)

1. **번호를 붙이는 이유는 속도와 메모리.** n그램은 문자열이 아니라 정수를 센다
2. **번호 매기기는 Step1~6에도 있었다.** 달라진 건 찾는 방법 — 글자는 코드포인트를 첨자로 쓰는 **배열**, 토큰은 **해시 테이블**
3. **글자 번호는 저장할 필요가 없고, 토큰 번호는 반드시 저장해야 한다.** 글자는 코드포인트라는 외부 기준이 있지만 토큰 번호는 우리가 정한 약속이기 때문이다. 현대 LLM이 `vocab.json`을 모델과 함께 배포하는 것과 같은 이유다
4. **해시값은 "어디부터 찾을지"만 정한다.** 같은지 여부는 문자열을 직접 비교해 판단한다. 안 그러면 조용히 틀린다
5. **번호는 사전순으로 매긴다.** 등장 순서로 매기면 검증기가 C의 읽기 순서를 흉내 내야 해서 교차검증이 성립하지 않는다
6. **정렬 기준은 양쪽이 같아야 한다.** C의 `strcmp`는 바이트 순, Python 기본은 코드포인트 순이다

# 3-b. n그램 세기

n=6으로 센다. 즉 **앞 5개 토큰(문맥) 다음에 어떤 토큰이 몇 번 나왔는지**를 모은다.

## 문장 앞뒤에 BOS/EOS를 붙인다

```
문장:  A B C
번호열: BOS BOS BOS BOS BOS  A B C  EOS
        <------ 5개 ------>        <1개>
```

- **BOS가 n-1개 필요한 이유**: 문맥이 앞 5개인데 첫 토큰을 뽑을 때는 앞이 0개다. 채울 것이 없으면 시작할 자리가 없다
- **EOS가 필요한 이유**: 끝낼 시점을 모델이 정해야 한다. 없으면 길이 상한으로 강제로 자르는 수밖에 없다

Step6(글자 단위)에서 쓴 것과 똑같다. 단위만 글자에서 토큰으로 바뀌었다.

### 검산 공식 — 패딩이 맞는지 확인하는 법

길이 L인 문장에서 n그램은 **L+1개** 나온다. 따라서:

```
전체 n그램 = 토큰 총수 + 문장 수        (n과 무관하다)
실측:  1,460,593 + 64,376 = 1,524,969  ✓
```

**패딩 개수를 하나라도 틀리면 이 값이 깨진다.** 그래서 검증 항목으로 쓴다.

## 자료구조를 바꿨다 — 문맥이 후보 목록을 들고 있다

| | Step4~6 | **Step7** |
|---|---|---|
| 저장 | `(문맥, 다음토큰)` 쌍을 해시에 | **문맥 → 후보 목록** |
| 후보 찾기 | 0번부터 V-1번까지 **전수 조회** | 그 문맥의 목록만 보면 됨 |

```c
typedef struct Entry {
    int       key[5];      /* 문맥 */
    NextOpt  *opts;        /* 후보 목록: {다음토큰, 빈도} */
    int       opt_count;   /* ← 후보가 몇 개인가 */
    long long total;       /* 후보 빈도 합 */
} Entry;
```

**바꾼 이유는 어휘가 커져서가 아니라 백오프(7단계) 때문이다.**

백오프는 *"후보가 부족하면 n을 한 단계 낮춘다"* 는 전략이다. **후보가 몇 개인지 바로 알 수 있어야** 하는데, 앞 방식에서는 그걸 알려고 매번 어휘 전체(16,920개)를 훑어야 한다. 새 구조에서는 `opt_count` 하나면 된다.

## 행 순서를 번호 오름차순으로 정렬했다

빈도표를 쓸 때 해시 칸을 도는 순서로 쓰면, **해시 함수가 바뀌면 순서도 바뀐다.** 그러면 Python 검증기가 같은 순서를 만들려고 **C의 해시 함수까지 흉내 내야 한다.**

번호 순 정렬은 해시와 무관하다. 3-a에서 번호를 사전순으로 매긴 것과 같은 이유다.

> **반복되는 원칙**: 검증기가 구현을 흉내 내야 하는 순간, 그건 더 이상 교차검증이 아니다. **구현과 무관한 기준**(사전순, 번호순)으로 정해 두면 양쪽이 독립적으로 같은 답에 도달한다.

## 질문: 표에 `<S>`나 `JKS` 같은 게 보이는데, 실제로도 이렇게 들어가나?

빈도표를 열어 보면 이렇게 생겼다.

```
BOS  BOS  BOS  BOS  BOS  ,/SP   40   0.062135
```

**아니다. 이 문자열은 사람이 읽으라고 출력할 때만 되돌린 것이고, 계산은 전부 숫자로 한다.**

코드에서 확인할 수 있다.

```c
// 파일을 읽을 때 딱 한 번 번호로 바꾼다
g_seq[g_seq_len++] = id;

// 세는 동안은 정수 비교뿐이다
if (e->opts[i].next_id == next_id) { e->opts[i].count++; ... }

// 출력 직전에만 문자열로 되돌린다
fprintf(fp, "%s	", g_id_to_tok[rows[i].ids[j]]);
```

### 숫자로 저장하면 얼마나 차이 나나 (실측)

| 저장 방식 | 크기 |
|---|---|
| **토큰 문자열** (지금 파일) | **55.8 MB** |
| 번호를 텍스트로 | 40.4 MB (73%) |
| **바이너리 (uint16)** | **15.7 MB (28%)** |

어휘가 16,920종이라 **토큰 하나가 2바이트**에 들어간다(uint16의 최대는 65,535). 실제 LLM 학습 파이프라인은 토큰 ID 시퀀스를 이렇게 **바이너리 배열**로 저장한다. 텍스트조차 아니다.

우리가 텍스트로 쓰는 이유는 하나다. **사람이 읽고 검증기가 비교할 수 있어야 해서**다. 공부용 선택이다.

### 그럼 숫자만 저장하면 `329`가 뭔지 어떻게 아나 — 어휘 파일이 그 열쇠다

```
# step7-3a_vocab.txt
0    BOS     0
329  <S>     408173
```

현대 LLM도 구조가 같다.

| | 무엇이 들어있나 | 형식 |
|---|---|---|
| `tokenizer.json` / `vocab.json` | 토큰 ↔ 번호 대응 | **사람이 읽는 텍스트(JSON)** |
| 모델 가중치 (`.safetensors`) | 숫자만 | 바이너리 |

**어휘 파일만 텍스트고 나머지는 숫자 덩어리다.** 그리고 어휘 파일은 모델과 반드시 같이 배포된다 — 학습 때 `329`가 `<S>`였는데 추론 때 다른 토큰이면 모델은 완전히 다른 말을 듣게 된다.

### 전체 흐름

```
step7-2b_tokens.txt      형태소 문자열        ← 사람용 (중간 산출물)
        ↓ 어휘표로 변환 (딱 한 번)
   C 내부 int 배열        숫자만              ← 실제 계산
        ↓ 출력할 때만 되돌림

```

실무에서는 가운데 "숫자만" 부분이 디스크까지 그대로 이어지고, 양 끝의 텍스트 파일 중에는 **어휘표 하나만** 남는다.

# 3-c. 문장 생성

빈도표가 생겼으니 그 통계를 따라 토큰을 하나씩 뽑는다.

```
BOS BOS BOS BOS BOS  ->  ?  ->  ?  ->  ...  ->  EOS 가 나오면 끝
```

## 빈도에 비례해 뽑는다

문맥의 후보가 `A(3) B(1) C(2)` 이면 합이 6이다. 0~5 중에서 난수를 하나 얻고, 후보를 앞에서부터 훑으며 빈도를 누적한다.

```
r = 0,1,2  ->  A        (누적 3이 r을 처음 넘김)
r = 3      ->  B        (누적 4)
r = 4,5    ->  C        (누적 6)
```

```c
long long r = rand_below(e->total);
long long acc = 0;
for (int i = 0; i < e->opt_count; i++) {
    acc += e->opts[i].count;
    if (acc > r) return e->opts[i].next_id;   /* 등호를 붙이지 않는다 */
}
```

**누적 비교에 등호를 붙이면(`>=`) 빈도 0인 후보도 뽑히고 경계가 한 칸씩 밀린다.** Step2부터 이어진 규칙이다.

## 함정 ① 난수가 모자란다

MSVC의 `rand()`는 **0 ~ 32,767**까지만 준다. 그런데 `BOS×5` 문맥의 빈도 합은 **64,376**(전체 문장 수)이다.

그대로 쓰면 **뒤쪽 후보가 영영 뽑히지 않는다.** 오류도 나지 않는다. 그냥 조용히 편향된 결과가 나온다.

```c
static unsigned long long rand30(void) {
    unsigned long long hi = (unsigned long long)rand();   /* 15비트 */
    unsigned long long lo = (unsigned long long)rand();   /* 15비트 */
    return (hi << 15) | lo;                               /* 30비트 */
}
```

`hi`와 `lo`를 **따로 받는** 이유도 있다. 한 식 안에 `rand()`를 두 번 쓰면 **호출 순서가 정해져 있지 않아** 같은 seed에서도 결과가 달라질 수 있다.

그리고 `% n`만 하면 앞쪽 값이 조금 더 자주 나온다(**모듈로 편향**). 그래서 n의 배수 경계를 넘는 난수는 버리고 다시 뽑는다.

## 함정 ② 재현성 — 후보를 정렬해 둬야 한다

후보 배열은 **코퍼스를 읽은 순서대로** 쌓인다. 그 순서대로 누적하면, 샘플링 결과가 **입력을 읽은 순서에 의존**하게 된다.

그래서 세기가 끝난 뒤 후보를 **번호순으로 정렬**한다(`sort_all_opts`). 이래야 같은 seed에서 항상 같은 문장이 나온다.

> 3-a의 번호 매기기, 3-b의 행 정렬에 이어 **세 번째로 같은 원칙**이 나왔다. **결과가 "읽은 순서"에 의존하면 재현도 검증도 불가능해진다.** 구현과 무관한 기준(번호순)으로 고정해 둔다.

## 질문: 빈도표 파일은 생성할 때 읽는 건가?

**아니다. 아무도 읽지 않는다.** 코드로 확인할 수 있다. 3-b가 파일을 여는 곳은 네 군데인데:

```c
fopen(path, "rb")   <- step7-3a_vocab.txt    읽기
fopen(path, "rb")   <- step7-2b_tokens.txt   읽기
fopen(path, "wb")   <- 빈도표                 쓰기만
fopen(path, "wb")   <- 보고서                 쓰기만
```

빈도표는 **쓰기로만 열린다.** 읽는 코드가 아예 없다. Step4~6도 같았다.

```
원본 데이터  --[매 실행마다 다시 센다]-->  메모리의 해시 테이블  -->  생성
                                               |
                                               +--[출력]--> 빈도표 파일
                                                              ^ 아무도 안 읽음
```

빈도표는 **결과물이지 입력이 아니다.** 그래서 `.gitignore` 대상이다 — 지워도 프로그램을 돌리면 다시 생긴다.

### 왜 저장해 두고 재활용하지 않나

**세는 게 싸기 때문이다. 262ms다.** 58MB 파일을 파싱해 해시 테이블을 복원하는 것보다 원본에서 처음부터 다시 세는 게 빠르다.

### 그런데 실제 LLM은 정반대다

| | 모델을 얻는 비용 | 모델을 어떻게 다루나 |
|---|---|---|
| **N-그램 (우리)** | 0.26초 | **매번 버리고 다시 만든다** |
| **실제 LLM** | 수일~수개월, GPU 수천 대 | **디스크에 저장하고 불러 쓴다** (`.safetensors`) |

N-그램의 "학습"은 그냥 세기라서 저장할 가치가 없다. 반면 신경망 가중치는 다시 만들려면 막대한 비용이 드니 반드시 저장한다.

**"모델 파일"이라는 개념이 왜 생겼는지**가 여기서 보인다. 학습이 비싸지는 순간 모델은 자산이 되고, 그때부터 저장·배포·버전 관리가 필요해진다.

## 질문: 이전 Step들은 세기와 생성을 같이 했는데, 왜 지금은 나눴나

맞다. `step6_5gram.c` 하나에 15구역이 다 들어 있었다.

[9] 뽑기    [10] 문장 생성  [11] 원본 일치율              <- 3-c, 5단계에 해당

**이번 분리는 코드 구조상 필요해서가 아니라, 단계별로 확인하고 넘어가기 위한 것이다.** 3-b에서 멈춰 빈도표를 들여다본 뒤 3-c로 가려고 쪼갠 것이다.

끝나고 나면 `step7-3c_6gram.c`가 Step4~6과 같은 모양의 완결된 프로그램이 되고, 3-b는 **"세기까지만 한 중간 지점"의 기록**으로 남는다.

## 생성 결과를 어떻게 검증하나

생성은 난수를 쓰므로 **"문장이 무엇인가"로는 검증할 수 없다.** 매번 달라지기 때문이다.

대신 **난수와 무관하게 항상 참이어야 하는 성질**을 본다.

|---|---|
| **모든 전이가 실재하는가** | `BOS×5`에서 시작해 한 토큰씩 밀며, 각 (문맥 → 다음)이 학습 데이터에 있었는지 |
| **EOS로 끝날 수 있었는가** | 마지막 문맥에서 EOS가 가능한 후보였는지 |
| **재현성** | 같은 seed로 다시 돌리면 같은 문장이 나오는지 |

383개 전이 전부 통과했다. 재현성 검사는 결과를 **임시 폴더**에 쓰게 해서 결과 파일 번호(01~99)를 소모하지 않는다.

12. **빈도 비례 샘플링**은 누적 합이 난수를 처음 넘는 후보를 고르는 것이다. 비교에 등호를 붙이면 빈도 0인 후보가 뽑힌다
13. **`rand()`의 범위를 확인한다.** 32,767보다 큰 합을 다루면 뒤쪽 후보가 조용히 사라진다. 오류가 나지 않아서 더 위험하다
14. **"읽은 순서"에 결과가 의존하면 안 된다.** 번호 매기기·행 정렬·후보 정렬 모두 같은 이유다
15. **빈도표는 결과물이지 입력이 아니다.** N-그램은 세는 게 싸서 매번 다시 만든다
16. **실제 LLM은 반대다.** 학습이 비싸서 모델을 저장한다 — "모델 파일"이라는 개념이 거기서 나온다
17. **난수를 쓰는 프로그램은 성질로 검증한다.** 결과물이 아니라 "항상 참이어야 하는 것"(가능한 전이인가, 재현되는가)을 본다

# 4단계. 역변환

3단계까지 끝내면 **토큰 열**이 나온다. 이제 그것을 사람이 읽는 문장으로 되돌린다.

## 왜 필요한가

3-c가 만든 것은 이렇게 생겼다.

```
침대/NNG<W><S><W>위/NNG<W>의/JKG<W><S><W>신음/NNG<W>은/JX<W><S><W>말/NNG<W>소리/NNG<W>로/JKB ...
```

**사람이 읽을 수 없다.** 그리고 읽을 수 없으면 **생성 품질을 평가할 수도 없다.**

글자 단위였던 Step1~6에는 이 단계가 아예 없었다. 글자 토큰은 이어붙이면 그냥 문장이었기 때문이다. 형태소로 오면서 생긴 비용이다.

## 방법 — 역할을 나눈다

```
침대/NNG <S> 위/NNG 의/JKG <S> 신음/NNG 은/JX ...
   ↓
침대 위의 신음은 ...
```

| 담당 | 하는 일 |
|---|---|
| **`<S>`** | 어절 경계 = 띄어쓰기 |
| **`kiwi.join()`** | 어절 **안**의 활용형 복원 (`넘어지` + `어` → `넘어져`) |
| **공백 제거** | join이 어절 안에 넣은 공백 삭제 |

이 분담은 [08 문서 2.5](08_Morpheme-Tokenization.md)에서 1,000문장으로 비교해 정한 것이다. 세 번째 항목이 빠지면 84.4%가 68.8%로 떨어진다.

**왜 어절 안의 공백을 지워도 되나**: 한 어절 안에는 원래 공백이 없다(그게 어절의 정의). 따라서 어절 내부에 나타난 공백은 **전부 join이 만든 것**이다. join은 원문의 공백을 모르고 품사만 보고 띄어쓰기 규칙을 새로 적용하기 때문이다.

```python
join([27/SN, 세기/NNG])  →  '27 세기'    숫자 + 일반명사는 띄움
join([2/SN,  미터/NNB])  →  '2미터'      숫자 + 의존명사는 붙임
```

## 결과 — 짧으면 자연스럽고 길면 무너진다

```
 1: 침대 위의 신음은 말소리로 변했다.
 4: 곧 일행은 옆방으로 들어갔다.
12: 나를 만난 로스모는 자기도 모르게 뒷걸음질쳤다.
13: 양미간을 모으고 있단 말야.
```

여기까지는 사람이 쓴 문장과 구분하기 어렵다. 그런데 길어지면:

```
 7: 보기에 추잡한 희극배우였기 때문에 이번 홍수로 온 나라 안의 어디서인가 물이 스며 나온다.
15: 그리고 물고기도 낚을 수 있는 태양에는 행성이 4개나 5개 정도가 있는데 어째서 시간 속에서다.
```

**앞부분은 멀쩡한데 뒤로 갈수록 어긋난다.** 이유는 단순하다. 모델이 보는 문맥이 **앞 5개 토큰뿐**이라, 그 너머의 일관성을 유지할 방법이 없다. 문장 앞머리에서 무슨 말을 시작했는지 **모델은 이미 잊었다.**

> 이것이 N-그램의 근본 한계다. n을 키우면 문맥은 길어지지만, 3-b에서 본 대로 **문맥당 후보가 1.25개로 줄어** 원문 복사가 된다. 길게 보려면 다양성을 잃고, 다양성을 지키려면 짧게 봐야 한다. 파트 2의 신경망은 이 맞교환을 깨려고 나온 것이다.

## 검증 — 교차검증을 할 수 없는 단계다

이 프로젝트의 검증 원칙은 *"검증은 다른 언어·다른 방식으로 작성한다. 같은 로직을 복사하면 같은 버그를 함께 가진다"* 이다.

그런데 역변환은 **`kiwi.join()`에 의존**하고, 같은 일을 하는 다른 구현이 없다. 직접 만들면 그게 곧 새로운 버그다.

### 그래서 왕복으로 잰다

```
토큰 열  →  [역변환]  →  문장  →  [다시 토큰화]  →  토큰 열
   └───────────────── 같은가? ─────────────────┘
```

복원한 문장을 **다시 Kiwi에 넣어** 원래 토큰 열이 나오는지 본다. 같다면 복원이 정보를 잃지 않은 것이다.

**이 검사가 성립하는 이유**는 `kiwi.join()`과 `kiwi.tokenize()`가 **서로 다른 함수**이기 때문이다. 하나가 틀리면 다른 하나가 그걸 되돌리지 못한다. 완전한 교차검증은 아니지만, 같은 코드를 두 번 돌리는 것과는 분명히 다르다.

> **일반화하면**: 교차검증할 상대가 없을 때는 **역함수를 찾는다.** 압축↔해제, 암호화↔복호화, 직렬화↔역직렬화 모두 같은 수법을 쓸 수 있다.

### 결과

| | 왕복 일치율 |
|---|---|
| 원본 문장 (08 문서 실측) | 85.9% |
| **생성 문장** | **86.7%** |

생성 문장이 원본보다 **오히려 조금 높다.** "생성 문장은 원본에 없던 조합이라 더 낮을 것"이라는 예상이 빗나갔다. 다만 표본이 15문장뿐이라 0.8%p 차이에 의미를 두기는 어렵다.

어긋나는 예는 대부분 **품사 판정 차이**다.

```
원래    : ... 있/VX 단/ETM 말/NNG ...
재토큰화: ... 있/VA 단/ETM 말/NNG ...
```

같은 글자인데 앞뒤 문맥이 달라지면서 Kiwi가 보조용언(VX)이 아니라 형용사(VA)로 본 것이다. **글자는 보존됐고 품사만 달라졌다.**

## 자가 시험에서 배운 것 — 장난감 입력은 검사를 망가뜨린다

검증기의 자가 시험(`--self-test`)을 이렇게 만들었다가 실패했다.

```python
src  = [(1, ["가/NNG", "<S>", "나/NNG"])]   # 장난감 토큰 열
good = [(1, "가 나")]                       # 정상이므로 PASS 여야 함
```

**PASS여야 할 케이스가 FAIL로 나왔다.** 왕복 검사가 걸린 것이다 — Kiwi는 `가`를 `가/VV`(동사 '가다')로, `나`를 `나/NP`(대명사)로 볼 수도 있어서 원래 토큰 열과 달라진다.

고친 방법은 **실제 문장을 쓰는 것**이다.

```python
sent = "곧 일행은 옆방으로 들어갔다."
src  = [(1, retokenize(kiwi, sent))]   # 실제로 토큰화해서 만든 토큰 열
good = [(1, sent)]
```

> **교훈**: 자가 시험 입력도 **실제 데이터의 성질을 가져야 한다.** 장난감 입력은 검사 로직 자체를 오작동시켜, 멀쩡한 코드를 고장 났다고 보고하게 만든다.

## 복습용 핵심 정리 (4단계)

18. **형태소 단위로 오면서 역변환 단계가 새로 생겼다.** 글자 토큰은 이어붙이면 문장이었지만 형태소는 아니다
19. **띄어쓰기는 `<S>`가, 활용형은 `join()`이 책임진다.** 둘의 역할이 다르고, join이 어절 안에 넣은 공백은 지운다
20. **짧은 문장은 자연스럽고 긴 문장은 무너진다.** 문맥이 5토큰뿐이라 그 너머를 기억하지 못한다
21. **교차검증할 상대가 없으면 역함수를 찾는다.** `join` ↔ `tokenize` 왕복이 그것이다
22. **자가 시험 입력도 실제 데이터의 성질을 가져야 한다.** 장난감 입력은 검사 자체를 오작동시킨다

# 5단계. 원본 비교

문장을 만들었으니 이제 물어야 한다. **이게 새 문장인가, 외운 것을 뱉은 것인가?**

## 과적합 — 이 단계가 재려는 것

강의의 비유가 정확하다.

| | 기출문제 외우기 | 원리 이해 |
|---|---|---|
| 같은 문제 | 100점 | 90점 |
| 새 문제 | **0점** | 85점 |
| 이름 | **과적합(overfitting)** | 일반화(generalization) |

> **과적합**: 학습 데이터에만 지나치게 맞춰져, 새로운 데이터에서는 쓸모가 없어지는 현상. N-그램만의 문제가 아니라 **모든 머신러닝의 핵심 개념**이고 파트 2의 신경망에서 다시 나온다.

N-그램에서는 **n이 커질수록** 과적합이 심해진다. 3-b에서 본 숫자가 그 예고편이었다 — 문맥당 평균 후보 **1.25개**. 후보가 하나뿐인 문맥에서 모델이 할 수 있는 일은 원문 복사뿐이다.

## 지표를 잘못 고르면 속는다

Step1~6은 **통째 일치**(문장 전체가 원본에 있나)만 쟀다. 그런데 이 지표에는 구멍이 있다.

```
원본: ... 하비가 인간의 마음속을  읽을 줄 안다고?
생성: ... 하비가 인간의 마음속을 [빌리는 대신에 ...]
      └──── 30토큰 그대로 복사 ────┘
```

**60토큰 중 30토큰을 베꼈는데 통째 일치는 0%다.** "새 문장"으로 집계된다.

그래서 지표를 하나 더 만들었다.

| 지표 | 재는 것 |
|---|---|
| ① 통째 일치율 | 문장 전체가 원본 문장과 같은가 |
| ② **최장 복사 구간** | 원본과 **연속으로** 겹친 최대 토큰 수 — 부분 복사를 잡는다 |
| ③ 중복 생성 | 같은 문장을 두 번 뱉었나 |

②를 **복사 비율**(최장 복사 ÷ 문장 길이)로 환산해 보고한다.

## 비교는 토큰 열로 한다

비교 대상이 둘 있다. 4단계가 복원한 **문장**이 아니라 3-c가 뱉은 **토큰 열**을 쓴다.

```
3-c 토큰 열  vs  원본 토큰 파일     ← 이것
4단계 문장   vs  원본 문장
```

복원 문장으로 비교하면 **왕복 85.9%의 복원 손실이 섞인다.** 모델은 원문과 똑같은 토큰 열을 뽑았는데 `kiwi.join()`이 글자를 다르게 복원해서 "새 문장"으로 잡히는 일이 생긴다.

> **일반화하면**: 무언가를 측정할 때는 **재려는 것 말고 다른 것이 끼어들 길을 막아야 한다.** 여기서 재려는 것은 "모델이 암기했는가"이고, 토크나이저 성능은 그것과 무관하다.

## 결과 — ①과 ②의 간극

200문장을 생성해 쟀다(n=6).

| | 값 |
|---|---|
| ① 통째 일치 | **24.5%** (49/200) |
| ② **평균 복사 비율** | **71.0%** |
| 평균 최장 복사 | 12.6토큰 (평균 문장 길이 23.1토큰) |
| ③ 중복 문장 | **0개** |

**①만 봤다면 모델을 3배 과대평가할 뻔했다.** "4문장 중 3편은 새 문장"처럼 보이지만, 실제로는 평균적으로 문장의 **2/3 이상이 원문 그대로**다.

분포를 보면 ①이 무엇을 놓쳤는지 보인다.

```
복사 비율 100%     52      ← ①이 잡는 것
         95~100%   0
         75~95%   43      ← ①이 놓치던 것. 거의 다 베꼈는데 "새 문장"
         50~75%   64
         50% 미만  41
```

### `95~100%`가 비어 있는 것도 말해 준다

**"한두 토큰만 틀린" 문장이 하나도 없다.** 전부 베끼거나, 아니면 꽤 일찍 갈라진다.

이유는 문맥 구조에 있다. 한번 원본에서 벗어나면 **문맥 5개가 통째로 바뀌어** 원래 궤도로 돌아올 길이 없다. 복사는 "중간에 살짝 벗어났다 돌아오기"가 아니라 **한 번 갈라지면 끝**이다.

### 중복이 이미 0이다 — 강의와 다른 점

강의가 백오프의 성과로 든 것이 *"중복 문장이 사라졌다"* 였다. 그런데 **우리는 백오프 전에 이미 200문장 전부가 서로 다르다.**

3-b의 숫자로 설명된다 — `BOS×5` 문맥의 후보가 **5,665개**다. 출발점이 이렇게 넓으면 200번 뽑아도 겹치지 않는다. 강의 데이터가 더 작았던 것으로 보인다.

> **그래서 7단계에서 백오프를 평가할 때 중복 지표는 쓸 수 없다.** 0에서 0으로 가는 지표로는 개선을 증명하지 못한다. **②가 유일하게 의미 있는 before/after 지표다.** 지표는 "개선되면 움직일 수 있는 것"이어야 한다.
> *(단서: 이 결론은 **프롬프트 없는 생성**에 한정된다. 6단계에서 뒤집힌다)*

## 검증 — "더 긴 건 없는가"까지 물어야 한다

C가 "최장 복사 16토큰"이라고 했을 때, 확인할 것이 **둘**이다.

| 검사 | 놓치면 |
|---|---|
| (a) 16토큰짜리 구간이 **실제로 원본에 있는가** | 과대평가를 놓친다 |
| (b) **17토큰짜리 구간은 어디에도 없는가** | **과소평가를 놓친다** |

(a)만 하면 C가 최장 구간을 **못 찾고 지나쳐도 검증이 통과한다.** 최댓값을 주장하는 계산은 "그 값이 맞다"와 "그보다 큰 건 없다"를 **둘 다** 보여야 한다.

그리고 Python 검증기는 C와 **다른 알고리즘**을 쓴다.

```
C      : 토큰 번호 → 등장 위치 역색인을 만들고, 시작점마다 따라가며 늘린다
Python : 원본을 "|토큰|토큰|" 문자열 한 덩어리로 만들고 부분 문자열로 찾는다
```

구분자 `|`로 토큰을 감싸는 이유는 **경계 사고를 막기 위해서**다. 그냥 `말/NNG`로 찾으면 `소말/NNG`에 걸린다.

## 복습용 핵심 정리 (5단계)

23. **과적합은 "외웠나 이해했나"의 문제다.** N-그램은 n이 커질수록 외우는 쪽으로 간다
24. **지표를 잘못 고르면 모델을 과대평가한다.** 통째 일치 24.5% 뒤에 평균 복사 71.0%가 숨어 있었다
25. **재려는 것 외의 요인이 끼어들 길을 막는다.** 암기를 재는 자리에 토크나이저 복원 손실을 섞지 않는다
26. **움직일 수 없는 지표는 지표가 아니다.** 중복률은 이미 0이라 백오프의 효과를 증명할 수 없다
27. **최댓값을 검증할 때는 "그보다 큰 건 없다"까지 확인한다.** 한쪽만 보면 과소평가를 통과시킨다

# 6단계. 특정 단어로 시작하기 (프롬프트)

## 지금까지는 모델에게 아무것도 시키지 않았다

3-c의 생성은 전부 이렇게 출발했다.

```
문맥 = BOS BOS BOS BOS BOS        "아무 말이나 해 봐"
```

6단계는 **출발 문맥을 우리가 채운다.**

```
문맥 = BOS BOS BOS 돈/NNG 을/JKO   "'돈을'로 시작해서 이어 봐"
```

구현은 이게 전부다. BOS 5개를 깐 뒤 프롬프트 토큰을 밀어 넣으면, 앞쪽 BOS가 창 밖으로 밀려나며 문맥이 완성된다.

```
history: [BOS BOS BOS BOS BOS] 돈/NNG 을/JKO
          └ 밀려남 ┘ └──── 마지막 5개가 문맥 ────┘
```

> **프롬프트(prompt)**: 모델에게 주는 시작 문맥. **ChatGPT에 글을 넣는 것이 바로 이 동작이다.** 사람이 친 글이 모델의 문맥이 되고 모델은 그 뒤를 잇는다. 장치는 같고 문맥 길이(5 vs 수십만)와 모델 종류만 다르다.

프롬프트를 **특별 취급하지 않는 것**이 중요하다. 생성 문장에 프롬프트도 포함하고, 그 뒤는 평소대로 뽑는다. 그래야 "모델이 그 토큰들을 스스로 뽑았을 때"와 완전히 같은 상태가 되고, 결과를 3-c와 직접 비교할 수 있다.

## 여기서 처음으로 **생성이 실패한다**

3-c에서는 한 번도 막히지 않았다. 이유가 있다. 생성 중에는 **실재하는 전이만 따라가므로** 도달한 문맥에는 반드시 다음 후보가 있다.

그런데 프롬프트는 **우리가 멋대로 만든 문맥**이다. 학습 데이터에 없을 수 있다.

실제로 세 가지 실패를 만났다.

| | 프롬프트 | 무슨 일 |
|---|---|---|
| ① 문맥이 없다 | `로봇이 돈을` | 이 5토큰이 6.4만 문장에 **한 번도** 연달아 안 나온다 |
| ② 어휘에 없다 | `그는 천천히 고개를 들었` | 활용이 끊겨 `ᆻ/Z_CODA` 같은 **종성 조각**이 나온다 |
| ③ 문장 시작을 잊는다 | `컴퓨터가 노래를 부르` | 7토큰이라 BOS가 전부 밀려났다 |

①이 **7단계(백오프)가 존재하는 이유**다. 사람이 보기엔 멀쩡한 한국어인데 모델은 할 말이 없다. 백오프는 이때 n을 낮춰 더 짧은 문맥으로 이어 가는 전략이다.

②는 예상 밖이었다. 막히는 지점이 문맥 조회보다 **한 단계 앞**, 즉 토큰화 결과가 어휘에 없는 데서도 생긴다. 프롬프트는 **완결된 말**이어야 한다.

③은 막히지는 않지만 더 미묘하다. 문맥이 5개뿐이라 프롬프트가 5토큰을 넘으면 BOS가 하나도 안 남는다. 모델은 **자기가 문장 첫머리에 있다는 사실 자체를 모른다.**

> 막혔을 때 **아무 토큰이나 억지로 고르지 않는다.** 그러면 "모델이 만들 수 있는 것만 나온다"는 성질이 깨져 5단계 검증이 통째로 무의미해진다. 막혔다는 사실을 그대로 기록하는 것이 옳다.

## 결과 ① — 강의 결과가 재현됐다

`돈을`로 15문장을 뽑았더니 10번 문장이 이것이다.

```
생성: 돈을 두 배로 걸고 하기로 했다.
강의: 돈을 2배로 걸고 하기로 했다
원본: 돈을 두 배로 걸지 않겠어
```

`걸`까지 원문을 따라가다 그 뒤를 다르게 이은 것까지 같다. (강의가 `2배`로 적은 것은 전처리 차이로 보인다.)

## 결과 ② — 프롬프트는 암기를 심화시킨다

5단계에서 만든 측정 도구를 **고치지 않고 그대로** 돌렸다. 출력 형식을 3-c와 같게 맞춰 둔 덕이다.

| 200문장 | 프롬프트 없음 | 프롬프트 `돈을` |
|---|---|---|
| 통째 일치 | 24.5% | 14.0% |
| 평균 복사 비율 | 71.0% | **74.6%** |
| **중복 문장** | **0%** | **39%** (78/200) |

출발점을 고정하면 갈 수 있는 길이 줄어든다. `돈을`로 시작하는 원본 문장은 **7개뿐**이고, 첫 문맥의 후보는 **1개**였다. 200번을 뽑아도 사실상 같은 몇 갈래를 반복하게 된다.

가장 극단적인 예가 11토큰 프롬프트다.

```
1~10: 그는 천천히 고개를 들었다.     ← 10문장이 전부 같다
```

후보가 1개라 모델이 덧붙일 수 있는 것이 마침표 하나뿐이었다.

## 5단계에서 한 말을 고친다

5단계에서 *"중복률은 이미 0이라 백오프 지표로 쓸 수 없다"* 고 했다. 그 말은 **프롬프트 없는 생성에 한정**된다.

강의가 백오프를 평가한 조건은 **프롬프트 고정**이고, 그 조건에서는 중복이 39%다. 충분히 움직이는 지표다.

> **교훈**: 지표를 평가할 때는 **어떤 조건에서 쟀는지**가 지표 값만큼 중요하다. "중복 0%"는 사실이었지만, 조건을 빼고 "쓸모없는 지표"라고 결론 낸 것이 성급했다.

## 복습용 핵심 정리 (6단계)

28. **프롬프트는 출발 문맥을 채우는 것이다.** 프롬프트 길이만큼 BOS가 밀려난다. ChatGPT도 같은 동작이다
29. **프롬프트를 특별 취급하지 않아야** 모델이 스스로 뽑은 것과 같은 상태가 되고, 결과를 비교할 수 있다
30. **생성이 실패할 수 있는 곳은 출발점뿐이다.** 도중에는 실재하는 전이만 따라가므로 막히지 않는다
31. **막혔을 때 억지로 메우지 않는다.** "모델이 만들 수 있는 것만 나온다"는 성질이 깨지면 검증이 무의미해진다
32. **지표는 측정 조건과 함께 읽는다.** 중복률은 프롬프트 없이는 0%, 프롬프트를 주면 39%다
